# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security
- **`javascript:` hrefs no longer reach a capture pane or the reader sidecar.** `lib/capture/profiles/util.js`'s `absolutize` explicitly listed `javascript:` among the schemes it passed through, so `<a href="javascript:alert(1)">` in a captured page was emitted verbatim into the reader-lite pane — mounted with `innerHTML` into a shadow root in the surface's own origin — and into the `<id>.simplified.html` sidecar the daemon serves over HTTP. The file's own header claimed a second line of defence ("the shadow mount sanitizes too"); nothing downstream sanitizes, and a recursive grep of `public/` for it finds nothing. The three bundled profiles that build their own `<a>` HTML (wikipedia, reddit, youtube) had three more copies of the same helper, none of which gated a scheme either. `lib/capture/markdown.js` did have a gate, but a regex one, and it was bypassable with no base URL — `java\tscript:alert(1)` went through as written, and `url` is optional in the `/api/capture` body. There is now one gate, `safeHref(href, pageUrl)`, which normalises through `new URL` (which strips the tab before the scheme is read, exactly as a browser does) and returns `''` for anything outside http/https/mailto/tel. The link text is kept; only the href is dropped. The lenient `absolutize` that rides the same helper kit — the one bundles reach for when they want an unresolvable value back unchanged — refuses `javascript:`/`vbscript:` after resolution rather than merely omitting them from a passthrough list, which on its own closed nothing (the `new URL` fallback underneath returned them verbatim). The gmail bundle's attachment download link, the one href in the bundled set that had no resolver at all and so met no gate, goes through `safeHref` too; a refused link leaves the attachment listed with its name, size and type.

- **The `git-dashboard` service no longer lets a pane turn a store value into a git option.** The pane picks what to show by writing `git_ctl { viewing, open }`, and the service passed both straight into git's argv. `execFile` keeps a shell out of it and the trailing `--` separates revs from paths, but git parses any earlier argv word beginning with `-` as an option — and `git log`/`git show` accept `--output=<file>`. The store is writable by every pane script in the page and by any local process, so once a user had run `claude-web-chat trust git-dashboard` (the builtin they are pointed at as the reference service), anything on the surface could make the daemon overwrite a file the user can write — a shell rc file, a `.git` hook — with git-log text. `viewing` is now accepted only when it matches a branch name the service itself just read, `open` only when it looks like an object name (`[0-9a-f]{7,40}`), and every ref is fenced behind `--end-of-options` on git 2.24+. A refused value falls back to the checked-out branch, which is what the pane already displays, so nothing about ordinary use changes.

  **After upgrading, service-backed components ask for trust once more.** Consent is keyed to the contents of `service.js`, so this fix invalidates the existing grant: run `claude-web-chat trust git-dashboard` (or bare `claude-web-chat trust` to see everything waiting) the first time a service pane comes up empty.
- **The `file-editor` service no longer lets a pane read past its own fence, or rewrite a file nobody asked it to.** Three fixes to the same input, all of it arriving in the `editor_ctl` store key that every script in the page can write. (1) A **version id** was joined into the snapshot directory unchecked, so `{action:'revert', version:'../../../../etc/passwd'}` read any file the daemon could and pushed it into the pane's buffer — an id must now match the `v<N>` shape the service mints *and* appear in the index it wrote. (2) The **path fence** was lexical, and reads and writes follow symlinks, so a link inside the project pointing out of it was followed; containment is realpath-based now, through the daemon's one containment engine (services get it as `ctx.fence`). (3) On respawn the service **replayed the persisted control write**, whatever it was — and the pane never clears that key, while the service is respawned every time the last viewer leaves, the pane returns to the active node, or the daemon restarts, and restoring a graph node puts that node's control write back. So a stale `save` silently rewrote the file on disk with an old buffer: save in the pane, close the tab, fix the file in your editor, reopen the tab, and your edit was gone. A respawn now replays only `open`/`browse` and seeds its cursor from the stale write, so later writes are still honoured and a mutation is never re-executed.

  **Two things you may notice.** A symlinked path that escapes the root via realpath is now **refused** — including a link whose target does not exist yet, which is the shape a write would have *created* outside the root. If you were reaching a file outside the project through a link committed in the repo, open it with `unfenced: true` (which is what that param is for, and what you approve when you trust it) or point `root` at the tree you mean. And, as above, **service trust is keyed to the contents of `service.js`**: run `claude-web-chat trust file-editor` once after upgrading, the first time the pane comes up empty.
- **A pack archive can no longer OOM the daemon by decompressing.** `listTarGz` — the pre-extraction gate every pack install passes through — gunzipped the whole archive into one Buffer with no ceiling. The download cap (64 MB) bounds nothing on that side: deflate compresses a run of zeros at roughly 1000:1, so a 64 MB body inflates to tens of gigabytes, and `Buffer.MAX_LENGTH` is 2^53-1, so nothing refused the allocation — the daemon holding the live graph was OOM-killed rather than throwing anything catchable. The install endpoint is reachable by any pane's `fetch`, so a rendered script (or a pasted URL) could take the process down. The inflate is now capped at 256 MB and the overflow is reported as a refusal naming the archive. The same cap bounds extraction: the listing runs before the file is handed to `tar`, and the bytes it measures are the bytes `tar` would write.

- **A component name is validated before it becomes a path, at every entry.** `GET /api/components/:name`, `GET /api/components/:name/seed` and `POST /api/components/:name/use` had no name validation at all. Express decodes `%2f` into a route parameter, so `/api/components/..%2f..%2fx/seed` arrived as the name `../../x` and was joined and `existsSync`'d unguarded: `/seed` served any `<dir>/seed.js` on disk, `/:name` any `<dir>/component.html`, and `/use` both read that file and wrote the name into `mount.component` — the string the service supervisor turns into the `service.js` path it forks. The kebab grammar is the containment rule (a name that cannot carry a separator cannot leave the components directory), and a name that fails it now answers 404. `lib/packs`'s `verifyPack` re-checks a *recorded* unit name the same way before `removeUnits` unlinks inside the directory it names; a unit that fails is reported and skipped rather than removed, so `pack remove` over a damaged record degrades instead of deleting elsewhere.

### Added
- **One project-registration engine — `lib/setup/registration.js`.** "Registered with Claude Code" is a model now, not eight opinions: `resolveRoot(cwd, {mode})`, `inspect(root)`, `apply(root, …)`, `remove(root, …)`, plus `hookEvents()` / `mcpArgv()` / `removeArgv()`. `doctor`, `status`, `install`, `uninstall`, `on`, `off`, `update` and the MCP dispatcher are all on it. What that consolidates: five different answers to which root a command operates on (install/uninstall/on/off anchored on `process.cwd()`, doctor/status walked up to `findProjectRoot`, update skipped its whole sync when that returned null); two hook counts that counted different things — doctor counted handlers, status counted handler groups — and neither compared what is registered against `templates/settings.hooks.json`; two contradictory `${CLAUDE_PLUGIN_ROOT}` policies in the same tree; an MCP argv doctor built from `__dirname`; and a `remove` that had never heard of the local-scope registration doctor's repair writes. It sits **above** `lib/update/managed-files`, which keeps every export (a pack installer must not become a dependent of a CLI-registration module), and `update` loads it out of `versions/<target>`, so its export surface is a cross-version contract. The guardrail is a round-trip test (apply → inspect → remove → inspect) scoped to the model's own fields, with `.web-chat/`, the migrations and the daemon named as excluded, plus one test proving all six project commands resolve the same root from the same subdirectory. A conventions row keeps it singular: `findProjectRoot(` is held at zero in those eight files, while every other command legitimately keeps walking up to find a *daemon*.

- **`process.kill(` joined the conventions ratchet.** Its homes are `lib/core/portfiles.js` (`isPidAlive` — the one `kill(pid, 0)` liveness probe, and the only copy that type-guards the pid) and `lib/cli/commands/stop.js` (the single SIGTERM escalation after an unacknowledged shutdown request), plus the two hub bounces, which signal only the pid `/api/health` just reported. `lib/cli/commands/ls.js`, which had re-declared the liveness probe three lines under the import of the module that exports it, is at zero — and the shrink-only rule keeps it there.
- **A first test for `ls`, the machine inventory and `--reap`.** None of the test files covered any of it: nothing seeded `~/.web-chat/instances.json` with a dead or a live-but-unreachable pid, and nothing asserted what `--reap` signals or leaves behind. `test/registry-ownership.test.js` pins the registry entry's ownership rule the way `test/portfile.test.js` pins the portfile's, and `test/daemon-portfile-ownership.test.js` — whose header used to note that the registry "never runs" in it — now boots its two real daemons with a registry under a fake HOME and asserts the surviving daemon keeps its entry.
- **`lib/capture/pane.js` — the capture pane renderer, out of the route file.** `defaultReduce`, `wrapModes`, `renderProfilePane`, `renderSimplifiedPane`, `feedbackCard` and `selectionCard` are pure functions of (record, distilled, mode, paths), and they lived in `lib/server/routes/capture.js`, which exported `defaultReduce` beside `mountCaptureRoutes` purely so `claude-web-chat profile dry-run` could reach across entry points for it — and then re-implemented the reduce-then-render step inline anyway, omitting the mode wrapper, so the dry-run preview was not what the surface renders. Both now call the one copy, and `profile dry-run` shows the wrapper.
- **`loadBundle(dir)` / `validateMeta(meta)` — one capture-profile bundle loader.** `claude-web-chat profile validate` is the gate the `/capture-profile` skill runs before every save, and it was a second loader with acceptance rules that disagreed with the daemon's three ways. See *Changed* for what that means for a bundle you already have.
- **Extractors and panes are handed a helper kit.** `extract({ url, html, root, esc, collapse, safeHref, absolutize })` and `render(distilled, ctx)` with the same four on `ctx`. A profile bundle lives outside the package with no require path back into it, so injection is the only mechanism it has — which is why nine hand-rolled `esc` declarations (in four character sets) and three incompatible URL helpers had accumulated across the bundled profiles. All are gone; the skill and `docs/capture-profiles-and-panes.md` document the kit, and the conventions tripwire gained a row on the *declaration* spelling (`const esc =` / `function esc(`) so a tenth cannot appear regardless of how its body is written. That row also scans `templates/` `.html`, which the ratchet had never looked at — the two builtin component templates are pinned there, since a pane script evaluated in the browser has no module scope to import from. One byte-level consequence: the injected `esc` is the repo's five-character `escapeHtml`, where the copies it replaces escaped four, so the HTML fields the wikipedia, reddit and youtube distillates carry (`summaryHtml`, `valueHtml`, `textHtml`, …) now serialise an apostrophe as `&#39;` rather than leaving it raw. It renders identically, but `get_captures` bytes change for those three profiles — which the *Changed* note below, written when only the reader render was affected, said would not happen.

- **A dependency-direction ratchet — `test/dependency-direction.test.js`.** `docs/extending.md` has always drawn the import direction (`core` ← `client` ← everything, and entry points never reaching into each other's internals), but it was a paragraph, and a paragraph is one lazy `require` away from being wrong. It already was, in four places, each the same mistake: a generic leaf helper parked above the leaf layer, so a subsystem that only wanted the helper had to import a whole other subsystem to get it. The test parses every relative `require()` under `lib/`, maps it to an edge between subsystems, and fails any edge the direction forbids that is not in a named baseline — each baseline entry carrying the reason it is allowed, and the baseline shrink-only, so a consolidation has to tighten the rule in the same PR. It also fails on a new top-level directory under `lib/` that no layer claims.
- **One durable-JSON-record engine — `lib/core/fsjson.js`.** `writeJsonAtomic` (serialize, write a per-pid temp file in the same directory, `renameSync` over the destination) and a four-state `readJson` that returns `ok` / `absent` / `corrupt` / `invalid` instead of collapsing them, plus `readJsonOr` for the readers that want one fallback and `renameAside` for the readers that must not destroy what they could not parse. The write idiom existed twice with two different spellings (`${p}.${pid}.tmp` in the instance registry, `${file}.tmp-${pid}` in the pack store) while the three records that most needed it — graph node files, `graph/_meta.json` and `draft.json` — had no atomicity at all, and five private read helpers each collapsed a different pair of absent/corrupt/invalid into one value. Both write copies and the finding-bearing readers now go through the engine; a shape predicate stays with the type that owns it and is passed in as `validate`, because `lib/core` holds no type-specific knowledge. Two conventions rows keep it singular: one matching both per-pid `.tmp` spellings, and a `writeFileSync(` row scoped to exactly the three files above rather than to `lib/` as a whole (about eight of the ~35 sites in `lib/` are legitimately not JSON records, so a tree-wide ceiling could never reach zero).
- **A stated platform position — `docs/platform-support.md`.** macOS and Linux are supported (the full suite runs on both in CI on every push); Windows is WSL2 only. The page is deliberately honest about the difference between "supported" and "bug-free": it lists the cross-platform defects that a Windows and a Linux assessment both surfaced, rather than filing them away as somebody else's platform. Per-platform findings and test plans live on the `platform/windows` and `platform/linux` branches, written so someone with real hardware can confirm or overturn each hypothesis — every claim in them is marked observed or inferred.
- **A doc-truth ratchet — `test/doc-truth.test.js`.** Every claim a shipped doc makes that a machine can check is now checked: the MCP tools it tells you to call exist, the `/api/…` routes it cites are mounted, the `claude-web-chat <sub>` commands it prints are registered, the `claude-web-chat docs <name>` it points at ship, no doc hardcodes `localhost:5173` (the port is per-project), CLAUDE.md's route `ctx` matches the literal the server builds, `docs/extending.md`'s tripwire table names every construct the conventions ratchet bans, the README's command block matches the CLI in both directions, and CLAUDE.md's engines table is a row-subset of the full one. The walked doc set and the truth readers live once in `test-support/doc-truth.js` — including the source-parser for the CLI commands map that `test/managed-templates.test.js` had a private copy of. One allowlist, each entry carrying its reason, and the allowlist is asserted in the **inverse** direction too: an entry that names something which has since shipped fails the build, which is exactly how the old `PLANNED` map came to exempt a doc from the check it belonged to for the whole life of the shipped `pack` tooling.

### Changed
- **The test harness gained an engine, and `npm test` gained a timeout and a HOME sandbox.** Contributor-facing, but the shape was the same "copy N+1" the package's own conventions ratchet exists to stop, just inside `test/` where nothing scanned. Nine files carried a private deadline poll under four names (`waitUntil`, `waitFor`, `until`, `waitForTrigger`) with three mutually incompatible timeout contracts — throw-with-a-label vs return-false vs re-check-then-return, boolean vs first-truthy-value, one calling its predicate synchronously — and one of them had no call sites at all. Three more opened an SSE stream passing only `onOpen`, so every failure path in `subscribeSSE` (non-200, request error, close) left the promise pending forever; that is the shape behind a run that hangs instead of failing. `test-support/helpers.js` now owns one `waitUntil`, one `openSSE` that rejects on error / close-before-open / deadline, a `wsConnect`/`wsHello` that can send headers, and a `withHub` for the capture hub; `createServer` and `createHub` are resolved lazily so a test that busts `require.cache` gets the module it just reloaded rather than a stale one that would pass for the wrong reason. `npm test` adds `--test-timeout=60000` so an unsettled await is a named failing test instead of an anonymous 15-minute CI job — deliberately **not** `--test-force-exit`, which turns a leaked handle from a loud hang into a silent green. `test/harness-conventions.test.js` ratchets the five constructs back into `test-support`; fixed sleeps and `process.env.HOME =` are deliberately not ratcheted, because a good number of both are legitimate. The two security fixes shipped in 0.6.x — the WebSocket `Origin` gate and the loopback bind — finally have regression tests: the harness physically could not send an `Origin` header before, so deleting either line passed the entire suite.

- **`ls --reap` asks instead of signalling, and no longer signals a pid it cannot identify.** It used to `SIGTERM` any listed daemon whose pid was merely alive and then unlink the portfile. Two problems. `~/.web-chat/instances.json` is a user-scope file that outlives every daemon, so after a reboot its pids belong to whatever the OS handed them to next — and the row `ls` itself printed as `(not answering)` (pid alive, port silent) is precisely that recycled-pid case, and precisely the one being signalled. And a raw signal skips the `POST /api/shutdown` ask, which is what makes `gracefulShutdown` run, so every reaped project silently lost its uncommitted surface — the reason `restart` dropped its own hand-rolled kill. Reaping now goes through `lib/cli/reap.js`: a surface is stopped only when a daemon **answers on its port and reports the pid the registry named**, and it is stopped through the same acknowledged-shutdown engine `stop` uses, with a 5 s per-row ack budget rather than `stop`'s 40 s (a reap is a serial loop over N projects). Because that budget is the reaper's and not the daemon's — a live turn can hold `gracefulShutdown` for 30 s — a row that acknowledged and is still draining when it expires is reported as draining and **left to finish**; `stop`'s SIGTERM escalation is switched off for reaping (`signalAfterAck:false`), since signalling mid-drain re-enters the guarded shutdown and `process.exit`s before `writeDraft` — destroying the very snapshot the ask was for. `claude-web-chat stop`, which waits out the full 40 s worst case, keeps the escalation. **Behaviour you will notice:** a daemon that is wedged — pid alive, port silent — is no longer stopped by `ls --reap`. It is printed with its pid and a `kill` hint instead, because from the outside it is indistinguishable from a stranger's process. A row whose pid is gone is cleared from both records, and nothing that could not actually be stopped is counted as stopped. `init`'s "clear N stale registry entries" remediation calls the same function, so it now clears the registry entries its question named rather than unlinking the other project's portfile and reporting `cleared.`
- **`ls`, `init` and `init --json` tell the truth about a stale surface.** `readInstances` prunes dead-pid entries as it reads, so every row the inventory saw already had a live pid: the `live` field was permanently true, the `(dead — registry entry is stale)` annotation could never print, the "N stale entries — clear with `ls --reap`" hint described work the read had already done, and `init`'s remediation for them was unreachable. The inventory is now `lib/util/registry.rows()`, which reads the raw registry and reports one honest `{pid_alive, reachable}` per entry; the pruning stays on `readInstances`, which the capture hub's idle monitor depends on. In the `init --json` report, `surfaces[].live` is accordingly renamed **`surfaces[].pid_alive`**.
- **An invalid `profile.json` is now a logged skip rather than an inert profile.** The daemon's loader checked nothing but "extract.js exports a function", so a matcher with a typo'd `type`, an uncompilable regex, or a malformed `pane` block loaded cleanly and simply never matched — no log, no clue, and `profile validate` said ✓ for some of the same bundles. One loader means one verdict, and the verdict is stricter: a bundle whose `profile.json` fails validation (or whose `pane.js` throws at require) disappears from `list_profiles` and from the extension's "Capture with `<name>`" button, with the reason on the daemon log, instead of sitting there doing nothing. In the other direction `validate` got *less* strict where the daemon was: a bundle with no `name` is accepted and takes its directory name, which is what the daemon has always done.
- **Unresolvable relative hrefs and `data:` URLs disappear from distillates and reader panes.** The old `absolutize` returned the raw value when it could not resolve one; `safeHref` returns `''` and the caller keeps the link text. In practice this affects a page captured with no URL (the `/api/capture` body's `url` is optional) and inline `data:` images in the reader view.
- **`article` and `simplify` resolve links against the page URL, not its origin.** Both precomputed `new URL(url).origin` and passed *that* as the base, so `<a href="c.html">` on `https://x.com/a/b/page.html` resolved to `https://x.com/c.html`. On any site using relative asset paths — very common for images — the reader view showed broken images and dead links. Every `<a>`, `<img>` and `<figure>` in the article distillate, the reader pane and the sidecar is affected; they now point where the page meant.

- **Four generic helpers moved down into `lib/core`, with re-exports at their old homes.** `isInside`/`realpath` (realpath-based path containment) moved from `lib/update/install-layout.js` to `lib/core/paths` — the pack pipeline's *security* walk was importing the *updater* to get it. `escapeHtml` moved from `lib/server/util/html.js` to a new `lib/core/html.js`, still escaping all five characters (`& < > " '`) exactly as before and with no fewer-characters mode — a mode nothing calls is a promise nothing keeps. `lib/server/export.js` and both escaping sites in `lib/capture` now use the one engine: export had a private copy of the replace chain, and `lib/capture/profiles/simplify.js` a four-character lookup map (no apostrophe) that it used for `href=` and `src=` as well as text. The Node floor is now `NODE_FLOOR` in `lib/core/versions`, and the GitHub repo slug is `REPO_SLUG` there with every URL built from it. Nothing changed at any call site's behaviour except the capture reader's render — the `<id>.simplified.html` sidecar and the simplified pane now carry `&#39;` for every apostrophe, which renders identically and does not touch the `get_captures` distillate (that was already on the five-character escaper). The conventions tripwire gained rows for **both** spellings of a hand-rolled escaper — the `.replace(/&/g` chain and the `{'&':'&amp;'}` lookup map, which is the shape nine of the eleven in-tree copies actually used and which the chain row does not match at all. What the map row grandfathers is exactly the code that cannot import the engine: the eight bundled capture profiles (a profile is user-authorable, and `.web-chat/profiles/<name>/extract.js` cannot `require` out of the package — giving profiles an injected `esc` is its own change) and `public/app/esc.js`, which is the client's own five-character home.
- **`--wc-*` design tokens are sanitised in one place.** `lib/server/theme.js` declared `TOKEN_RE` and `sanitizeTokens`, and then `lib/server/export.js` and `lib/server/routes/graph.js` each declared the key filter again next to their own strip set — `[{}<>;]`, `[\n;{}<>]` and `[{}<]`, three answers to one question, with the narrowest of them guarding the tokens baked into a graph preview page. Both now call `sanitizeTokens`/`tokenDecls` from the theme engine, whose strip set is the union of the three (it takes `\r`/`\n` with it: `;{}` are already gone, so a newline cannot start a second declaration, and a token value has no business spanning lines). A conventions row pins the filter to that one home. In the same pass `writeExport` stopped hand-joining `.web-chat/exports` and reads `EXPORTS_DIR` from the path authority like everything else.
- **Every URL the CLI prints now honours `WEB_CHAT_REPO`.** The slug was declared twice (both honouring the override) and hardcoded four more times in user-facing strings that did not — so pointing web-chat at a fork moved the downloads while `update`, `version` and `init` still told you to `curl` the original repository's `install.sh`.
- **Node 22 is now the floor** (`engines: >=22`, was `>=18`). Not a preference — a dependency of `node-html-parser`, one of the four runtime deps, moved to ESM-only at `entities@5`, and `node-html-parser@8` requires `^8.0.0` of it. `require()` of an ESM module needs `require(esm)`, which landed in Node 22 (and was backported to 20.19). Below that, `entities/dist/index.js` throws `ERR_REQUIRE_ESM` while `lib/server` is still being required — so the daemon does not start and the CLI does not run at all. Pinning `entities` backwards would hand `node-html-parser` a package with a different API; Node 18 and 20 are both past end-of-life. CI now covers 22 and 24 (24 is what releases are built and run on, and it had never been tested).

- **`claude-web-chat update` now syncs the whole registration — and never touches Claude Code's own config.** The managed-file sync runs the registration engine's `apply()`, so an update also adds the `.web-chat/` line to a project's `.gitignore` when it is missing and reconciles the `.mcp.json` entry — the same steps `install` runs, minus the state directory, the migrations and the daemon pre-warm. The one thing it will **not** do is `claude mcp add web-chat --scope local`: completing an unresolvable `${CLAUDE_PLUGIN_ROOT}` stub writes Claude Code's own config, *outside* the project, and that belongs to `install` and `doctor`, which the user typed on purpose. `update` prints the command for you to run instead.

### Fixed
- **`claude-web-chat install` in a subdirectory now installs into the project, not into the subdirectory.** It anchored on `process.cwd()` with no up-tree walk, so typed in `packages/app` of an installed project it created a *second* nested `.web-chat/`, `.claude/settings.json` and `.mcp.json` — files Claude Code never loads, since it reads the project root — and from then on every command run below that directory resolved the nested install instead. It now adopts the enclosing root and says so. **If you deliberately nested a second surface inside another project, that is no longer supported**: install the inner one from a directory that is not under an installed root, or keep the two projects side by side.
- **`uninstall` is reversible again.** `doctor` (and `init`, which runs it) repairs an unresolvable MCP entry by shelling out to `claude mcp add web-chat --scope local`, which writes into Claude Code's own config — and nothing in `uninstall` had ever heard of it, so after a "clean" removal Claude Code kept spawning the MCP server for that project and the first tool call auto-spawned a daemon that re-created `.web-chat/`. `uninstall` now runs `claude mcp remove web-chat --scope local` too, tolerating "not found"; **on a machine with no `claude` on PATH it prints the command instead of reporting a removal that did not happen**. It also resolves the project root up-tree (from a subdirectory it used to print "web-chat uninstalled from <subdir>" with every row "not present" — a no-op reported as success) and strips the hook handlers for the events `templates/settings.hooks.json` defines rather than substring-scanning whatever events happen to be in `settings.json`.
- **`doctor` and `status` no longer pass a project that is missing half its hooks.** The turn lifecycle needs both: `UserPromptSubmit` takes the turn lock, `Stop` commits the node. Both commands counted handlers whose command mentioned `claude-web-chat-hook` and reported success on any non-zero count, so a project whose `Stop` hook was lost to a hand edit or a merge reported "1 web-chat hook(s) registered and resolvable" while no turn ever committed. Both now report per event against the template, and doctor repairs a missing one.
- **`doctor`'s MCP repair stops pinning Claude Code to a version directory that gets deleted.** It built the bin path from `__dirname`, which on a managed install is `~/.web-chat/versions/<v>/…` — the exact path `install` uses `stableBin` to avoid, because `pruneVersions` removes all but the newest three. Written into a *local-scope* registration (which overrides `.mcp.json` and never self-heals), that meant the MCP server silently stopped spawning three updates later while doctor kept reporting everything green. The argv comes from the engine now, and points at `~/.web-chat/current/bin/…`.
- **`install` stops rewriting a committed `${CLAUDE_PLUGIN_ROOT}` stub to your machine's absolute path.** With `CLAUDE_PLUGIN_ROOT` unset — every session outside plugin packaging — `ensureMcpRegistration` replaced the portable placeholder in a tracked `.mcp.json` with `/Users/<you>/…`, while `doctor`, facing the identical entry, deliberately left the file alone and registered at local scope instead. One policy survives, and it is doctor's: the stub is preserved and the registration is completed with `claude mcp add --scope local`.
- **`claude-web-chat update` actually syncs the new release's templates.** `reconcileManagedFiles`, `ensureHooks` and `ensureMcpRegistration` were bound at module load from the tree the process started in — the version being replaced — and the template directory is resolved relative to that module, so "sync managed files" compared your project against the *old* templates and reported everything up to date. The new rules, skills and hook template only arrived on some later `install`. The sync now runs the newly installed build's engine, loaded out of `versions/<target>` the way the daemon restart already was, and a failure to load it says so out loud instead of degrading to a silent no-op.
- **`on` in a project that was never installed refuses instead of reassuring you.** It printed "web-chat is not disabled for this project" for a directory with no `.web-chat/` at all — false reassurance, and the opposite of what `off` did with the same input. Both now walk up to the enclosing project and refuse, naming `claude-web-chat init`, when there is none.
- **An MCP tool call in an uninstalled project names a command that would help.** The project toggle scope treats "no `.web-chat/`" as disabled (correct for the hooks, which must exit silently), and the dispatcher turned that into "Run `claude-web-chat on`" — which answers "web-chat is not disabled for this project" and changes nothing. The disabled envelope carries `reason: 'not-installed' | 'marker'` now, and the hint says `claude-web-chat init` for the first.
- **`install` no longer kills `init` mid-sequence.** A malformed `.claude/settings.json` or `.mcp.json` made `install` `process.exit(1)` from inside a library call, so `init` — which calls it in-process — never reached its own `userFacing` catch, its closing lines, or the `finally` that closes the readline prompt. It throws instead, and the CLI dispatcher reports a `userFacing` error once, for a synchronous throw and a rejected promise alike.

- **Running the test suite no longer writes into your real `~/.web-chat` or bounces your live capture hub.** One test spawns a production daemon through the real spawn path, and that spawn passes no `env`, so the child inherited the developer's `HOME`: its `start()` registered a throwaway temp project in the real `~/.web-chat/instances.json` and called `ensureHub()`, which SIGTERMs and respawns a running hub whose protocol version is behind the checkout. On a machine that is dogfooding web-chat, every `node --test` run could therefore take down the hub the open surface depends on. A second, unnoticed case: the profile CLI test `spawnSync`s the real `claude-web-chat profile` against the developer's real `~/.web-chat/profiles`. `npm test` now loads `test-support/sandbox.js` via `--import`, which points `HOME`/`USERPROFILE` at a throwaway dir before any `require`, so every env-less subprocess inherits the sandbox; the autospawn test additionally takes a per-test home and waits for the daemon to exit instead of sleeping 300 ms and hoping.

- **A torn `graph/_meta.json` no longer boots you to a blank surface and then deletes your draft.** `_meta.json` is rewritten on every lock acquire and release, so it is the file a crash, a SIGKILL or a full disk is most likely to catch mid-write — and it was written with a bare `writeFileSync`. `graph.load` then swallowed the parse error with an empty `catch {}`, leaving `active` null, which is *also* what a deliberate "new graph" wipe looks like; the fall-back-to-latest recovery only fired for a non-null id, so it never ran. The daemon came up empty, and `loadDraft` was then handed that null, decided every real draft belonged to a different commit point, and unlinked it — losing the one file that exists to protect uncommitted work. All three records (node files, `_meta.json`, `draft.json`) are written atomically now, a torn or non-object `_meta.json` means "the active id is unknown" and takes the same latest-node recovery a dangling id already took, and an absent one still means "no commit point" — the distinction the tri-state read exists for.
- **A graph node file containing `null` or `{}` no longer wedges the daemon for that project forever.** The skip-on-error guard in `graph.load` promised that one unreadable node could not stop a boot, but it wrapped only the `JSON.parse`. `null` and `{}` are both valid JSON and both plausible outputs of a crash or a placeholder write, and the unchecked value then reached the chronological sort (`a.created_at`) and `n.id.replace` — throwing out of `graph.load`, which `createServer` calls unguarded. The shape is checked inside the same read now (`n<digits>` id, finite `created_at`), so an unusable file is skipped and logged. Every node the daemon has ever written passes, so nothing real is rejected.
- **A draft the daemon cannot use is kept, not deleted.** `loadDraft` was the only reader in the tree that destroyed the record it had failed to read. An unparsable `draft.json`, or one whose `base_active` names a different commit point, is now renamed aside as `draft.json.corrupt-<ts>`; the newest three are kept so `.web-chat/` cannot grow a tail of them. It is still not applied — the surface comes up on the active node exactly as before — but the bytes are recoverable by hand.
- **An unreadable `_version.json` no longer skips every pending migration.** `readVersion` returned the literal `0` for a missing file, a truncated one and an `EACCES` alike, and the runner reads `0` as "fresh project → stamp the current schema and run nothing". So a project that lost its version stamp to a crash was marked current with its migrations silently unrun — the opposite of the runner's own append-only contract. A file containing `{}` was worse: the resulting `undefined` matched neither branch and nothing was stamped at all. Absent still first-touches; an unusable file now warns on stderr and is assumed to be v1, which is safe precisely because migrations are required to be idempotent. The stamp is written atomically, so the corrupt case is much harder to reach in the first place.
- **A departing daemon could tear down the live one's registry entry.** The portfile learned an ownership rule in 0.6.x — a daemon may only remove a record that still names its own pid, because two daemons can come up on one root and the one that leaves must not take the other's note off the door. Its twin, the `~/.web-chat/instances.json` entry, was released on the very next line of `gracefulShutdown` with no rule at all. So in exactly the scenario the portfile fix was written for, an orphaned daemon's exit correctly left the live daemon's `server.json` alone and then deleted its registry entry — and with it `claude-web-chat ls`, `doctor`'s registry check, and the capture hub's routing, which is how a page capture from the browser extension finds the project it belongs to. Both records are now released through one function, `release({root, pid})`, under the portfile's exact tri-state `pid` contract; `deregisterInstance`/`deregisterHub` carry the same guard and report what they removed. Called without a pid they stay unguarded, so nothing that relied on the old behaviour changes.
- **`ensureHub` no longer stalls ~12 s in silence when the hub belongs to someone else.** The hub binds one fixed port for the machine while the registry it reads is per user, so on a shared host one user's daemon meets another's hub. If that hub was stale, the `SIGTERM` that bounces it threw `EPERM` and the error was swallowed: the first loop then waited the full window for a port that could not free, the child it spawned found the port taken and exited, the second loop waited again, and `null` came back — which the daemon discarded, so nothing was logged anywhere and only `doctor` could notice that captures had nowhere to land. An `EPERM` now ends the attempt immediately with a message naming `WEB_CHAT_HUB_PORT`, and the daemon logs a hub it could not bring up. Only `EPERM` bails: any other failure — `ESRCH`, the stale hub having exited between the probe and the signal — is logged and the wait-then-respawn goes ahead, because that port really does free.
- **HTML entities are decoded once, everywhere.** `node-html-parser`'s `rawText` is the raw source text and `text` is its decoded form, and every inline walker in `lib/capture` except `markdown.js` read `rawText`. So `<p>Tom &amp; Jerry&#8217;s&nbsp;show</p>` reached the `article` distillate as literal source text, and — because `simplify` escapes what it reads — reached the reader pane and the `.simplified.html` sidecar double-escaped, where it *displayed* as `&amp;` and `&#8217;`. The wikipedia, reddit and youtube bundles put the same double-escaped text in the HTML fields their panes inject; the gmail bundle compensated with a hand-rolled decoder that mapped six named entities, collapsed every *other* named entity to a space, and ignored numeric entities entirely (it is gone with the cause). `&nbsp;` and `&amp;` are on nearly every real page, so this touched nearly every capture.
- **A nested list no longer emits its items twice.** `<ul><li>outer<ul><li>inner</li></ul></li></ul>` distilled to the items `["outerinner", "inner"]` — the nested item once merged into its parent and once again on its own — because `article`, `simplify` and reddit's body walker all used `querySelectorAll('li')`, which descends into nested lists. They take the list's own `<li>` children now, the rule `markdown.js` already used.
- **`inspect_capture { profile }` re-runs the profile with the capture's URL.** It had no `url` parameter at all, so the re-run — the authoring dry-run the tool description advertises — ran every extractor with an empty URL: on the youtube fixture the capture path yields `videoId dQw4w9WgXcQ` and an `i.ytimg.com` thumbnail while the re-run yielded `null` for both, reddit fell back to a hardcoded origin, and every distillate's own `url` field came back `''`. The `/raw` route had `rec.url` in hand two lines above the call.
- **A `mount_suffix` collision now actually resolves.** The guard fell back to the profile's *name*, which is the value that collided in the case it logged: profile `a` with `mount_suffix: "b"` plus a profile actually named `b` both ended on suffix `b`, so their capture panes clobbered each other after a single warning that said it was using `b`. It walks to a suffix that is free.

- **Re-using a service pane's id with different params now restarts — and re-gates — the child.** The supervisor decided whether a running service was still the right one by its `service.js` hash alone, but params are the other half of what a service *does* and of what you approved: `file-editor`'s `unfenced:true` is exactly what lifts its writes out of the project root. Using a component again on an existing mount id replaces the mount in place, so the old child kept running with the old params — the pane's scope chip still reporting the old root, the requested change silently not applied — and the new shape was trust-checked only when something unrelated (a viewer leaving, a navigation) happened to restart it, at which point the pane went dark waiting for a `claude-web-chat trust` nobody had been asked for. Identity is now the pair, matching the trust key. Two bookkeeping leaks went with it: a pending trust request is retired when its pane is cleared (it was listed by `claude-web-chat trust` and re-announced to every arriving browser forever), and a crash block is dropped with its pane rather than keeping a reusable mount id blocked. Neither is retired merely because no browser is watching — a refresh must not swallow a request you are walking to the terminal to approve.
- **A service that never finished shutting down could not be killed.** The supervisor's documented fallback — IPC `stop`, then `SIGTERM` two seconds later — was answered in the child by a handler that returned immediately once a shutdown was already in flight. So a `stop()` that never resolves (an awaited stream close that never fires is the ordinary way to write one by accident) swallowed the IPC stop, ignored the SIGTERM, ignored the later disconnect, and lived on holding whatever timers, watchers or sockets it had failed to clear; there is no `SIGKILL` escalation above it. A second signal is decisive now: the child exits outright rather than waiting on the stop it is already stuck in. Cleanup that matters belongs inside the grace period — `docs/service-components.md` now says so rather than promising more than the fallback delivered.
- **A restarted service pane could leave a second copy of the service running.** The supervisor tracked each service child by mount id and bound its `exit` handler to that id alone — but a reconcile stops and respawns a mount in one synchronous pass, so the old child's exit arrived *after* its replacement was already registered under the same id. The exit was then read as the replacement crashing: the running child was dropped from tracking (and its version recorded as failed), which meant nothing ever stopped it — not clearing the pane, not the last viewer leaving, not navigating away, not daemon shutdown — and the next reconcile forked a third process writing the same store keys. The handler is bound to the child's own entry now and ignores an exit for a child that has already been superseded, the same identity check the `started` message has always made.
- **A pane could delete or hijack the surface's own chrome by naming it.** A mount id and a render target are both agent-supplied strings that nothing validated, and the client resolved them against the whole document: `render({ id: 'main' })` removed `<main>` and appended the pane to the detached element, `id: 'status'` deleted the connection pill, `id: 'overlay'` deleted the graph viewer, and `target: 'topbar'` filed a pane inside the header (the same class of mistake that shipped the 0.6.0 service-trust prompt inside the hidden graph viewer). Because the mount persists in `state.mounts` and in every committed node, the removal replayed on every reload and every later mount then threw on a null slot — the surface stayed dead until the mount was cleared from outside the browser. The client now only ever removes an element that is a mount host, and resolves a target against the list of real slots instead of by id. A pane host also no longer claims a DOM id that the chrome already owns — it carries the mount id in its dataset and mirrors it onto the element only when it is free — because the shell resolves its own chrome *live* (`document.getElementById` on every minbar reconcile, drawer open, queue-rail update): a pane named `minbar` or `drawer` used to win those lookups instead, and won them again after every reload. A comment pin resolves its anchor through that same mount-id lookup rather than by DOM id, so a pin placed on a chrome-named pane still draws instead of being silently dropped from the marker layer. Rejecting such an id outright is the server's job and comes with the mount-set engine; this is the client half, which is what stops a name bricking the surface.
- **One bad pane no longer reads as a dead surface.** The `hello` frame mounted its panes in a bare loop, so if any one of them threw, the whole handler unwound: the remaining panes never mounted and the rest of the frame — the topbar's active pill, the queue rail, the version check — never ran. Each mount is isolated now; a failure is logged and the frame carries on — and the failed mount is unwound rather than left half-built, so a later render of the same id replaces one pane instead of stacking a second beside an empty one.
- **Re-running `install.sh` upgraded nothing.** The `current` symlink was swapped with `mv -f current.incoming current`, and `mv` stat()s its destination: a `current` pointing at a version directory looks like a directory to it, so the new link was moved *inside* the old version (`versions/0.5.0/current.incoming`) instead of over it. A first install was fine; every upgrade through the curl one-liner after that unpacked the new release, printed `Installed claude-web-chat v<new>`, and left `current` — and all three commands in `~/.local/bin`, which resolve through it — running the old code. `claude-web-chat update` was never affected (its Node swap uses `rename(2)` correctly). The swap is now `ln -sfn`, and the installer is executed twice against a scratch HOME in the test suite, which is the case CI had never covered.
- **`save_component` over a builtin name permanently broke that builtin.** `POST /api/components` — what the `save_component` tool and any pane script's `fetch` hit — checked that a name was kebab-case and nothing else, and `componentsRegistry.write` then wrote a `meta.json` with no `builtin` marker. That marker is the only thing `seedBuiltins` repairs on, so a single `save_component({name: 'git-dashboard', …})` replaced the builtin with something that could never be refreshed: every later fix to `git-dashboard` or `file-editor` silently failed to land, and the pane was left pairing foreign HTML with the real `service.js`. The packs pipeline had always refused these names; the ordinary save path never did. The kebab grammar and the reserved list now live together in `lib/core/names.js` and are asserted at every writer — the save route (400 for a malformed name, 200 `{ok:false, reserved:true, hint}` for a reserved one, the shape the drawer and the tool already read), the registry write, `validateManifest` and `planInstall`. `save_component`'s description says so, so Claude does not try.

  Two consequences worth knowing about. The refusal is **prospective**: a project where this already happened keeps the shadowed component, and can no longer overwrite it back through the same route — `seedBuiltins` now names any such directory on stderr at boot, with the path to delete to get the builtin back, but it still will not touch it, because your edits are in there. And a component directory whose name is **not** plain kebab-case (hand-made, or created before the save route checked) stops resolving through the read routes rather than resolving by luck.
- **`pack remove` unlinked whatever the installed record named, with no containment check.** `.web-chat/packs.json` is project-tier, and `lib/packs/store.js` already states the threat it was written against — a repository can commit a plausible-looking `.web-chat/` tree, which is why quarantine records were moved to the user tier. The install record never got the same treatment: `verifyPack` and `removeUnits` built every path they touched by joining `unit.name` and `f.path` straight out of it. A cloned repo carrying a record whose unit names `../../../..` shows up in `pack list` as an installed pack, and the documented recovery — `pack remove <name>` — then deleted whatever the record named; over HTTP the attacker needed only the sha256 of a file whose content they already knew. The record is now validated once, at read time: a kebab-case unit name for the kinds whose name builds a directory, a file list that is actually a list, the same `..`/absolute/drive-letter refusal the archive gate uses on every recorded path, and a realpath containment check on the unit's own directory and on every recorded file that exists. That containment is anchored on the **project root** (a system-tier record's on the home), not on the unit directory — git commits symlinks, so a repository that also ships `.web-chat/components/<unit>` or `.web-chat/themes` as a link out of the project would otherwise have both sides of the check resolve through the same link and agree. A unit that fails is **refused** whole — nothing unlinked, reported with its reason, counted as drift so the HTTP path's `refuseOnDrift` stops, and kept in the record so the evidence is not erased. `--force` does not override it.
- **`planInstall` was documented as pure and created six directories.** It resolved its component registry through `lib/server/paths`, whose `resolvePaths` calls `ensureProjectDirs`, so *every* plan — including the one `quarantinePack` computes for a tree the user has **not** approved, whose whole promise is "nothing is installed, nothing is registered" — mkdir'd `.web-chat/components`, `services`, `graph`, `captures`, `themes` and `profiles` in the target project. The registry is now built from `lib/core/paths` directly. (The plan test suite only ever snapshotted files, which is how this survived; it snapshots directories now.)
- **`init` waved Node 18–21 through with a green tick.** `package.json` engines and `install.sh` both require Node 22, but `init`'s first-run precondition — the only check a dev checkout or a hand-copied tree ever sees — compared against a literal `18`. It printed `✓ Node 20.11.1`, ran the full install (hooks, `.mcp.json`, managed files), and then `open` failed eight seconds later with "server failed to start — check server.log", which is exactly the confusing first-run failure that gate exists to prevent. The floor is read from `lib/core/versions` now, a test asserts that number matches `package.json` and `install.sh`, and the refusal names both the floor and the reason for it.
- **`claude-web-chat open` died with a raw stack when there was no browser launcher.** `launchBrowser` wrapped `spawn()` in a `try`/`catch`, but a missing executable is reported asynchronously as an `'error'` event, not a throw — so the catch was dead code and no listener was attached. On any Linux server, WSL, slim container or desktop without `xdg-utils`, `open` printed "server started at http://localhost:5173" and then took an unhandled error, exiting 1 with the URL scrolled off above the trace: the "open this URL manually" fallback it was carrying all along was unreachable, and the failure read as a broken install. `launch` awaits `open()`, so it went down too. The listener is attached before `unref()` now; the `try`/`catch` stays for the synchronous `EACCES` case.
- **A departing daemon could tear down the live one's portfile.** `deletePortfileFile` unlinked `.web-chat/server.json` unconditionally, with no check that the record it removed was the caller's. `server.json` is the only thing that maps a project to a running daemon — the CLI, the browser and the MCP tools all resolve through it — so if two daemons ever shared a root (the unguarded `install` spawn that 0.6.0 closed was one way in; a concurrent spawn slipping past `spawnDaemon`'s probe is another), whichever exited first deleted the survivor's record. The result is the worst kind of running server: `status` says "not running", `doctor` reports no problems, `stop` has nothing to stop, and the daemon keeps serving and keeps writing the graph. Deletes now carry the pid the caller believes owns the file — the daemon passes its own, `ls --reap` passes the pid it listed and signalled, `doctor` passes `null` for "reap only if the process it names is gone" — and a record held by a different, still-live process is left alone. Unowned or unparseable records are still removed.

- **Turns that changed nothing no longer clutter a graph written before they stopped committing.** Fold-forward stopped a no-change turn from committing a node, but it could only ever help going forward — every graph already in use kept its existing run of byte-identical nodes, one per chat-only turn, which is exactly what makes an old graph unnavigable. (One real project here: 744 nodes, 554 of them indistinguishable from their parent.) The graph payload now reports, at read time, which nodes are identical to their parent (`collapsed`), which surviving node stands for each run (`absorbed`/`absorbed_count`), and which edge to draw (`display_parent`); the viewer hides them, attributes their triggers to the node that absorbed them, and offers a chip to show them anyway. Nothing on disk is touched — node files stay append-only and `parent_id` stays the truth — so this is reversible by turning the chip on, and the same graph read by an older build is unchanged. A node is only ever hidden when hiding it costs nothing: never a root, a fork, a tip, the active node, or one that is bookmarked or named.

- **The docs stopped claiming things the code stopped doing.** CLAUDE.md documented a route `ctx` carrying `pushEvent`/`broadcast` — the hand-paired pair its own engines table forbids — two releases after the bus replaced them. The `tab-stream` README (served live from the daemon's install page) and both driver examples told the reader to have Claude `wait_for` a key, a tool deleted with the channels rewrite, and quoted a 5 MB body limit that is 200 MB. The `embed-helper` README still sent people to `localhost:5173`, wrong for every project after the first. `docs/export-pages.md` was the pre-implementation plan, linked from the README as the user doc for export; it is now the export contract, with the plan's two still-load-bearing decisions kept as design history. `docs/capture-profiles-and-panes.md` said "shipped in 0.3.0" over four sections specifying an in-page interaction slice that does not exist — those now carry `NOT BUILT — design` banners, and its profile-reload advice names `claude-web-chat profile reload` instead of a restart. `docs/extending.md`'s tripwire table was missing two of the constructs the ratchet bans and its `projectPaths`/`userPaths` key lists predated the packs and services work — the lists are now a pointer at the source, which cannot drift. The README listed `init` twice and pinned a version number in its layout illustration.

## [0.6.0] - 2026-08-24

### Security
- **`Authorization` is now dropped on a cross-host redirect.** A GitHub release asset URL redirects to object storage on a different host, and the redirect follower carried every header across that hop. Latent while nothing minted a token — but `GITHUB_TOKEN` has to be honoured (unauthenticated `api.github.com` is 60 requests/hour/IP, and a pack install makes several), which would have turned it into a live credential handed to whoever answered at the far end. A token is also only ever minted for a `github.com` host now, never for a URL the user pasted.
- **The daemon and the capture hub now bind loopback.** Both called `listen(port)` with no host, so everything web-chat serves — the graph, the shared store (which holds whatever a `file-editor` pane has open), arbitrary HTML/JS injection through `POST /api/render`, and `POST /api/update` — was reachable from the local network with no authentication. Set `WEB_CHAT_HOST` to opt into a different interface deliberately.
- **The WebSocket endpoint now checks `Origin`.** Browsers apply no same-origin policy to WebSocket connects and the `hello` frame is an unconditional full-state disclosure, so any page a user visited could open `ws://localhost:<port>/ws`, read the entire store and every pane's HTML, and write store keys back. Non-browser clients (local drivers, the CLI) send no `Origin` and are unaffected.
- **Service consent records moved to the user tier** (`~/.web-chat/services/trusted.json`). They used to live at `.web-chat/services/trusted.json` *inside the project*, so a repository could ship its own pre-approval: cloning a hostile repo and opening it ran its `service.js` with no prompt.
- **Service consent moved to the terminal — `claude-web-chat trust`.** It used to be a decision made on the surface, which cannot work: pane scripts are compiled with `new Function` and run in the page's own window realm with `document`, `fetch` and `WebSocket`, and no CSP is served, so a component's pane can synthesise a click on any button, open its own same-origin socket and read anything broadcast to the shell, and call any localhost endpoint. Nothing delivered to that page is a secret from the code the gate exists to gate. The surface now shows a notice naming the command; only a shell can grant. Consent is also keyed per **(project root, `service.js` hash, params shape)**, so the same component in another project, an edited service, or different params each ask again — which is what stops one `file-editor` approval covering `unfenced: true`, or a cloned repo inheriting a grant.
- **Capture reads are no longer world-readable.** The CORS layer reflected whatever `Origin` arrived, so any website the user visited could read every capture — distilled content and raw DOM — from the unauthenticated `GET /api/captures*` routes. Only extension and same-machine origins are reflected now.

### Fixed
- **The surface's first paint died on Node 18 and 20.** `public/app/mounts.js` read `navigator.platform` unguarded to pick `⌘` vs `Ctrl` for the zero-state's keyboard hints, and `globalThis.navigator` only exists from Node 21 — so on the versions `package.json` actually claims to support, the `ReferenceError` escaped the `hello` WebSocket handler and took the whole initial render with it. Found by CI's first-ever run: the suite had only ever run on a maintainer's Mac, on a newer Node than any supported floor.
- **The `＋` button never closed the drawer.** Every other chrome trigger declares `aria-controls`, which is what opts it into the dismiss layer's skip-the-panel-I-own rule; `＋` declared none, so `pointerdown` closed the drawer and the button's own click immediately reopened it. It also expressed openness with `.open` while every other panel uses `.hidden`, which is why the dismiss layer carried two special cases for it.
- **A component saved mid-session was invisible in the ⌘K palette until a reload.** The palette memoised its own component list and nothing ever invalidated it. There is now one cache, invalidated by a `components` frame the daemon emits wherever the component set can move — so a `save_component`, or a whole pack install, shows up everywhere at once.
- **A component whose `meta.json` name disagreed with its directory was listed but unspawnable.** The registry listed by `meta.json`'s `name` and resolved by directory, so such a component appeared in the drawer and the palette under a name `use_component` could not resolve. The directory name is the identity now; the disagreement is shown as a chip instead of silently preferred.
- **A soft rejection from `use_component` looked exactly like success.** The drawer discarded the response, so spawning into a locked or driver-owned pane simply appeared to do nothing.
- **Service-backed components could never be approved at all.** The trust prompt was emitted as a render targeting `overlay`, which the client resolves to the graph-viewer element — `display:none` until the user presses `G`. The prompt was filed inside a hidden panel, so both shipped builtins (`git-dashboard`, `file-editor`) and every user-authored service simply never started, with no prompt and no error. Approval is now a terminal command (see Security above), and the surface's notice is re-announced to every arriving viewer so a refresh mid-prompt no longer leaves a pane sitting there unexplained.
- **`claude-web-chat docs` crashed on every installed copy.** `docs/` was missing from the package `files` allowlist, so the three pointers the shipped rules file gives Claude all died with a raw `ENOENT` stack. The directory now ships, and a future packaging slip degrades to a message instead of a crash.
- **A single truncated node file could wedge a project's daemon permanently.** `graph.load()` parsed every node through a bare `JSON.parse`, so one partial write — a crash or a full disk — threw out of the unguarded `createServer` call path and the daemon could never boot again for that project. Unreadable nodes are now skipped with a warning.
- **Re-running `install` started a second daemon on the same project** and overwrote the portfile, orphaning the first — which kept running and kept writing the same graph directory, invisible to `stop`, `status` and `doctor`. It now probes for a live instance first, matching every other spawn site.
- **A Push could report "Delivered to Claude ✓" and be silently dropped.** Two causes, both fixed: `install` pinned `WEB_CHAT_CHANNEL=1` into `.mcp.json`, which made the MCP server start a channel bridge in *every* session including ones launched without the capability flag; and the bridge's ack confirmed only that bytes were written to stdout, not that anything received them. The env now comes solely from the launch line that also carries the flag, `install`/`update`/`doctor` clean a stale one, and an ack with no live consumer leaves the batch retained so the parked-delivery backstop still fires.
- **The launch command web-chat printed could not work.** `LAUNCH_COMMAND` omitted the `server:web-chat` argument the flag requires, so the incantation shown by `install`, the queue rail and `doctor` was inert.
- **`list_components` returned cross-tier duplicates.** The registry deduped on `get` but not on `list`, so a name present in both tiers appeared twice, identically, with no signal which one `use_component` would resolve to. Shadowed tiers are now reported on the surviving entry instead.
- **`get_graph` now reports `pending_bookmark` and `pending_reaim`** — the name of a graph the user just started (applied to the next commit) and a navigation queued during the current turn. Both were previously invisible, so Claude could be working inside a graph the user had named without any way to know it.
- Documentation no longer hardcodes `http://localhost:5173`. The port is per-project and walks upward, so that URL was wrong for every project after the first — and the rules file shipped into user projects was telling Claude to send people to another project's surface.

- **The port walk now probes before binding, and web-chat's own clients dial `127.0.0.1` rather than `localhost`.** Both fell out of the loopback bind above: a bind to `127.0.0.1:P` does not collide with a process holding the wildcard `*:P`, so the walk began handing out ports that already had a server on them — and because every internal client resolved the *name* `localhost`, which is both `::1` and `127.0.0.1` on a dual-stack machine, requests could land on whichever daemon that resolution happened to pick. Observed in practice while upgrading: a new loopback-bound daemon took a port a legacy wildcard-bound one still held, and another project's queue started arriving.

### Added
- **Component packs — `claude-web-chat pack`, and the `＋` drawer's Manage tab.** A pack is a git repository that installs as components **plus a Claude skill**, and the skill is the whole point: `list_components` is a *pull* (Claude only learns a component exists if it decides to call the tool) while a skill's frontmatter description sits in context from session start. The format was specified and had no code behind it; this is the pipeline.

  Fetching prefers a published release carrying `SHA256SUMS` (verified before anything is unpacked) and otherwise falls back to the repository tarball **pinned to a resolved commit sha** — an asset can be deleted and re-uploaded under the same tag, a commit sha cannot, so the weaker-looking option is the stronger pin. `pack get` downloads for review without installing: the verified tree is staged where nothing in web-chat reads it, inert *by location* rather than by a flag someone has to check, and `pack review` shows the manifest, the install plan, every file, and what `SKILL.md` actually tells Claude. `approve` re-hashes the staged tree against a record **this machine** wrote, so a repository cannot commit its own pre-approval. Removal is per **unit**: a component whose recorded files all still match is removed whole, and one you have edited is kept whole — never stripped down to the files you did not touch. Every install, quarantine and removal appends to `.web-chat/packs/audit.log` with its actor.

  A **built-in component name is refused outright**, in either tier, for either actor, with no override: `seedBuiltins` only repairs a directory whose `meta.json` says `builtin`, so a pack shadowing `git-dashboard` would have won permanently. Your own same-named component is never silently replaced (`--replace` is terminal-only), and a pack's `service.js` is unapproved by construction — consent is keyed to the file's hash, so a fresh one still waits for `claude-web-chat trust`. The honest limit is written down in `docs/component-packs.md` and at the head of `lib/server/routes/packs.js`: the install endpoint is reachable by any pane script and **cannot tell a pane's `fetch` from a user's click**.
- **`gh` is used to fetch a pack when it is on your PATH and logged in.** A component library can be private, and the plain HTTPS path cannot reach one: it authenticates only if `GITHUB_TOKEN` happens to be exported, and even then a bare token does not carry the SAML/SSO authorization an organization requires — which the credential `gh` already holds does. When `gh` is available it resolves the commit, reads the release, and streams the tarball; it also lifts the anonymous 60-requests/hour/IP API limit that a couple of installs can exhaust. Without `gh`, nothing changes — the HTTPS path is untouched and remains the fallback.

  Scoped the same way `Authorization` is: **your `gh` credential is only ever spent on github.com**, or on an enterprise host you configured yourself via `GH_HOST`. A pack URL is pasted by whoever asked for the install — and on the surface that can be a pane script — so an arbitrary host never gets it. `WEB_CHAT_NO_GH=1` forces the plain path. Which transport ran is recorded in the pack's provenance and shown in `pack list` and the drawer.
- **The `＋` drawer is now the components *and* packs manager**, with Library and Manage tabs — tabs rather than stacked sections, so an install form never pushes the hot path (spawn a pane) below the fold. Rows carry chips for `built-in`, tier, `service` (and *needs approval* when one is waiting), `seed`, `form` and shadowing; a row spawns into a **stable slot** so panes stop stacking forever, with `⧉` for a second copy. Install leads with *Download for review*; *Install now* is secondary and takes a second, deliberate click for a URL that was never reviewed.
- **The surface has a first-run state.** `#main` used to be literally empty on first open — every other panel in the app has a considered empty state, and the one thing every new user sees first had none. It now says what the surface is, offers a prompt to paste, and names the four keys that matter (palette, component library, graph, push).
- **`claude-web-chat ls`** — every surface running on this machine, which project each one is, and on what port. The daemon is one-per-project and its port walks upward from 5173, so this was previously unanswerable; the registry the capture hub keeps already had it. `--reap` stops the ones that aren't the current project and clears stale entries.
- **`npm test`, and CI.** The suite had never run anywhere but a maintainer's Mac and nothing had ever verified Linux. `npm test` is now the correct entry point (the obvious `node --test test/` misresolves), and GitHub Actions runs it on Ubuntu and macOS across Node 18/20/22.
- **The connected-browser count is exposed** on `/api/health`. It was already tracked for the service supervisor and never surfaced, so Claude could render into a surface nobody had open, say "take a look", and be told it worked.
- **`install` writes `.web-chat/` into `.gitignore`.** Three docs already stated it was gitignored and nothing ever wrote the line, so a project was one `git add -A` from committing its graph, portfile and drafts. Idempotent, and it respects a rule you already wrote.

### Changed
- **Installing a skill no longer claims to need a Claude Code restart.** `docs/component-packs.md` stated that components are picked up live and skills are not. Checked against Claude Code 2.1.243: a `SKILL.md` written into `.claude/skills/<name>/` mid-session becomes available on its own within a few seconds, with no `/exit` and reopen. (A `.mcp.json` change still does need one — that really is read only at session start.)
- **The `UserPromptSubmit` hook no longer claims the render tools will fail.** It said so whenever the daemon was down — but the MCP client auto-spawns and the call succeeds, so the hook was talking Claude out of using the surface on exactly the turns that needed it, on the strength of a false claim. It now reports the thing it never checked: whether a browser is actually watching.
- `install`'s next steps lead with the ordinary path (restart Claude Code, then `claude-web-chat open`) and present Channels as the optional research preview it is.
- `status` reports the real channel state — connected, or parked-until-your-next-message — instead of inferring it from project wiring.
- Server tests sandbox `HOME`, so the suite no longer writes the developer's real `~/.web-chat`.

## [0.3.0] - 2026-07-12

### Added
- **Channels are the wake path, and they work everywhere.** Wake-worthy activity — page captures, declared pane signals, and shared comment pins — collects in the surface's queue rail; hitting **Push → Claude** hands over the whole batch. With the Claude Code Channels capability a Push wakes Claude live and no-prompt; without it the batch is *parked* and delivered as context with your next message. Either way there are no background listeners to arm, so the loop works on every Claude Code.
- **Bundled capture profiles.** The package now ships ready-to-use capture profiles — Gmail, Wikipedia, YouTube, Reddit, and a generic reader-lite article view — as a first-class package tier, so common sites distill cleanly the moment the browser extension is loaded, with no per-user setup. User-authored profiles still override the bundled ones.
- **Public-repo distribution.** MIT-licensed and installable in one line: `curl -fsSL …/install.sh | sh` puts the `claude-web-chat` command on your PATH straight from the public repository — no npm registry. `claude-web-chat update` (now reporting the version before and after) and the 24-hour update check target the repo too. The README leads with the one-liner and documents loading the browser extension from the installed package.

### Changed
- **Review hardening.** A pass over the queue / bridge / comment-policy substrate the wake path leans on: private comment pins no longer leak their text onto the wake bus, navigating the graph no longer strands queued items, and the surrounding fixes each landed with a test.

### Removed
