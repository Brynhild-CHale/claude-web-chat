# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Upgrading from 0.7.6

No state migration runs: nodes written by 0.7.6 open as they are (a page with no
markdown is one grid run of its panes), and no service asks for approval again —
the trust identity (`service.js` contents, project root, params) is unchanged, and
the new `after` and `place` are render arguments, not params. What you have to do:

1. **Run `claude-web-chat update` inside a web-chat project, then reload every open
   surface tab and `/exit` + reopen Claude Code.** `update` restarts that project's
   daemon, not the page or Claude Code (typed outside a project it installs the
   build and restarts nothing — run `claude-web-chat restart` in each project, or
   `update --restart-all`).
   An open tab keeps running 0.7.6's chrome against the new daemon — no markdown,
   no page title or Contents — until you reload it. A running session keeps the 23
   tools it started with: `write_markdown`, the 24th, arrives with the next
   session, and so does the session's presence in `claude-web-chat ls`, `status`
   and the Sessions panel.
2. **Run `claude-web-chat install` in each other web-chat project.** Every other
   project whose surface is open is still running 0.7.6's server — a daemon with a
   tab attached never exits on its own — and a reopened Claude Code there gets 404s
   from `write_markdown`. `install` now restarts a server still on an older build
   (one line says so), and so do `open` and `start --daemon`; to restart all of
   them at once, run `claude-web-chat update --restart-all` (from anywhere — it
   works when there is nothing new to install). `claude-web-chat ls` lists them.
   The rules file (which now teaches `write_markdown`, pages and `api.spawn`), the
   `/web-chat` command and the `capture-profile` skill changed too: `update` syncs
   them in the project you run it from; every other project refreshes on its own
   `install` (`status` says `N need refresh` until then). A copy you edited lands
   beside it as a `.new` sidecar to merge. A project becomes *known* — listed by
   `ls --all` and the tunnel picker's Inactive section, and startable from the
   picker — once its surface has run on 0.8 (its own daemon started on 0.8, or it
   was running when any 0.8 daemon started); a stopped project last used on 0.7.x
   appears after its next `claude-web-chat open`.
3. **Expect a new look, and read-only previews.** The chrome is restyled — topbar,
   block header, graph screen, queue rail, ⌘K palette — while Earthy, the default
   theme of every existing project, keeps 0.7.6's colours (bar three light-mode inks
   darkened a shade for contrast; a project created from now on starts in
   Georgetown Blue); Paper and Georgetown Blue are new
   builtin packs, and ⋯ → Settings gains a light/dark Mode switch and brand image
   slots. Previewing an older node no longer lets you edit it, and branch-on-edit is
   gone: to continue from an older node, make it active on the graph screen (**Set
   active** or **⑃ Branch**), which first preserves any uncommitted work as a node.
   Pages now carry markdown between their panes, with a title and a Contents nav.
   ⋯ gains **Sessions** (`S`) and **Replay…** (`R`). Narrow windows get a bottom
   bar, and a phone keeps its blocks interactive with the layout fixed.
4. **New commands and flags, all opt-in:** `claude-web-chat tunnel
   setup|up|down|status|logs` (nothing is reachable from outside until you run
   `setup` and `up`), `export --replay` / `--gif` / `--mp4` / `--webm`, `export
   --script <file.json>` and `--prompts`, `update --from <tarball>` and `update
   --restart-all`, `ls --all`, the VERSION / CLAUDE / TURN / VIEWERS columns of
   `ls` (and `ls --json`), and `status`'s `Claude:` line.
5. **Out-of-tree drivers: `POST /api/graph/branch-here` and the `branch-here` WS
   frame are gone** (see *Removed*). Re-aim with `POST /api/graph/active`, which
   preserves uncommitted work first.
6. **A theme you saved as `earthy`, `paper`, `georgetown-blue` or `georgetown` is shadowed by the new
   builtin.** `apply_theme` takes the builtin, and `list_themes` marks the row
   `shadows` with a hint; the file stays on disk. Re-save its tokens under another
   name to keep using it.
7. **Rolling back to 0.7.6 turns remote access off.** 0.7.6 has no `tunnel`
   command, so `update --to 0.7.6` with a tunnel portal running first stops it
   with this build's `tunnel down` (it refuses to roll back, changing nothing, if
   the portal will not stop) and says remote access is off until you are back on
   0.8 (`claude-web-chat update`, then `tunnel up`).

### Added

- **`update` names the other projects still running an older build, and `--restart-all` restarts them.** `update` restarts one daemon — the project it is typed in — and a daemon with a tab attached never exits on its own, so every other open surface went on serving the old build. After the install, `update` asks each running project's server which build it serves (the new `package_version` field on `GET /api/health`, else `GET /api/version`'s `current`, which 0.7.6 has) and lists those on another build with `cd <project> && claude-web-chat restart`; `update --restart-all` restarts them on the new build instead, one at a time, and sums up (`Restarted 2 of 2.`). It works when there is nothing new to install too. A rollback lists them but does not offer the flag, which the older build may lack.
- **`install`, `open` and `start --daemon` restart a server still running an older build.** When this project's daemon answers with a build other than the CLI's, it is restarted onto this one through `restart`, with one line: *Restarted the web-chat server on v0.8.0 — it was still running v0.7.6.* A daemon whose build cannot be read is left alone.
- **`claude-web-chat update --from <tarball>`, and dev-versioned builds to feed it.** `node scripts/build-release.js --dev` stamps `<next minor>-dev.<yyyymmddhhmm>.<sha>` (e.g. `0.8.0-dev.202609271415.5e9dc5d`) into the built artefact only — the repo's `package.json` is untouched, and a normal build stays byte-reproducible — and `update --from` installs such a tarball as the managed version through the same verify, unpack, `current` swap, bin links, managed-file sync and daemon/portal restart as a GitHub update, without contacting GitHub. The `SHA256SUMS` beside the tarball is checked (a mismatch or missing entry is refused; no `SHA256SUMS` at all needs `--yes`), a version already on disk is not overwritten without `--force`, and it refuses on a checkout like `update`. `claude-web-chat version` says `dev build (installed from a local file)` and prints the tarball's sha256; `update --list` marks dev builds; `update --to <release>` rolls back. Each build merges its line into `dist/SHA256SUMS` — replacing its own, dropping the lines of tarballs no longer in `dist/` — so an older build still there verifies too. The `update` in 0.7.5 and 0.7.6 does not know `--from` (it silently drops the flag and takes the GitHub path), so the first dev build onto such an install is unpacked into `~/.web-chat/versions/<v>/` by hand and activated with `update --to <v>` — the steps are in *Testing an unreleased build* in `docs/extending.md`.
- **Theme packs: install a theme from a GitHub link, logos included.** A pack may now ship themes as `themes/<name>/theme.json` (tokens, optional light/dark `modes`, optional `fonts`) with optional `logos/` (`logotype`, `lockup`, `seal`, each with an optional `-reversed` dark-mode mark, SVG or PNG) and `fonts/` (WOFF2 files under an OFL licence — installed with the theme but not yet loaded by the surface or exports, so name a bundled fallback after it in the token) beside it, and may be themes-only — no components and no `SKILL.md` needed. It goes through the same `pack get` → review → approve / `pack install` transaction as a component pack, lands in the theme library of its tier (`.web-chat/themes/`, or `~/.web-chat/themes/` with `--global`) with provenance, so `pack list`, `--verify` and `pack remove` cover it. While an installed theme is the project's global theme, its logos fill any brand slot the project left empty; the project's own Settings → Brand image always wins. Refused at plan time, and shown in the review: raw CSS in the theme (not allowed yet), a logo that fails the Brand upload check or is not the format its name says, a font that is neither bundled nor a licensed WOFF2, and a built-in theme name (`earthy`, `paper`, `georgetown-blue`, `georgetown`, `web-chat`) — no override. A theme's token values, top-level or in a mode, may not load anything either: one carrying `url(`, `image-set(`, `image(`, `cross-fade(`, `src(`, `expression(`, `@import`, `javascript:` or a CSS escape is refused at review like raw CSS, because the chrome paints tokens with no CSP and exports inline them, so such a value would report every viewer to its host (`lib/core/theme-values`). The check judges the value as it will be painted, and a value carrying `{`, `}`, `<`, `>`, `;` or a line break is refused outright, since those characters are stripped before a token is painted and `ur;l(` would otherwise reassemble into `url(`. See `docs/component-packs.md`.
- **Theme packs in the drawer, Settings and the terminal.** Drop a theme pack's GitHub link into ＋ → Manage like any pack: the review card draws each theme's palette per mode as a swatch strip (background, panel, text, accent, green, gold), shows its logos (served from the staged copy through a sandboxed image route, and only once they pass the Brand check), lists its fonts, and prints any refusal; a themes-only pack is no longer told it lacks a `SKILL.md`. After the install, **Apply now** makes the theme the web-chat-wide one, and ⋯ → Settings → Theme lists installed themes under **Installed** with the name of the pack they came from. `pack review` and `pack list` show a pack's themes (and `review` now prints plan-time refusals such as raw CSS), and removing a pack whose theme is the active one — `pack remove` or the drawer — puts the project back on its default theme, says so, and repaints every open surface (a `--global` pack also resets the all-projects default when it named that theme). `docs/themes.md` gains *Sharing a theme as a pack*.
- **`claude-web-chat ls` shows which projects have a Claude Code session attached.** Every session's web-chat MCP server now says so in the machine registry (`~/.web-chat/instances.json`, a `role:'mcp'` row per process) from the moment Claude Code starts it until it exits — no daemon needed, and a session that has not called a tool yet still counts. The row is written whatever the on/off toggle says, so a project where web-chat is switched off still shows its session. `ls` gains three columns: **CLAUDE** (`● 1`, `● 2 · channel` when a Push wakes one mid-session, `—`), **TURN** (`mid-turn`, or `wake` for a channel wake's turn) and **VIEWERS** (connected browsers), and lists a project that has a session but no surface too. `ls --json` prints the whole row. `--reap` is unchanged and never touches a session. The row goes when Claude Code hangs up, on SIGTERM, or at exit; a crashed session's row is dropped on the next read once its process (or the Claude Code process that spawned it) is gone.
- **Sessions say which web-chat release each surface and each Claude session runs — and which still need a restart after an update.** `claude-web-chat ls` gains a **VERSION** column, and the Sessions panel (`S`) and the tunnel picker show a compact `v0.8.0` beside each surface and each attached Claude session (a dev build's long string is clipped on the page, whole in its tooltip). A Claude Code session keeps the MCP server it started with, so after `update` one started earlier still runs the old tools: its row now carries a ⚠ — *Claude is on v0.8.0 — restart Claude Code to pick up v0.8.1* (or *1 of 2 Claude sessions is on …* when only some are), or, when it is the surface that is behind, the `claude-web-chat restart` to run there. It starts with 0.8.0: a session started under 0.7.x records no presence at all, so after this update such a session is simply not listed — restart it. `GET /api/health` gains **`package_version`** (the release; `version` stays the protocol number the hub/portal self-heal compares), MCP presence and daemon registry rows record theirs, and an inactive project remembers the release it last ran. `ls --json` rows carry `surface.package_version`, `claude.package_versions` (`[{version, sessions}]`) and `version_skew`.
- **Replays scroll to every change.** Each step of a replay — in the browser player, a `replay.html`, a GIF or a video — now smooth-scrolls its frame to what that step changed: the newest pane's top to the top of the window, then down to any other change below the fold, the first dwelling longest. Before, every frame showed its page from the top, so a pane added further down was never seen. A step that changed nothing stays where the last change was. The scroll is part of the replay's timeline, so `seek(t)` is still exact and a GIF or video draws the motion (moves are sampled at `fps` even with `transition: 'cut'`; a still stretch is still one frame). A replay script step takes **`scroll`**: `'auto'` (the default), `'none'`, or the id of one pane or markdown item on that node's page to look at instead.
- **`claude-web-chat status` has a `Claude:` line** for the current project: how many sessions are attached, whether the channel is on, and when one last called a tool.
- **A Sessions panel in the browser: every web-chat on this computer and its Claude state.** ⋯ → **Sessions** (also `S`, and ⌘K *Sessions…*) lists each project — title and `~`-shortened root, whether its surface is running (port, viewers, active node) or stopped, and whether a Claude Code session is attached (`×N` sessions, channel on/off, a **mid-turn** / **wake turn** badge while a turn lock is held, when a tool was last called). This page's own project is highlighted; clicking another running one opens it in a new tab, and a stopped one shows its `claude-web-chat open` command with a copy button — the page never starts a surface. It refreshes every 5s while open. Backed by a new local-only `GET /api/machine/sessions`, which reads the same classifier as `claude-web-chat ls`.
- **The tunnel picker lists Active and Inactive projects with live Claude presence, and can start a stopped one.** Every project whose surface has booted on this machine is now remembered in `~/.web-chat/projects.json` (upserted on each daemon boot, together with every other daemon running at that moment — a 0.7.x daemon never records itself, so a project still on one is picked up when any 0.8 daemon starts; nothing earlier is known, so a stopped project last used on 0.7.x appears after its next `open`. A project whose directory is gone, or no longer has `.web-chat/`, drops out on the next read, and `$HOME` — whose `.web-chat/` is the user tier — is never recorded). The picker shows two sections: **Active** (a running surface — click to open) and **Inactive** (stopped). It reads the same classifier as `claude-web-chat ls` and the Sessions panel (the registry's `sessions()` + `enrichSessions()`): each surface shows its viewers, active node and a **mid-turn** / **wake turn** badge, and each project whether Claude Code is attached (`×N`, channel on/off, last tool call). Clicking a stopped project known on this machine asks *Start <project> on <host>?*; on confirm the portal starts its daemon — the same detached start `claude-web-chat open` uses — waits for it to answer and takes you there. A project with Claude attached whose surface has never booted on this machine is listed (*surface never started here*) but can only be started on the host. Starting is narrow: the start is `POST /api/sessions/<id>/start` on the picker's own hostname, it names the project by its id only (never a path), only a project on the known list can be started, a hidden project (`no-remote`, `expose.exclude`) answers exactly like an unknown id, it needs the picker's own Origin, one start per project per 10 seconds, and each start is a line in the remote access log. Hidden projects stay off the picker; ports and pids stay off the page. The picker wears **Georgetown Blue** — generated from the pack's own tokens, light or dark with the device, Caslon headings served same-origin under the same strict CSP. Its `/api/sessions` rows are `{id, title, url, surface, claude, known}` (plus `last_seen_at` for a stopped one), and the response carries `host`. The portal's protocol is now 8, so `tunnel up` restarts an older portal.
- **A push says where it came from.** Every push — Push → Claude, a Retry, an immediate signal, a parked delivery and its drain — records `origin` (`remote` when it came through the tunnel portal, else `local`) and `device` (`mobile` while the browser is in its phone view — or, failing that, when its User-Agent says Mobile — else `desktop`). Claude sees both on the `<channel>` tag as `push_origin` / `device` and as a `Pushed from: origin=… device=…` line in the summary (so a parked delivery carries them too), and the rules file tells it what to do: on `origin=remote`, answer on the surface, don't ask for terminal commands and keep the chat short; on `device=mobile`, prefer compact panes. They also ride the `wake` event and the flushed queue-remove event in the event log, `GET /api/queue/pending` and the push response. A label only — nothing is allowed or refused on it. The channel meta vocabulary gains `push_origin` and `device` (the existing `origin` still means the event source). Refresh the rules file with `claude-web-chat install`.
- **`claude-web-chat ls --all` and the Sessions panel's Inactive group.** `sessions()` (the one machine classifier) now also returns the known projects with no surface and no Claude session, as `known:true` rows with `surface:null, claude:null`; every row carries `known`. `ls` prints them only with `--all`; the Sessions panel puts them in a collapsed **Inactive** group (it stays open across refreshes once you open it), each with its `claude-web-chat open` command.
- **`GET /api/health` reports `active_label`, `last_commit_at` and `lock_stale`**, so a cross-project listing can say where each surface is, and not call an expired lock a turn in progress, without pulling the whole graph.
- **Three theme packs ship as builtins: Earthy, Paper and Georgetown Blue.** `list_themes` and ⋯ → Settings list them; `apply_theme` applies them. **Earthy** is today's look, both modes, value for value but for three light-mode inks darkened for contrast (see *Changed*) — `public/app.css`'s two token blocks verbatim — and stays the default for every existing project, so no project changes theme on upgrade (a new project starts in Georgetown Blue; see *Changed*). **Paper** is flat cream with Earthy's olive accent and every depth effect switched off. **Georgetown Blue** (`georgetown-blue`) is navy and Pantone 293 on a cross-hatched putty vellum, with Libre Caslon headings and prose and a 2px blue rule under a white topbar (the `--wc-topbar-rule-width` token, so no builtin pack carries raw CSS). Paper and Georgetown Blue have dark modes too: Paper's is warm charcoal, still flat; Georgetown Blue's is navy surfaces with a lightened 293 accent, 1205 gold bookmarks on burgundy and a faint cross-hatch, Caslon kept — so ◑ works under every pack. Applying a builtin stores a reference to it, so later refinements to a pack reach the projects that applied it. `web-chat`, the old name for the stock look, still applies — as `earthy` — but is no longer listed, and so does `georgetown` — as `georgetown-blue`. ⋯ → Settings and the ◑ tooltip name each pack by its display name, and `list_themes` rows for the builtins carry it as `title`. A theme saved before this under a builtin's name is shadowed, by one rule everywhere — the builtin wins: `list_themes` shows the builtin's row with `shadows: ['local']` (or `'system'`) and a hint to re-save the tokens under another name, and the saved file stays on disk, unapplied and not renamed.
- **Light/dark is now a mode inside a theme.** A theme may carry `modes: {light: {tokens, css}, dark: {tokens, css}}` over its mode-free `tokens`/`css`, through `set_theme`, `save_theme` and the theme file alike. ◑, `T` and the palette flip the mode within the current global theme, re-flattening node and pane themes along with it. When that theme declares one mode only, ◑ is greyed out and its tooltip says so, and the palette entry says so too. Your `wc-mode` preference is kept, so switching back to a two-mode pack restores it. A theme with no `modes` (every theme saved before this) behaves exactly as before. `get_theme` takes `mode` (light by default) and reports `mode`/`modes` when the global theme has modes. `list_themes` names each theme's modes without dumping the per-mode maps. Exports bake the light mode unless asked; the chrome's previews follow the viewer's mode (see *Changed*).
- **Libre Caslon Text is bundled, and exports carry their fonts.** Georgetown Blue's headings and prose now render in Libre Caslon Text (Regular, Bold, Italic; SIL OFL, from the Google Fonts builds) served same-origin from `/fonts/` beside Geist and Geist Mono, each family with its licence file. `public/fonts/fonts.css` is now the one place `@font-face` is declared — `app.css` no longer carries its own — and an export inlines, as `data:` URIs, exactly the bundled families its resolved theme names, so a themed export keeps its type offline instead of falling back to whatever the reader has installed. An unthemed export is unchanged (no fonts, ~0 bytes added); a Georgetown Blue export grows by about 205KB, an Earthy or Paper one (applied as a theme) by about 185KB. The release tarball grows by 88KB (the six Caslon woff2 files and their licence).
- **Every builtin pack is held to WCAG AA contrast in every mode.** `test/theme-contrast.test.js` measures the ink/fill pairs the chrome paints (body and muted text on the stage and panels, accent labels, button labels on accent, green and gold fills, bookmarks, keycaps, hovered and active rows) and requires 4.5:1 for running text and 3:1 for UI and large text. The accent ink (`--wc-accent-text`) is held to the 3:1 line: it colours accent labels and also the links in a page's markdown, so a link in body-size prose can fall short of AA's 4.5:1 (Earthy light's is 3.04:1 on the stage). Georgetown Blue's light count badge on the burgundy gold fill is now white (navy on burgundy read at 1.8:1). Earthy light's four 0.7.6 shortfalls are fixed (see *Changed*).
- **One canonical design-token table** (`lib/server/theme-packs.js`, documented in the new `docs/themes.md` — `claude-web-chat docs themes`). It merges the design's drifting token sets into 63 tokens. New are `--wc-display` (headings) and `--wc-reading` (prose), plus `--wc-gold-bg`, `--wc-edge`, `--wc-scrim`, `--wc-panel-92` and `--wc-border-soft`, now defined in `app.css` for both Earthy modes too, and `--wc-topbar-rule-width` (the topbar's bottom rule: 1px, 2px in Georgetown Blue). The design's single `--wc-r` maps onto the existing `--wc-radius`/`-sm`/`-lg`. Every pack defines every token in every mode it declares, and a test holds the rules file, `set_theme`'s description and the docs to the table.
- **Brand image slots: a logotype in the topbar, a lockup and seal on exports.** ⋯ → Settings → Brand has three drop targets (drop an SVG or PNG, or click to choose; Remove clears one). The **logotype** sits left of the web-chat wordmark in the topbar; the **lockup** heads an exported page and the **seal** sits in its footer, both inlined as `data:` URIs so the file stays self-contained. Images are per project, under `.web-chat/brand/`, at most 256 KB each, and their type is read from the bytes. An SVG with script, event handlers, `javascript:` urls, `<foreignObject>` or entity declarations is refused. Every image is shown only through `<img>`, never as inline markup, and `/brand/<slot>` is served with `nosniff` and a no-script, sandboxed CSP. An unset slot draws nothing, so nothing changes for a project that sets none. HTTP: `GET /api/brand`, `PUT`/`DELETE /api/brand/:slot`, `GET /brand/:slot`; see `docs/themes.md`.
- **Pages: markdown between and around panes — `write_markdown`, the 24th MCP tool.** The surface is now one ordered page sequence of panes and markdown items (no stored sections: consecutive panes form a grid run, prose sits between runs, and `#`/`##` headings build the Contents nav). `write_markdown({text, id?, after?})` puts a chunk of prose on the page and replaces it by id like `render`; `render` and `use_component` gain `after` (an item id or `"start"`) to position a pane, with an unknown anchor still writing (appended) and returning a `warning`. Markdown travels with the surface exactly like a pane — committed into nodes, restored on navigation, drafted on shutdown, auto-preserved when Set active moves off an unsaved surface, cleared by Wipe and a page-wide `clear` (pinned panes still stay, with the markdown directly above them — below) — and a markdown edit or a reorder now counts as a surface change for the no-change check. `list_mounts` returns the page `order` and each markdown item's headings; `diff_nodes` reports `markdown` and page `order` changes; the glance preview and page exports render the prose in place. Nodes written before this need no migration: a node without markdown reads its page order off its mounts, as it always did. `start` is the page-top anchor and never an id: `render`, `use_component` and `write_markdown` refuse it with `{ok:false, reserved:true, hint}`.
- **The markdown directly above a pinned pane survives a wipe with it.** Wipe and a page-wide `clear` keep each pinned pane's heading and caption: the contiguous markdown items directly above it, back to the previous pane or the top of the page (`page.markdownAbove`, read before anything is removed). All other markdown is cleared, and the survivors keep their page order. A pinned pane first on the page keeps no prose; prose below the last pinned pane goes; `clear {force:true}` keeps no pin, so it keeps no prose either.
- **One markdown renderer, host and browser.** `lib/core/markdown` renders the subset (paragraphs, headings, strong/em, code and fenced code, flat lists, links) with every character escaped and links gated to http/https/mailto/relative, and exposes `headings(text)` with the same slugs the rendered elements carry. The chrome gets the identical implementation as an ES module at `/app/markdown.js`, built from the renderer's own source rather than copied; a conventions tripwire fails the build if a second markdown parser appears, and another holds every write to the page order and markdown items inside `lib/server/domain/page`.
- **Pane placement, Claude's layout, and per-run flags.** `render` and `use_component` take `place: {col, span, rows}` — a pane's start column (1–12), width (2–12 columns, shrunk to fit) and height (2–24 rows of 40px) on the page's 12-column grid; out-of-range values are clamped and the applied placement is returned as `place`, and `list_mounts` now reports every pane's current `place` (an older pane sized in pixels answers in rows, without being rewritten). A placement is recorded as that pane's "Claude's layout" baseline, and the page order Claude proposed is kept beside the live one, so after the user drags and resizes, `POST /api/page/reset-layout {run_anchor}` puts one grid run (the panes after a markdown id, or `start`) back: baseline sizes, un-minimized, Claude's order — locked panes keep their slot and size. `POST /api/page/move {id, after}` is the user's reorder, which never moves the baseline. Each run also carries a narrow-screen `stacks` flag (`POST /api/page/run {anchor, stacks}`; default stacks). The baseline order and run flags travel with nodes and drafts only when they are off their defaults, so an un-rearranged node keeps its exact shape; a run-flag change is a surface change, `diff_nodes` reports `runs`, and `hello`/`reset` carry `runs`.
- **Pane history.** `GET /api/mounts/:id/history` lists the distinct versions of one pane along the active node's ancestry (or `?from=<node id>`'s), newest first — each with the node that introduced it, its label, author, owner and trigger summary, and a content hash. A version is the pane's content (html, params, component): a resize or the user's typing is not a new version. The entry matching the live pane is marked `current`, and live content no node has yet leads as a `live` row. `GET /preview/pane/<node>/<mount>` renders one version read-only, in the same CSP-fenced document as the node preview. `POST /api/mounts/:id/restore {node_id, with_form?}` ("make current") copies that version's content and layout back into the live slot as a user action: it stays Claude's pane, shows in the event log as `source:'history'`, keeps the live pane's pin, lock and minimized flags and its typed values (the version's with `with_form:true`), and folds into the next commit. It is refused on a locked pane and on a pane — or a version — a driver owns.
- **The page, drawn: markdown between grid runs, a title, and a Contents nav.** The live surface now renders the page sequence: each markdown item through the one renderer (`/app/markdown.js` — escaped, links gated) at reading width, and each run of consecutive panes as its own 12-column grid (40px rows, 14px gap) with every pane placed by its `col` / `span` / `rows`; a pane without a column flows, and one sized in pixels before rows existed keeps its height. The page's first `#` heading is its title — in the topbar's title slot and as the page H1, with a meta line (node · panes · updated time) and a **PREVIEW · READ-ONLY** badge while viewing an older node. From 1100px a **Contents** column lists every `#`/`##` heading, numbered (`1`, `1.1`, `2`; a `##` with no `#` above it is a top-level row, so a `##`-only page numbers 1, 2, …), with the blocks under each; a row smooth-scrolls to its heading, and the column is not drawn on a page without headings. ⌘K gains **section** rows (choosing one scrolls to it), and a block row names the section it sits under (`§1.1 · figure`). The page ends in a dashed "Claude's next turn appends…" line. A markdown edit, a re-render or a reorder touches no other pane: panes are ordered inside a run with CSS `order`, so nothing is re-parented (and no `<iframe>` reloads) unless a pane changes run.
- **Rearranging a run, and putting it back.** Drag a block by its header to move it within its run: its start column follows the pointer, snapped to the grid, hovering another block takes that block's slot, and on drop the run settles into reading order — sent to the daemon as the fewest user moves (`POST /api/page/move`) plus the new column (`pane:state`). The edges and corner resize in whole columns and 40px rows (2–24), persisted as `colSpan` / `rows`. A locked block does neither. A run that is off Claude's layout — a pane resized, moved or minimized away from where Claude placed it, or the run out of Claude's order — shows **↺ Claude's layout** (`POST /api/page/reset-layout`); a run with two or more blocks (or already fixed) shows a **stacks on narrow / fixed grid** chip (`POST /api/page/run`). Both are absent on a read-only preview or phone. The full-surface frames and every frame that moves Claude's order now carry `claude_order` (the baseline ↺ compares against). Minimized blocks are chips under their own run.
- **One page stylesheet: `public/page.css`.** The run grid, pane placement, the narrow-screen rules and the markdown prose styles live in one file the chrome links and the node preview (`/preview/node`, the glance, pane history, every replay frame) and the page export inline (`lib/server/runtime/page-css-src.js`). The preview now lays a node out in the same runs as the live page, with the same placement, so a node looks the same in the graph as it did live; the two private copies of the `.md-block` CSS are gone. `/page.css` is on the remote-access allowlist.
- **A block's history, in the browser.** ◷ on a block's header (behind ⋯ on a block narrower than half the grid) opens a panel listing the versions of that block along the active node's ancestry — label, time, a non-Claude author, the prompt that introduced it, **CURRENT** on the one showing — from `GET /api/mounts/:id/history`. Hovering a version draws it read-only beside the list (`/preview/pane/:node/:mount`, in the viewer's light/dark — `/preview/pane` and `/preview/node` now take `?mode=light|dark`, since the daemon has no mode of its own); a click keeps it. It is view-only until **Make current** (`POST /api/mounts/:id/restore`), which is disabled, with the reason, on the version already showing, a locked block, and a block or version written by anyone but Claude; a refusal from the daemon is shown as its hint. Outside click, Escape (also after a click into the version preview, whose frame forwards the key) and a second ◷ close it and unload the preview.
- **A pane-spawned block names its parent.** A block another block put up (`api.spawn`) carries **↳ parent** on its header — click it to show the parent — and **↳ parent · closed** once the parent has gone (children stay, as before, until you close them). The `render` frame now carries the pane's `owner`, as the hello/reset snapshot always did, so a single render keeps the chip right; a pane whose owner changes re-mounts. A block spawned while you were previewing keeps its chip on ↩ active.
- **The phone graph log shows which sections each turn changed.** Each card lists the `#`/`##` sections its turn touched with what it added, changed and removed there (**# Results +2 ~1 −1**), computed by the daemon from each node's page against its parent — new `GET /api/graph/changes` (`lib/server/domain/lineage` `sectionChanges`; panes compare by content, never layout or typing). Pages without headings show none. The route is on the remote-access allowlist.
- **Panes can spawn panes.** A pane script now gets `api` beside `store` and `root`: `api.spawn({id?, component?, params?, html?, after?, place?})` puts up a child pane and `api.close(id)` takes one down, both resolving to the daemon's envelope (`POST /api/pane/spawn` / `POST /api/pane/close`). A child is owned by its parent (`owner: "pane:<parent>"`) and lands beneath it by default: a pane may replace and close only its own children, or close itself; Claude and drivers need `force:true` to re-render or clear one, like a driver's pane; a user-locked child refuses both. Caps bound a runaway script — 20 live children per parent, 60 pane-spawned panes in all, 3 generations, 30 spawn/close calls per parent per 10 s, 256 KB of html and 16 KB of params — and a spawned pane cannot declare wake signals (`params.signals` is stripped with a warning). Through the tunnel portal a spawn may name a saved component but not carry raw `html` (403 `{ok:false, remote:true, hint}`). In an export or a node preview the same `api` answers `{ok:false}` and writes nothing.
- **`GET /api/replay/path` — which nodes a replay plays, and what each one says.** The groundwork for replay: `resolveReplayPath` (`lib/server/domain/replay-path.js`) walks one lineage from `from` down to `to` (defaults: the active node, and the nearest bookmark at or above it, else the tree's root) the way the graph viewer draws it. A no-change node the viewer hides is skipped, and its prompt plus anything already folded onto it rides in the next kept step's `folded[]`, so nothing is lost. Each step is a caption — `{label, author, kind, prompt, reply, summary, folded[], created_at, dt_from_prev}` — capped at 200 steps (`truncated` says when). `from` must be an ancestor of `to`; `live` is refused.
- **A node records Claude's reply, not only the prompt.** The `Stop` hook now sends a short summary of Claude's final message with `turn-end` — from the hook payload's `last_assistant_message`, or the tail of the session transcript on Claude Code versions without it — and the daemon stores it as `trigger.reply` (whitespace collapsed, at most 280 characters; `lib/core/reply.js` is its one definition, applied by the hook and re-applied by the daemon). A turn that changed nothing keeps its reply in its folded entry, next to its prompt. It shows as one line under the trigger in the graph inspector (full text on hover), as the tooltip on a folded turn's ghost row — on the canvas sleeve and the phone log — and in replay captions (`reply` in `GET /api/replay/path`). Additive: a node with no reply has no `reply` key, and nothing is migrated. Stored only under `.web-chat/`; page exports do not include it.
- **Replay: watch a lineage play forward, node by node.** A player overlay (`public/app/replay.js`) plays the surface from the nearest bookmark down to the node you are viewing — or any stretch of that lineage you pick — with play/pause (`Space`), step (`←`/`→`), a scrubber with a tick per node, speed 0.5–4×, cut or fade, and captions showing each node's label, time and Claude's reply — plus the turn's prompt when you tick **Include my prompts**. Open it from the graph inspector (**▶ Replay**, `R`), ⌘K (**Replay to …**), ⋯ → **Replay…** or `R` on the surface (to the node on screen); **Open this node** previews the step on screen. It never touches the live surface: it frames `GET /replay`, one self-contained document (`lib/server/replay/document.js`) served under the node previews' CSP, whose steps are the node preview page built on demand as windowed `<iframe srcdoc>` frames. `GET /api/replay/html` downloads the same document as `replay-<from>_<to>.html`, playable offline; a replay's payload carries only the caption text it shows, so without `include_prompts=1` it ships no prompts. `window.__wcReplay.seek(ms)` is deterministic — it is what the GIF/video renderer below seeks through.
- **Replays as GIFs — drawn by the browser you already have.** `export` gains `format: 'replay' | 'gif'` (with `from`, `to`, `hold_ms`, `transition`, `captions`, `width`; `html` stays the default and is unchanged), `claude-web-chat export` gains `--replay` / `--gif` with `--from`, `--hold`, `--fade`, `--width`, `--captions`, and the replay player gains **↧ GIF**. All three go through `POST /api/replay/render`, which writes `replay-<from>_<to>-<stamp>.{gif,html}` under `.web-chat/exports/`. A GIF is drawn by a headless system Chrome, Chromium, Edge or Brave (`WEB_CHAT_CHROME` overrides) driven over `--remote-debugging-pipe` on a throwaway profile — no debugging port, no Puppeteer — then decoded by a new built-in PNG decoder (`lib/core/png.js`) and encoded by a new built-in GIF encoder (`lib/core/gif.js`: per-frame median-cut palette, LZW, frame differencing). No browser is an honest `chrome-not-found` with a hint; `GET /api/replay/capabilities` and `claude-web-chat doctor` say what was found. Prompts stay out of anything written to a file unless asked for (below). Renders are single-flight, JSON-only, and capped in frames, size and time; `GET /api/replay/file/:name` hands a rendered file back, fenced to `exports/`. Chrome runs as the leader of its own process group and is torn down in bounded steps — `Browser.close`, SIGTERM to the whole group, then SIGKILL — with its profile always removed, so a wedged browser cannot outlive the render; stopping the daemon mid-render aborts it (`503` `aborted`). A browser that exits (`chrome-exited`) or a page that crashes in it (`page-crashed`, from `Inspector.targetCrashed`) fails the render at once — mid page load included — instead of holding the single flight until the five-minute timeout. A daemon killed outright leaves its Chrome profile and ffmpeg frame directory behind, so every daemon sweeps `.web-chat/tmp/` at boot and before each render, removing the `chrome-<pid>-*` / `frames-<pid>-*` directories whose pid is dead (`lib/replay/tmp.js`).
- **Replay captions: an explicit "Include my prompts" toggle, off by default.** Off, a caption is each node's label, time and Claude's reply summary, and the file holds NO prompt text anywhere — not the prompt, not its 100-character trigger summary, nothing in the embedded payload. On, the prompt is shown too. It is a checkbox in the replay player, remembered per browser, which also drives every file saved from the player (↧ replay.html / GIF / MP4 / WebM — one click, and the note that links the file says *includes your prompts*); the `export` MCP tool takes `include_prompts: true`, `claude-web-chat export` takes `--prompts` / `--no-prompts`, and `GET /replay`, `GET /api/replay/html` and `POST /api/replay/render` take `include_prompts`. Everything that writes a file defaults it off. `captions` is `on` (default) or `none`.
- **Replays as MP4 / WebM, and better GIFs, when ffmpeg is on the machine.** `export` `format: 'mp4' | 'webm'`, `claude-web-chat export --mp4` / `--webm` and the player's new **↧ MP4** / **↧ WebM** render the same replay as H.264 / VP9 video (`yuv420p`, constant `fps`, cut to the replay's exact length). A new encoder module (`lib/replay/encode.js`) writes each distinct captured frame once under `.web-chat/tmp/`, describes the holds in an `ffconcat` list, and runs the ffmpeg `lib/replay/find` locates (`WEB_CHAT_FFMPEG` overrides; 4.4+) with an argv it builds itself, inside the render's wall-clock budget. With ffmpeg present a GIF uses it too — one `palettegen` palette over the whole replay, `paletteuse` with `sierra2_4a` dithering limited to changed rectangles, exact holds — and falls back to the built-in encoder (reporting `fallback`) if ffmpeg fails; without ffmpeg a GIF is built in as before and MP4/WebM are an honest `422` `ffmpeg-not-found` with a hint, answered before any browser starts. `GET /api/replay/capabilities` now reports `mp4`/`webm` availability and `gif_encoder`, the player disables the formats this machine cannot make (with a title saying what to install), and `doctor` says what ffmpeg adds. `lib/core/png.js` gains `pngSize` (IHDR only), and `palettegen` gets a tripwire row so the ffmpeg command line keeps one home.
- **Replay scripts — Claude directs the replay.** `export` takes a `script`: `{from, to, title?, default_hold_ms?, include_prompts?, steps?: [{node | nodes:[…], hold_ms?, caption?, transition?}]}`. `from`/`to` pick the two moments; each step is one beat with its own hold, transition and caption, and `nodes` groups a run of consecutive nodes into one beat that shows the last of them with a caption listing the group. Nodes no step names are skipped; without `steps` it is the plain replay at `default_hold_ms`. A script is checked by one function, `normalizeReplayScript` (`lib/server/domain/replay-path.js`) — a node off the path, steps out of order or repeated, a group with a gap (a hidden no-change node may sit inside one), more than 200 steps or a malformed script is refused with `{error, code, step}` naming the step; holds clamp to 0.5–20 s and captions/titles are cut to length. The replay document, the player and the GIF/MP4/WebM renderer all play its answer — per-step holds and fades set the timeline and the frames — and a plain from/to replay is its no-steps case. `export({ script, open: true })` (and `POST /api/replay/open`, MCP/CLI only: refused to a browser or through the tunnel) opens the player on that script in every browser watching the surface — a remote viewer's phone included — via a `replay:open` frame, and writes nothing; `claude-web-chat export --script <file.json> [--gif|--mp4|--webm|--replay|--open]` does the same from a JSON file. Browsers load a script by id (`GET /replay?script=<id>`; held in memory, `lib/server/replay/scripts.js`). The player shows the script's title and captions and keeps its controls; there is no authoring UI. The rules file gains a short **Replays** section on when and how to write one.
- **Groundwork for remote access through a Cloudflare tunnel.** `lib/core/remote-policy.js` is the default-deny table of which daemon routes a remote, allowlisted viewer may reach: the surface the browser drives is allowed; pack writes, service trust, the turn/hook internals, shutdown, `format=file` exports, captures and the extension downloads are refused with a hint naming what to run on the host; wiping the graph needs an explicit opt-in. `test/remote-policy.test.js` fails the build on any daemon route the table does not classify. `lib/client` gains `pipe()`, a streaming pass-through that never discovers or spawns a daemon and always dials it as `127.0.0.1:<port>`; the registry's hub helpers generalise to `registerRole`/`readRoleEntry`/`deregisterRole` for any one-per-machine process; and `userPaths()` names the `~/.web-chat/tunnel/` files (config, connector token, logs).
- **The tunnel portal** (`lib/portal`, run by the hidden `claude-web-chat portal run`, which `tunnel up` starts). One loopback process on port 5171 (`WEB_CHAT_PORTAL_PORT`) that a Cloudflare tunnel reaches, serving a picker at your chosen hostname (`wc.example.com`) and each running project at its own origin (`wc-<id>.example.com` by default, `<id>.wc.example.com` optionally). Every request must carry a Cloudflare Access token that the portal verifies **itself** — RS256 only against Access's published keys, issuer, audience and expiry checked, and the signed-in email on a local allowlist no dashboard setting can widen; a key set that cannot be fetched fails closed. Behind that: the default-deny route policy, CSRF checks (an exact-origin match on every write and on the live socket), an allowlist of which request headers reach the daemon (so the capture token, the shutdown header and the MCP-sighting headers can never be forged from outside), no-store/no-framing/no-referrer response headers (the node, pane and replay previews may be framed by their own origin only, and are no-store too), a streamed proxy and a WebSocket relay that is cut when the sign-in token expires (and not before — a month-long Access session, past `setTimeout`'s ~24.8-day ceiling, is waited out in steps). Opening a stopped or hidden project's hostname gets a friendly page linking back to the picker; a stopped project is started only from the picker (above).
- **`claude-web-chat tunnel setup|up|down|status|logs` — reach your surfaces from anywhere.** `setup` asks for (or takes as flags) the picker hostname, flat or nested style, the Access team and AUD tag, the allowlisted email — one by default, with a loud warning that an allowlisted account can drive trusted service panes, i.e. act as you — and a NAMED tunnel (`token`, dashboard-managed, or `local`, from `cloudflared tunnel create`); it proves the team name by fetching its Access signing keys, writes `~/.web-chat/tunnel/tunnel.json` and the connector token 0600 (the token is read from a file or a paste, never a flag value), and prints the dashboard steps with your hostnames filled in. `up` refuses a missing or invalid config, an empty allowlist, a quick tunnel (which cannot sit behind Access), daemons moved off loopback by `WEB_CHAT_HOST`, a missing or pre-2024.1 cloudflared (printing `brew install cloudflared`, Cloudflare's Linux repository, or the WSL note — web-chat never installs it) and a missing token; then it starts the portal detached, which runs cloudflared as its own child — the token in `TUNNEL_TOKEN`, never argv; a local tunnel from a generated ingress that routes only your hostnames and makes cloudflared require Access too — restarting it with 1s→60s backoff and stopping it with the portal. `status` shows the portal, whether the connector is ready (cloudflared's loopback `/ready`), the last Access key refresh, the allowlist size and every exposed project's URL; `doctor` gains a tunnel section once setup has run. The tunnel config, Access key set and cloudflared handling moved into a shared `lib/tunnel/` so the portal, the CLI and doctor read them through one normaliser. The portal follows `tunnel.json` while it runs (below) and reports what it enforces (`config_fp` on its `/api/health`): `tunnel up` restarts a portal whose config differs from the file, and `tunnel status` warns while they disagree. `setup` over an unreadable `tunnel.json` moves it aside as `tunnel.json.corrupt-<time>` just before writing the new one and names what was not carried over. The portal records its connector in `~/.web-chat/tunnel/cloudflared.pid.json`, and a new portal stops one a killed portal left running, after checking with `ps` that it is still that cloudflared on the recorded metrics port; a connector with no record is never signalled, and `tunnel up` refuses while it holds the metrics port. Walkthrough, security model and residual risk: `claude-web-chat docs remote-access`.
- **Remote-access hardening.** A project can keep itself off the tunnel with a `.web-chat/no-remote` marker, and `tunnel.json` can hide projects with `expose.exclude` (instance ids, or absolute directories that hide everything under them) — a hidden project is left off the picker and its hostname answers exactly like a stopped one, and `tunnel status` lists hidden projects with the reason. Switching web-chat off (`claude-web-chat off`) does not hide a project: it stays on the picker, and startable from it — use `no-remote` for that. Every remote write and live-socket connection from a signed-in account — let through or refused — is one JSON line in `~/.web-chat/tunnel/remote-access.log` (who, which project, method, path, status; 0600, rotated at 1 MB; `tunnel logs --access`). A client that fails the sign-in check 20 times in a minute is answered 429 for the next minute before any check runs. `remote.allowDestructive` (the one opt-in that lets a remote viewer wipe a graph) is now shown by `tunnel status`. Hiding a project also cuts the viewers already on it: while any relay is open the portal re-checks every second and closes, with code 4403, each one into a project that is now hidden or stopped. Theme saves (`POST /api/themes`) are refused remotely — listing and applying still work — and the daemon itself refuses `location:'system'` and `set_default` on a request carrying the portal's label. `POST /api/markdown` and `GET /api/machine/sessions` are refused remotely with a host hint, which the Sessions panel shows. Remote reads do not give out the host's paths: services waiting for trust, the pack listings and a quarantined pack's review mask the project root as `<project>` and the home directory as `~`, and replay capabilities say only whether Chrome and ffmpeg are installed. The portal reports its own `PORTAL_PROTOCOL_VERSION` (separate from the hub's), and `tunnel up` restarts a portal left running by an older build instead of reporting it "already up" (and `update` restarts a running portal on the new build — below). Viewed remotely, the page says so where it matters: the portal adds `X-WC-Remote: 1`, the daemon's `/api/health` echoes `remote: true`, and the ＋ drawer's Manage tab points pack changes at the host (disabling Install / Discard / Remove) while a service waiting for approval tells you to run `claude-web-chat trust` on the machine running web-chat, not the device in your hand.
- **The portal follows `tunnel.json` and its connector token while it runs, and `update` restarts it.** The running portal watches `tunnel.json` (a directory watch, with a 2-second poll behind it) and applies a valid edit at once: the allowlist, the Access team and AUD, `expose.exclude`, `remote.allowDestructive` and `showRoots`. A removed account is refused on its next request, and its open live sockets are closed within a second (code 4403, the same sweep that cuts a project hidden by `no-remote`). A file that is missing, unreadable or invalid makes the portal **fail closed**: every request except its own loopback health check is answered 503, every live socket is cut (4503), and the log says why, until the file is valid again, when it resumes on its own. A change to `hostname`, `style` or the `tunnel` section needs a new cloudflared, so it is not applied live: the portal keeps routing the hostnames it started with (while applying the rest of the same edit), logs "restart needed", and `tunnel status` says to run `tunnel up`, which restarts it. The connector token (`~/.web-chat/tunnel/token`, token tunnels) is watched too but never applied live — it is cloudflared's, handed over at its launch — so a different one in the file (a re-run `tunnel setup`) or none is reported: `/api/health` gains `config` (`state`: `ok` / `restart-needed` / `invalid`, the `error`, the `restart` sections, `live`) and `token` (`state`: `ok` / `restart-needed`, and `fp`, a short hash of the token cloudflared runs on, never the token), `tunnel status` says **restart needed (connector token changed)**, and `tunnel up` compares that hash with the file's, the way it compares `config_fp` with `tunnel.json`, and restarts the portal and cloudflared on the new token instead of saying "already up". After `claude-web-chat update` or an `update --to`, a portal registered as running is restarted on the new build — through `tunnel up`'s own stop/start bounce, loaded from the build just activated so `portal run` starts on its code — and `update` prints one line saying so and that remote viewers will reconnect. A restart that fails (a `tunnel.json` or token `up` would refuse leaves the old portal running; anything later leaves it down) is reported with `claude-web-chat tunnel up`, and the update still succeeds. The exception is a target with no `tunnel` command at all (a rollback to 0.7.6): the portal is stopped with the running build's `tunnel down` BEFORE `current` moves — refusing the rollback if it will not stop — and `update` says remote access is off until a build that has the command is back, never naming a command the target lacks. Every restart's `tunnel down` — from `update`, from `tunnel up` replacing an older or stale-config portal, and on its own — waits (up to 10s) until the stopped portal and the connector it reported have both exited and the metrics port is free, so the new portal never meets the old connector; one of that portal's connectors still running after the wait is stopped (SIGTERM, then SIGKILL) once `ps` confirms it is still that cloudflared, and one that survives even that is a refusal naming its pid. A connector the stopped portal never reported is not waited on or signalled.
- **`tunnel setup` with one Cloudflare API token.** `claude-web-chat tunnel setup --api-token-file <file>` (or `--api-token <t>`, or a paste when asked — a first setup now offers this path by default) does the Cloudflare side itself: a remotely managed tunnel (`web-chat`, or `--name`) routed to the portal on `http://127.0.0.1:5171`, proxied CNAMEs for the picker and the session wildcard, Cloudflare's One-time PIN login method, a reusable Access allow policy for your email(s) and a self-hosted Access application covering the picker and the sessions (`wc.example.com` + `wc-*.example.com`) with a 30-day session (`--session`) — then it reads back the Zero Trust team name and the application's AUD tag and writes `tunnel.json` and the connector token as before. The default sign-in is the emailed PIN **plus Access independent MFA with biometrics** (Face ID / Touch ID / Windows Hello, or a security key; `--mfa-session`, default 720h): setup turns independent MFA on for the organization if it is off — writing the organization back whole, as `GET` returned it with only the MFA settings changed and limited to the fields the Update endpoint takes — without requiring it for the account's other apps, and requires it on this application only. If the organization refuses, setup asks for MFA on the web-chat application alone (`Sign-in: … — required on this application only`), and only when that is refused too falls back to the PIN alone with the long session, naming both reasons; a re-run on an existing setup turns MFA on in place, writing only the organization and the application; `--signin pin` asks for that outright, and `--signin google` prints the Google OAuth client values (JavaScript origin and redirect URI for your team) and creates the Google login method from the client id and secret. What you got is recorded as `signin` in `tunnel.json`. Every step converges — a re-run changes nothing — and every read happens before the first write, so a DNS record setup would replace, a same-named tunnel managed from a local config file, or an Access application of another type on the hostname stops the run with an explanation and nothing changed. `--dry-run` prints the plan and changes nothing; in the flat style the plan warns in one `⚠` line when the wildcard DNS record sits on the zone apex (`*.example.com` catches every subdomain you have not defined; the portal refuses those hostnames with 421, but they reach this machine) — a warning, never a stop. The token needs five permissions: Cloudflare Tunnel Edit, Access: Apps and Policies Edit, Access: Organizations, Identity Providers, and Groups Edit, DNS Edit, and Account › Account Settings › Read, which makes listing the account the plain path (without it setup finds the account through the zones the token can see, and `--account <id>` is used directly, proved by one account-scoped read). A refusal names the permission it lacks the way your dashboard names it, old and new names both (Cloudflare Tunnel is *Cloudflare One Connector: cloudflared* in newer dashboards, and the permissions reference spells *Edit* as *Write*); an `--account` the token cannot reach, or a token that sees neither an account nor a zone, says which and how to find the account id. A rate limit is waited out, and the API token is never stored. A pasted token is shown as it is pasted (the terminal prompt does not hide input), so on a shared or recorded screen prefer `--api-token-file`. The manual path (`--team`/`--aud`/`--kind`) is unchanged. `claude-web-chat docs remote-access` leads with this path — a four-step quick start, then the manual walkthrough — and its Troubleshooting section maps each message setup, sign-in or the tunnel can stop with (a rejected token, a missing permission, no zone, Zero Trust off, two accounts, a conflict, a rate limit, a half-finished run, MFA refused with 12062, no code, no biometric prompt, the portal's 403 and 401) to what to do.
- **Set up remote access from the browser: ⌘K → *Set up remote access…*** (also ⋯ → *Set up remote access…*, both offered only on a local page). ### Fixed

- **Reloading the page made an unchanged surface look changed, so Set active added an empty 'user' preserve node.** Every page open (a reload, a reconnect, a phone opening the page, the new auto-reload after an update) ended by publishing each untouched pane's rendered form values — `{}` for a pane with no fields — as if the user had typed them, and the surface then differed from its node: Set active auto-preserved a node holding nothing, and a chat-only turn committed a node instead of folding. The chrome now takes what a pane shows at mount as already known, and the daemon treats an empty form snapshot as no form values, so only real typing counts as a change.
- **Claude's page-wide `clear {}` was refused over a pinned pane it would have kept.** A pinned pane owned by a driver or by the pane that spawned it stays through a bulk clear, but still counted as a clobber and refused the whole clear — and every spawned child is foreign to Claude, so one pinned child blocked every page-wide clear. The refusal's hint then said to pass `force:true`, which also removes every pinned pane, the user's included. A pane (and the markdown directly above it) that the clear keeps no longer counts, and the hint and the `clear` tool now say what `force:true` does to pins.
- **`update`, `restart`, `start` and `open` typed outside a project booted a server rooted there.** Each fell back to the bare working directory, so `claude-web-chat update` in `~` or `~/Downloads` started a daemon rooted there — which made a `.web-chat/`, and in `~` ran the first-run migration into the user tier — and this build would then have remembered the directory as a known project the tunnel portal can start. Now `start` and `open` refuse a directory with no `.web-chat/` (naming `claude-web-chat init`), `restart` says there is nothing to restart, and `update` restarts nothing outside a project. `$HOME` is never a project root, even reached through a symlink, and never a known project: a `projects.json` entry for it, or for a directory without `.web-chat/`, is dropped on the next read.
- **After an update, an open page kept running the previous build.** Two causes, both fixed. The update restarts the daemon and the page's socket reconnects, but the modules already loaded in the tab were still the old ones: on reconnect the chrome now compares the daemon's version with the one the page loaded from and reloads itself once when they differ — typed form values are saved first and restored on the fresh page, and it is at most once per build per tab, so it cannot loop. And a release tarball pins every file's modified time (for byte-reproducible builds), so the daemon's static-file validators — a fixed `Last-Modified` and an ETag made of size + mtime — came out identical across builds, and a browser holding a cached `topbar.js` was answered `304 Not Modified` by the new version, even after a reload: the chrome's files now carry an ETag that names the build, send no `Last-Modified`, and are served `Cache-Control: no-cache`, so every browser picks up a new build on its next load, with no cache clearing.
- **The graph's trunk no longer strikes through node labels.** An edge was drawn glyph to glyph, so the vertical line ran through the label under each node (`n1.0`, `n1.3`), the ⚑ bookmark caption over it and a ×N stack's range. It now starts under the label of the glyph above and stops over the caption of the node below, and a fork's elbow leaves its node sideways from the lower right instead of dropping through the label and across the glyph beneath. When the branch lands several columns away, the elbow is routed around what lies between: it crosses each column in a gap between that column's rows, steps between heights only in the empty space between columns, and never runs along another fork's elbow — drawn at one height it went through the glyphs on its row and lay over the neighbouring fork's edge, so the picture showed the wrong parent. A bookmarked branch head now gets the same caption room as a bookmarked node on a trunk. A gap rather than a halo in the background colour, because the Earthy and Georgetown Blue grounds are gradients no flat colour matches; the same geometry under every pack and mode.
- **⌘K on the graph screen no longer opens an invisible palette under it.** The palette painted below the graph overlay (and the glance and the replay player) but took focus, so the graph's arrow and letter keys stopped working and ↵ ran a row nobody could see. While one of those is open ⌘K now does nothing — the graph has its own jump search.
- **Queue ⟲ Revert could delete a pane Claude rendered.** One Apply click in a pane with a declared signal puts two rows on the rail — an `activity` row from the shell's click listener and a `signal` row from the pane's `store.set` — and reverting the `signal` row routed to the pane-removal path, deleting the pane and everything typed into it. A `signal` Revert now undoes the interaction like an `activity` one: the pane stays, its form values go back to the pre-run baseline, and the signal key goes back to its pre-write value (or is removed if it was absent) through a server-sourced `queue-revert` store write that can never enqueue or wake. Only a `capture` item's Revert removes a pane now; a `comment` whose pin is already gone reverts nothing instead of falling back to the pane. The ⟲ tooltip says what each kind actually does.
- **A signal item named the wrong pane.** When two panes declared the same signal key, the item's `origin_mount` was the last pane to declare it, not the pane that wrote it — so a Revert acted on a pane the user never touched. It is now the writing pane (the per-pane store facade's stamp), with the declarer only as a fallback for an unattributed write.
- **Revert restored the typed values it was meant to undo.** The activity baseline was stamped when the item was enqueued, after the debounced form snapshot had already carried the new typing. The baseline is now the pane's form values from before the first change since the last Push, and dismissing an item (× without Revert) ends that run, so the next Revert goes back to the values you kept rather than past them.
- **The surface could not connect when served over https.** The chrome opened `ws://` unconditionally, which a browser refuses from a secure page as mixed content, so a surface served over https (a local TLS-terminating proxy, say) sat on "reconnecting…" forever. The socket now follows the page's scheme — `wss:` under `https:`. The daemon's Host and Origin gates are unchanged: a non-local hostname is still refused.
- **`?` did nothing in the graph viewer, though its status line advertises "? keys".** The keyboard layer returned early while the overlay was open, and the shortcut legend painted underneath the overlay anyway. `?` now opens the legend over the graph (Escape closes the legend first and leaves the graph open), and the legend lists the graph's own keys: arrows to select, Space to glance, ↵ to open, A to set active, E to export, B to bookmark.
- **The graph canvas could not be panned on a touch screen.** Pan and graph-heading drags listened to mouse events only, which a finger never produces. They now run on pointer events with `touch-action: none` on the canvas; the first finger owns a drag and a second one is ignored. Wheel zoom is unchanged.
- **The docs pointed at a topbar ⬇ export button that does not exist.** The control is **⋯ → ↧ Export node** (also in the ⌘K palette), plus the graph inspector's **↧** and `E` for the selected node. The Claude rules file, `docs/export-pages.md` and `docs/guide.md` now say so — the rules file is a managed file, so `claude-web-chat update` refreshes a project's copy.

### Security

- **A browser socket can no longer forge a bus event.** The daemon built the live socket's `event` frame by spreading its payload, so a frame sent on a browser's socket — the surface's own, or a remote viewer's through the tunnel portal's WS relay — could carry `kind:'wake'` and wake Claude as if the user had pushed, with a chosen batch and provenance, or a huge `seq` that made the channel bridge drop every later real wake and `get_events` report a gap. An `event` frame is now rebuilt from an allowlist: only a dom `click`/`change`/`submit` with its known fields becomes an event, `kind` and `source` are written last, and anything else is dropped. This closes the frame, not a pane's reach: pane code runs with the chrome's own authority and can still Push as the user can, read every store key and call any local route — panes are trusted, agent-authored code (`docs/driving-the-surface.md` says so).
- **Node previews run sandboxed.** The graph inspector's thumbnail, the glance and a block's version preview (◷) re-run old pane code; framed same-origin, that code could reach the chrome through `parent`/`top`, where the preview CSP's `connect-src 'none'` does not apply. They are now framed `sandbox="allow-scripts"` (an opaque origin), and Escape pressed inside one comes back by `postMessage`. The replay player is still same-origin — the chrome drives it through its window — and is recorded as an accepted risk.
- **The `website` pane frames and opens http(s) pages only.** A `javascript:`, `data:`, `blob:` or `file:` URL — from params, the address bar, or a remote viewer's spawn — could run in the surface's own origin once "try embed anyway" pointed the pane's allow-same-origin frame at it. The pane now refuses such a URL before it asks or frames anything, with no way round, and `/api/embed-check` answers it `code:'unsupported-scheme'` without making a request.

### Internal

- **The one-token setup run and the tunnel lifecycle moved into `lib/tunnel/`.** `lib/tunnel/api-setup.js` holds what `tunnel setup --api-token` does around `cf-setup`'s gather/plan/apply (read what `tunnel.json` holds, build what setup wants, print the plan, stop on a conflict, apply, prove the Access keys, write `tunnel.json` and the connector token), and `lib/tunnel/control.js` holds `up`/`down`/`restartPortal`/`collectStatus`, so the CLI and the browser setup page run the same code; `lib/cli/commands/tunnel.js` keeps the terminal's questions and printing, and still exports `restartPortal` for `update`. No behaviour change in the CLI.
- **`compareVersions` orders prerelease tails by semver precedence.** It ordered a prerelease below its release but compared two prereleases as equal, so every dev build of one number tied; now two dev builds order by their stamp, and numeric identifiers compare numerically (`0.7.6 < 0.8.0-dev.<stamp> < 0.8.0`). The update banner offers the real 0.8.0 to a dev build and stays quiet about 0.7.6. `isDevVersion` in `lib/core/versions` is the one spelling of "is this a `--dev` build". Version pruning now always keeps the newest release (no prerelease tail) as well as the newest three, so repeated dev installs cannot prune the rollback target.
- **The logo image check and the bundled-font list moved into `lib/core`** (`core/brand-image`, `core/fonts`), and the builtin theme names joined `core/names`, because `lib/packs` now needs all three and may not import `lib/server`. `lib/server/brand.js` and `lib/server/fonts.js` keep their exports; the brand fill is one code path for every theme that has logos (`fillSource`). The daemon now also refuses a remote (portal-proxied) pack write itself, behind the portal's existing refusal.
- **The one-token tunnel setup is tested against every failure the fake Cloudflare API can play.** `test-support/fake-cloudflare.js` can now also refuse independent MFA on the organization or the application alone (`sim.mfaRefused: 'org'|'app'`) and fail any request a set number of times (`sim.fail`, a run that dies half way); a missing zone is a fake with other `zones`. `test/tunnel-cf-setup.test.js` covers each of the four token permissions being named when missing, a hostname in no zone, Zero Trust never turned on, a rate limit that does not lift, `--dry-run` over a conflict and over a finished setup, MFA refused on the application only, a re-run after an MFA refusal changing nothing and a later run upgrading the same application (same AUD) to biometrics, a half-finished run completed without duplicates, a two-account token needing `--account`, and the pasted and flag-value tokens never reaching disk. Test-only; no product change.
- **`lib/util/outbound.js`, the outbound request engine.** The Cloudflare API client was the fourth public-internet requester, the point at which the `require('https')` ratchet said to extract one: `request` / `fetchJson` are https only (plain http to a loopback host alone, for a test's fake) and bounded in time and size, and Access's key-set fetch moved onto it. The embed probe and the release download keep their own fenced requests. `test-support/fake-cloudflare.js` is an in-process fake of the Cloudflare API endpoints setup uses, reached through `WEB_CHAT_CF_API`.
- **The real-Chrome and real-ffmpeg tests are opt-in.** `test/replay-capture-e2e.test.js`, the real-ffmpeg case in `test/replay-encode.test.js` and the ffmpeg read-back in `test/gif.test.js` used to run whenever the machine happened to have the program, so the suite changed with what was installed. They now skip unless `WEB_CHAT_E2E_CHROME=1` / `WEB_CHAT_E2E_FFMPEG=1` is set, and each skip names the variable; the fake-binary tests run everywhere as before, and CI sets neither. One gate decides (`e2eGate` in `test-support/helpers.js`), and the harness ratchet holds a bare `findChrome()`/`findFfmpeg()` in a test at zero. Test-only; no product change.
- **The "crashing service is not respawned" test failed now and then on a loaded machine.** Its first wait was already satisfied before any child had spawned (the approval's reconcile was still inside its 200ms debounce), so the test really asked a freshly forked child to boot, crash and be reaped inside a fixed 400ms sleep — about 100ms of headroom that parallel suites sometimes ate. The supervisor was never at fault, and the race was as old as the test: the pre-upgrade 0.7.6 tree fails the same way as soon as the crash takes 150ms longer. The test now waits for the crash to be recorded against its version and checks for a respawn right after a synchronous reconcile, with no sleep. Test-only; no product change.

## [0.7.6] - 2026-09-18

### Upgrading from 0.7.5

`claude-web-chat update` is all it takes, and this time there is nothing else to
say: no state migration runs, no service re-asks for approval, no managed file
changes, and nothing you have installed behaves differently. The three changes
below are internal to what the daemon hands Claude, plus one decoding fix. The
only visible difference is in Claude's own tool results, described under
*Changed*.

### Fixed

- **A response body split across socket reads could lose characters, and nothing ever noticed.** `lib/client`'s `request()` accumulated the body with `chunks += c` and never called `setEncoding`, so every Buffer was decoded on its own and a multi-byte character straddling a socket read was replaced by U+FFFD on both sides of the seam. The failure is silent by construction: the replacement characters land inside a JSON string literal, so `JSON.parse` succeeds and every caller behind `api()` — every MCP tool, every hook, every CLI command, every driver method — believed it had the text. Corrupted store values and captured text then rode into committed graph nodes and exports with nothing to trace them back to. Multi-chunk bodies are ordinary rather than exotic here: the body limit is 200mb and `get_store`, `get_events` and `export` routinely exceed one socket read. `subscribeSSE` had always decoded as a stream; `request()` never did. **You may notice** nothing at all — this corrupts quietly or not at all — but any non-ASCII that round-tripped through a large response was at risk.

### Changed

- **`set_store` no longer hands Claude the entire store back.** `POST /api/store` echoes the whole store in its response, and `set_store` returned that response verbatim — so writing one key reported every key, measured at 288KB against a real project store and 14% of every byte this MCP surface had ever spent. Nothing reads the echo: `lib/driver.js`'s `setStore` returns the call result unread, and no browser code fetches `/api/store` at all (the surface takes `store:patch` over the WS). The tool now returns `{ok, keys_written, store_keys, store_bytes}` — what it wrote, plus enough to notice the store growing. `get_store` is unchanged and remains the read path. The **route** still echoes: its response is a wire shape an out-of-tree driver could depend on, and only the MCP tool's return value has exactly one reader.
- **`get_active` and `get_graph` cap the turn lock's message at 200 characters.** `graph.lock.message` is the user's own prompt, stored unsliced and returned whole, so the largest MCP result ever recorded against this daemon was a `get_active` of 49,556 characters — 49,400 of them that one field, handed back to the model that had just read it. Its two neighbours were already capped (a folded message at 1000, a trigger summary at 100); this one was missed. When the message is cut, `lock.message_bytes` carries the true length beside it — the shape a capped capture read already uses — and when it is not, no `message_bytes` appears. Shaping happens at the MCP boundary (`lib/mcp/shape.js`), not at `/api/graph`, because the browser and out-of-tree drivers read that route too.

## [0.7.5] - 2026-08-31

### Upgrading from 0.7.0

`claude-web-chat update` is all it takes. No state migration runs, and — for the first
time — the managed files arrive on the same hop: the 0.7.0 updater loads this build's
registration engine, so the corrected rules file and skills sync without a separate
`install` (`status` confirms). Four one-time notices:

1. **A service-backed pane whose params carried `form_reset`, `routing` or `signals`
   asks for approval once more.** Those render-control keys no longer count toward a
   service's consent identity (see *Changed*) — approve it and it stays approved.
2. **The capture extension's token must be re-entered once per machine.** It moves out
   of `chrome.storage.sync`, which was replicating a local secret to every browser
   signed into the profile; it is removed from sync storage on first use.
3. **After a crash you may find `<name>.corrupt-<timestamp>` files in
   `.web-chat/graph/`.** They are the bytes of records the daemon could not read —
   kept instead of destroyed (see *Fixed*). Deleting them is safe once you no longer
   want them.
4. **Rebuilding a tagged tree now hashes identically on any supported OS.** If you
   verify releases by rebuilding: hashes match from this release forward; earlier
   tarballs keep their published checksums.

### Changed

- **A service's consent no longer depends on how its pane was rendered.** The trust key covers (project root, `service.js` contents, params), and "params" now means the params the *service* gets: the three keys the shell reads for itself — `form_reset`, `routing`, `signals` — are stripped before the fingerprint, since they say how a render behaves and nothing about the host process. Re-rendering a service-backed pane with `params.form_reset:true` used to restart its child and ask you to approve a service that had not changed. **You will notice two things, once:** a pane whose params carried one of those keys asks for approval one more time after upgrading (a narrow echo of the 0.7.0 re-trust, upgrade step 3 — approve it and it stays approved), and `service.js` receives `ctx.params` without those keys (the pane script still sees them).
- **`claude-web-chat trust <name>` decides one request, and says which.** The supervisor keeps `file-editor` fenced and `file-editor --unfenced` apart precisely so one approval cannot cover the other, but the by-name path recorded a decision for *every* pending request under that name, printed none of their params, and asked nothing — so a pane that mounted a component a second time with params of its own could ride along on the approval you meant for the first. A name matching more than one waiting request now prints each of them and refuses, and you pick one with `--params-fp <fingerprint>` (the listings print it; the full trust key works too) or take them all with `--all`. `--all` given a name is scoped to that name instead of every service on the machine, and a grant now names the params it granted.
- **Capture profiles get `listItems` on their injected helper kit.** A profile bundle lives outside the package and cannot `require` into it, so the bundled reddit extractor carried its own copy of the own-`<li>` list walker — the copy the ctx kit exists to prevent, and the one place the nested-list fix (a nested item emitted twice: once absorbed into its parent's bullet, once on its own) sat with no test pinning it. `listItems(el)` now rides `extract({...})` and `render(distilled, ctx)` alongside `esc`, `collapse`, `safeHref` and `absolutize`; use it instead of `querySelectorAll('li')` when flattening a list. No distillate bytes change for any profile.

### Security

- **The tab-stream extension stops replicating your capture token to your Google account.** The token is the only authentication on the capture path and it is a secret about one machine, but it lived in `chrome.storage.sync` alongside the endpoint and profile preferences — so Chrome uploaded it and pushed it to every profile signed into the same account. It now lives in `chrome.storage.local`; a token an older build synced is adopted onto this machine and removed from sync the first time the extension reads its config, so nothing needs re-entering. **You may notice** the token no longer appears on your other browsers: set it there once, per machine.

### Fixed

- **An oversized download no longer strands a `.part` file in the version cache.** `download` enforces its byte ceiling by destroying the write stream and unlinking the partial file, but `fs.createWriteStream` opens its file descriptor on the thread pool and `destroy()` does not cancel a pending open — it waits for it, then closes. On a loaded machine the open was still queued when the cleanup ran, so the unlink found nothing and the open then created a 0-byte `.part` that nothing ever removed. Cleanup now waits for the stream to close before unlinking. The ceiling itself is unchanged.
- **A long turn no longer loses its work to a graph click.** A turn holds a lock so a click on the graph cannot move the commit point out from under it, and that lock goes stale after a while so a turn that dies without finishing cannot wedge the graph forever. But nothing restarted the clock while the turn was working, so the window was measured from the moment the turn began — and for a turn started by a Push (three minutes) an ordinary long turn outran it, after which the next click on a node discarded everything it had rendered, uncommitted and with no undo. Two changes: Claude's own writes now restart the clock, so a working turn keeps its lock however long it takes (a pane driven by a service component does *not* — its writes must not hold a lock open); and if a stale lock is taken anyway, the abandoned turn's panes are committed as a `preserve` node first, the same way editing a form on an older node preserves what was on screen. **You may notice** an extra node in the graph after a turn that was interrupted; it holds work that used to vanish.
- **A catch-up cursor from before a restart is now reported as a gap.** Event sequence numbers begin again at 1 each time the daemon starts, so a cursor held across `claude-web-chat restart` (or a crash, or a self-update) sits above everything in the new log. `get_events({since})`, the browser's reconnect catch-up and a driver's `getEvents` all read that as "nothing has happened since you last looked" and carried on, while the tool's own description promised a gap whenever a cursor stopped being usable. Such a cursor now answers `gap:true` with `reset:true` (and no `dropped` count, which is unknowable across a boot), so anything that already resyncs on a gap does the right thing; the SSE `gap` frame carries the same marker.
- **A push in flight when the channel drops is redelivered the moment it reconnects.** A Push fired at a live channel is held until the bridge confirms delivery, and a reconnecting bridge is supposed to fold that un-confirmed push back in and redeliver it. It only did so when something else was *also* waiting to be delivered — so in the exact case the fold exists for (the stream died with a push in flight and nothing parked behind it), the push instead waited out a 20-second timeout and arrived attached to your next typed message. It now redelivers on reconnect, and the redelivery is itself held for confirmation, so a second drop is still recoverable rather than silent.
- **"Channel: connected" now means the same thing as a Push does.** The queue panel, `claude-web-chat status` and `init` read one endpoint to say whether a Push wakes Claude, and it answered with the raw count of open wake streams — not the liveness test the push itself uses, which also requires a fresh heartbeat. A half-open stream (a laptop that slept, a Claude Code session that died without closing its socket) therefore showed "channel: connected — a Push wakes Claude now" and hid the parked-delivery notice, while the very next Push parked. Both now use the same predicate; the raw stream count is still reported as `wake_consumers` for diagnostics.
- **The first turn after the daemon starts now commits its own node.** When no daemon was running, the turn-begin hook had nothing to lock — so a turn whose first tool call started the daemon and rendered ended with nothing committed, and its panes sat uncommitted until the *next* prompt's turn-end swept them up and stamped them with that prompt's text. That work now commits at the end of the turn that did it, as a node whose trigger reads `unlocked-turn` and carries no prompt (because there was no lock to read one from). A turn that changed nothing still commits nothing.
- **A push is only confirmed “delivered” once it has actually been sent.** The channel bridge acked a wake the instant it *called* the notification, but that call is asynchronous — a closed transport or a failed write arrives as a rejected promise, never as a throw — so a push that never left the process was still acked, and the ack is what tells the daemon to drop the batch it was holding for you. The ack now waits for the send to settle and is skipped when it fails, so the queue rail times out and offers Retry / Hold instead of showing “Delivered ✓” for something Claude never received.
- **A pane theme supplied on a render is sanitized like every other theme.** `POST /api/render` accepts a `theme`, and it was the one door onto a pane's theme that skipped the theme engine's normalizer: token names that are not `--wc-` prefixed were kept, and values kept the structural characters that let a token break out of its own `name: value;` declaration — while the same theme sent to `POST /api/theme` was cleaned. (`GET /api/theme` normalizes on the way out, so the read side always looked right.) A render's theme now takes exactly the path `set_theme {scope:'pane'}` takes. Omitting `theme` still keeps the pane's current one and sending `null` still clears it; raw `css` at pane scope is unchanged — it remains the documented escape hatch, scoped to that pane's shadow root.
- **A capture over a locked pane says so instead of reporting a clean success.** `POST /api/capture` writes the record and bumps the `tab_capture` signal whatever happens to the pane, but the pane write is a soft-reject when the user has locked that pane — and the route dropped that verdict, so the extension showed a successful capture over a pane that never updated with nothing anywhere explaining why. The response now carries a `pane` field: `'rendered'`, `'not-requested'` (the caller passed `render:false`), or the refusal envelope itself (`{rejected, locked, id, hint}`). Additive on the wire; a caller that does not know the field ignores it.
- **`/api/embed-check` recognises the fully-qualified spelling of `localhost`.** `http://localhost./` (and `http://foo.localhost./`) missed the name check, so the refusal came from the DNS-time filter instead of the cheap first pass. The fence held either way; the first layer now holds on its own.
- **`/api/embed-check` refuses a loopback or private address wrapped in a NAT64 prefix.** The v6 fence decoded only the `::ffff:` v4-mapped prefix, so `http://[64:ff9b::7f00:1]/` — the RFC 6052 well-known prefix wrapping `127.0.0.1` — read as a public host on a machine with NAT64 connectivity. The well-known prefix and the deprecated v4-compatible `::a.b.c.d` form are now decoded to the v4 address they carry, the RFC 8215 local-use prefix `64:ff9b:1::/48` is refused whole (its embedding length is not knowable), and a dotted v4 tail is folded into hextets inside the address expander so every spelling takes one path instead of a shortcut of its own.
- **`diff_nodes` no longer drops a store key named `toString`, `constructor` or `valueOf`.** The store diff asked `key in other` rather than `Object.hasOwn`, and the store is a plain object, so a key sharing a name with an `Object.prototype` member read as present on both sides: it was not reported as added, and the other loop never reached it either, so it vanished from the diff instead of showing up wrong. The theme-token diff used the same test and is fixed with it (no token can collide today — every one is `--wc-` prefixed — but the loop no longer depends on that).
- **A long-lived graph no longer breaks the graph viewer, `get_graph` and `export` all at once.** The hierarchical labels (`n1.0`, `n1.1`, …) are derived from topology on every read by a walk that recursed once per node — and a trunk is a linear chain, one node per committed turn, so at roughly 3,000 turns it overflowed the call stack and every reader of the graph started answering 500 with nothing to repair (labels are derived; there is no file to fix). The walk is an explicit stack now, so depth costs nothing, and the result is cached until the topology actually changes rather than being recomputed on every request.
- **The file editor stops showing a Save as done when nothing was written.** The pane cleared its unsaved-changes marker the instant Save was pressed, before anything could have run — so a Save clicked in the moment between a pane appearing and its service starting (or in a project where that service was never approved) left the buffer looking saved with the file untouched, and said nothing. `service.js` now echoes the control write it actually executed (`ack`), the pane clears the marker on that echo rather than on the click, and a Save with no answer within a couple of seconds says so and names the two things that fix it. A Save the service refuses — a path outside the project root, say — also keeps the buffer marked unsaved now, where it used to go clean beside the error. **You must approve the file editor once more after upgrading:** `service.js` changed, and consent is keyed to its contents, so run `claude-web-chat trust file-editor` the first time a pane sits empty.
- **What you do while the connection is down is no longer thrown away.** Every frame the page sends the daemon — a pane's store write, a pane pinned/locked/minimized/resized, a pane's activity events, a pane script's error — was gated on an open socket and silently dropped when there wasn't one; and because the reconnect's catch-up runs daemon→browser only, the reconcile then replaced the local copy with the daemon's older picture too, so the change was lost at *both* ends with nothing logged anywhere. Those frames now queue in the page (store patches merged into one, one entry per pane, a capped tail for the rest) and are sent once the reconnect's snapshot has been applied, with the local copy re-converged to match. **You may notice** a store value or a pane layout you changed across a laptop sleep now surviving instead of reverting. Typed form values were already covered by the reconnect flush and are unchanged.
- **`node-render`'s description says what the pane does.** It promised "HTML previews of each mount (scripts stripped for safety)" and a store snapshot; it has neither — the pane is an iframe onto the node's live `/preview/node/<id>` document, which splices in the mount runtime and runs every mount's scripts. That description is what Claude reads to decide whether the component fits, so anyone relying on it to embed an untrusted node "safely" was misled. It now names the containment that actually holds (an `allow-scripts` sandbox with no `allow-same-origin`, plus the preview document's CSP) and says plainly that the scripts run. Behaviour is unchanged; the existing directory is refreshed on the next daemon boot, as builtins always are.
- **The first-run tour stops declaring params it never reads.** `step` and `url` were in `web-chat-tour`'s `params_schema` and passed by `claude-web-chat init`; the component reads neither (it advances on observed evidence and never renders the URL).
- **The queue rail reads the parked batch, instead of re-reading the prose meant for Claude.** `GET /api/queue/pending` stripped the structured batch and returned only the wake envelope, so the rail's "Held for next prompt" section reconstructed its rows by matching `- [kind] summary` bullets out of `envelope.content` — text `lib/channel/envelope.js` writes for Claude, with a silent fall back to a bare "N signals awaiting delivery" whenever the shape did not match (a reworded bullet, a summary containing a newline, the 50-line cap on a large batch). The endpoint now returns `items` — the parked batch reduced to the same summary-only fields a queued item shows — and each held row renders through the same row builder a staged one does. **You may notice** held rows now carrying the source and why-wake lines staged rows have always had.
- **Dismissing the update bar remembers the right version.** The × handler recovered the version it was closing by running a regular expression over the bar's own message text. A reworded sentence — or the ✕ landing while the bar was borrowed for one of the other messages it carries, such as "you're up to date" — recorded nothing, so the bar came straight back on the next check in the same session it had just been closed for. The announced version is tracked directly now, and dismissing a borrowed message no longer mutes a release announcement nobody was shown.
- **The ⌘K palette lists the turns the graph draws.** It built its node rows from the raw commit list while every other viewer surface reads the display topology, so a turn that changed nothing — collapsed out of the DAG, the history list and the counts — still had a palette row, and picking it dropped you on a node the graph does not draw: the topbar's ↓ was dead there and only the ↑ fallback got you back out. Reveal the collapsed turns in the graph viewer and they reappear in the palette, as they do everywhere else.
- **A component spawn the daemon refuses now says so on screen.** Clicking a component in the ＋ drawer when the target pane is locked or owned by a service closed the drawer and reported the refusal into the *Manage* tab's status line — a panel that had just been hidden, that does not exist at all on a daemon without the pack routes, and that the next open rebuilds from scratch. The refusal was, in practice, a `console.warn`. It now appears in the same in-page notice the graph viewer uses.
- **`pack list --verify` no longer calls a refused record "locally edited".** A unit whose own provenance record cannot be resolved — an unknown kind, a path that resolves outside its directory — counts as drift, and the list line had one word for every kind of drift, so it blamed the user's edits for something they never touched. It now reads `· record refused`, the same distinction `pack info` and `pack remove` already made.
- **`install` no longer prints two contradictory paragraphs about one file.** A managed file whose baseline was lost while a conflict was outstanding keeps its `.new` sidecar and reports as drift — and both reporting blocks claimed it, so the same file got "merge the sidecar, then delete it" and, immediately below, "differs with no recorded baseline … run `install --force`", which would discard the edits the first was preserving. Only the sidecar reminder is printed for such a file now.
- **`claude-web-chat uninstall` in a directory that is not a project no longer un-registers anything.** It resolved its root tolerantly — falling back to the current directory when no `.web-chat/` was found above — and `remove()` un-registers Claude Code's local-scope entry by running `claude mcp remove web-chat --scope local` *in that directory*. Typing it somewhere random therefore wrote to Claude Code's own config on behalf of a project that never existed. It now reports that there is nothing to uninstall and touches nothing. A directory whose `.web-chat/` was deleted by hand but whose hooks or `.mcp.json` entry survive is still uninstalled — that wiring is what the command exists to undo.
- **A component pack is no longer refused for writing an npm range this build does not parse.** `requires.web-chat` promises that a range shape the small built-in grammar does not implement counts as satisfied — but an x-range (`1.x`, `1.2.*`), a disjunction (`^1 || ^2`) and a hyphen range (`1.2.0 - 2.0.0`) all had a numeric core the clause matcher took confidently and wrongly: `1.x` became an exact pin on `1`, `||` was read as a conjunction nothing can satisfy, and the pack failed validation with `this pack needs web-chat 1, this is 0.7.0`. Those shapes are now treated as unknown, which means satisfied.
- **`update --to <older version>` no longer syncs your project's managed files FORWARD.** Rolling back to a release that predates the registration engine (anything before 0.7.0) fell back to the running build's engine and announced it as "syncing with THIS build's templates, which may be older" — in a rollback they are newer, so the project's rules, skill and hook template were written forward to files the version just activated does not ship. A rollback in that direction now leaves managed files alone and names `claude-web-chat install` — which is the rolled-back build — as the way to sync them with its own templates. An upgrade is unchanged.
- **`install.sh` sweeps the dangling `current.incoming` link an older installer left inside a version directory.** The `mv` that bug fixed deposited the new symlink at `versions/<old>/current.incoming`, and the sweep that came with the fix only cleared `~/.web-chat/current.incoming` — so every install that had ever been upgraded through the broken installer kept the dangling link, and the mtime it stamped on that version directory skewed the prune's newest-first ordering, letting an older version outlive a newer rollback target. Re-running the installer now clears it.
- **`ls --reap` can clear a registry entry that names no project root.** Every surface below the reap is addressed by its root, and a missing root resolves to the current directory — so a hand-edited or legacy entry sent the reap looking for the portfile of the project you were standing in, while the removal of the entry itself threw and was swallowed. `ls` therefore printed the row as `(dead — registry entry is stale)` with a `--reap clears` hint that never cleared it, on every listing, forever. A dead one is now removed by the id the entry carries; a live one is reported and left alone, since nothing can say which surface it describes.
- **Spawning a daemon no longer leaks a file descriptor pair into the process that spawned it.** Both detached spawners opened the child's log file and never closed the parent's copy — and the project-daemon one opened it twice, once for stdout and once for stderr. `spawn()` gives the child its own duplicate, so what the parent kept was pure leak: invisible in a one-shot CLI, but the MCP server is long-lived and respawns a dead daemon on demand, so a Claude Code session leaked descriptors for as long as it ran. Both spawners now go through one `spawnDetached` that opens the log once and closes it as soon as the child owns its own.
- **An interrupted `update` can no longer outrank the release you are running.** The download was staged *inside* `~/.web-chat/versions/`, so a Ctrl-C mid-download (nothing in the CLI handles SIGINT, so the cleanup never ran) left a `wc-release-XXXXXX/` directory that `update --list` printed as a version and the comparator's non-numeric fallback sorted above every real release — so the prune protected the debris and deleted a genuine rollback target instead. Staging moved to `~/.web-chat/staging/`, a sibling on the same filesystem so the move into place is still a rename; only a directory whose name parses as a version is listed, activated or rolled back to; and a staging directory more than a day old is swept by the next download. **You may notice** a `versions/wc-release-…` left by an older build — it is now ignored everywhere, and safe to delete.
- **The pack panel's error text is themed, not hardcoded.** Both `.err` states in the component-pack panel asked for `--wc-coral`, a token no palette block has ever defined, so they painted from the literal `#d05a4a` written beside them as a fallback and no theme could move them. They now use `--wc-comment`, the coral the rest of the chrome already errors in (the push-failure notice, a failed comment reply). **You may notice** those two lines are a slightly warmer coral, and follow your theme.
- **A saved theme reaches the whole chrome now.** Five chrome surfaces — the topbar's gradient and bottom hairline, the dock-button hover, the stepper hover, the queue rail, and the active row in the graph history — were painted from hex literals with a hand-written light-mode twin each: a second palette living outside the `--wc-*` blocks, where no theme could reach it. Setting `--wc-header-bg` still left `#2c2519` at the top of the topbar and a `#211c12` rail. Those surfaces now resolve through tokens — `--wc-topbar-top`, `--wc-topbar-border`, `--wc-rail-bg`, `--wc-hover-bg`, `--wc-row-active-bg`, and `--wc-gold-fg` (the ink on a gold fill, which was the same literal twice) — defined in both palette blocks, so `set_theme` and a saved theme restyle them like everything else. Stock light and stock dark are unchanged pixel for pixel.
- **A graph node the daemon could not read is no longer overwritten by the next commit.** The next node id was seeded only from the node files that *loaded*, so a torn or wrong-shaped `n2.json` — skipped at boot rather than wedging it — left the counter behind it and the next turn wrote straight over the one record of that turn. An id is now claimed by a file existing: the seed scans the `graph/` directory listing, including the `.corrupt-<ts>` copies below, so a skipped id is spent for good and a surviving node whose parent is that id can never graft onto an unrelated new node.
- **An unreadable graph record is kept, not destroyed.** A node file that fails the read, and a torn `graph/_meta.json` before the boot recovery rewrites it, now move to `<name>.corrupt-<timestamp>` beside themselves (newest three kept) — the rule `draft.json` already followed. **You may notice** these files in `.web-chat/graph/` after a crash or a full disk; they are the bytes of a turn the daemon could not parse, and deleting them is safe once you no longer want them.
- **The boot recovery of a torn `_meta.json` can no longer stop the daemon starting.** Recovering `active` from the latest commit ended in an unguarded write, so a `graph/` that had become unwritable (or a directory sitting at `_meta.json`) threw out of the boot path. The heal is best-effort now: the recovered commit point is already in memory, and only persisting it for the next boot can fail.
- **Committed nodes no longer carry the live-only `gen` counter.** `snapshotLive` spread the whole live mount record into every node file and draft while the restore path picked a fixed field list, so the pane re-render counter was written into history nothing would ever read it back from — against the stated decision that committed node bytes were unchanged. A snapshot now carries exactly the fields the restore reads. Existing node files are untouched and load as before.
- **A service child survives a failed store push.** The driver handed to a service-backed component now contains an unawaited call's rejection (one stderr line, the write is lost, the next push carries the state) instead of letting it become an unhandled rejection that kills the child — which, combined with the supervisor's crash-block, silently stopped that service until its next edit. A service that awaits a driver call still sees the rejection.
- **A daemon that dies mid-response no longer hangs the thing that called it.** `lib/client`'s low-level `request()` settled only when a response reached its `end`; a daemon that crashed, was `restart`ed or reset the socket after the headers but before the body completed left the promise pending forever — and because the client deliberately has no default socket timeout (a driver's `/api/wait` long-poll needs none), the MCP tool call, hook or CLI command behind it hung with no error and no timeout. It now rejects with an `ECONNRESET`-coded error, which the client's existing connection-refused handling folds into its respawn-and-retry: a mid-response death behaves like a refused connection.
- **A non-2xx from the daemon is a typed error.** `client.get`/`post` threw a bare `Error` whose only content was a formatted message, so callers could not branch on the status and guessed in both directions. They now throw an `HttpError` carrying `{status, body, method, path}` (the message is unchanged). **You may notice:** `claude-web-chat profile reload` and `claude-web-chat unlock` used to print `✓ reloaded undefined user profile(s)` and `no lock was set` when the daemon answered 404 or 500 — they now report the failure and exit non-zero. The `export` MCP tool returns its documented `{error, ref}` for an unknown node label instead of surfacing a raw transport error to Claude.
- **A reconnect no longer overwrites the node you are previewing, and no longer eats what you typed.** The `hello` frame the daemon sends on every WebSocket connection — first open, and equally the reconnect after a laptop sleep, a `claude-web-chat restart` or a self-update — was applied by its own hand-written code path, separate from the one `reset` uses. It ignored the detached-preview state, so a reconnect while viewing an older node re-mounted the live surface straight over it; it removed nothing, so a pane the daemon had cleared during the drop lived on locally until the next full reset; and it re-mounted every pane blindly, destroying values you had typed in the meantime. All full-surface snapshots now go through one applier (`applySnapshot` in `public/app/mounts.js`) that owns the preview fold, removes panes the frame does not carry, and keeps the live DOM of a pane whose content is unchanged. **You may notice:** after a reconnect, form values typed while the connection was down are preserved and pushed to the daemon (they used to be marked as sent before the send was gated, and were silently lost), and a pane that is unchanged is no longer torn down and rebuilt — its script keeps running, and the store keys that moved are published to it instead. A `hello` is now authoritative about the store as well: a key the daemon does not have is published as removed rather than kept locally.
- **A mount id can no longer name the graph inspector's chrome or the export shell's.** The reserved-id set had a derived half (the ids in `public/index.html`) and a hand-maintained half for the ids the shell builds lazily — and the hand half had fallen four behind: a pane mounted as `gv-preview`, `gv-diff`, `gv-diff-sect` or `gv-set-active` claimed the id the graph inspector later looks up, so the node preview drew into the pane and the inspector's Set-active button stopped working. Both halves are derived now — a test scans `public/app/*.js` for the id literals the shell writes — and the same derivation covers the two documents that write a pane host with no free-id check of their own, the export shell (`export-head`, `export-main`, `export-empty`, `wc-export-data`) and the glance preview. Only the two ids a helper builds from a computed name (`wc-theme-global-css`, `wc-theme-node-css`) stay hand-listed. Renaming a mount that used one of these ids is the only user-visible effect; nothing else changes.
- **Two panes of one component with different params are two trust notices again.** The `service:trust` / `service:trust:clear` frames carried the `service.js` hash alone while consent is keyed to (root, hash, params), so two variants of one service collapsed into a single card in every connected browser — and clearing either pane, or approving just one variant, took the other's card away while its request was still pending on the server (the CLI still listed it). Every notice now carries the trust key the daemon minted, plus the params it is about, and the browser keys its cards and dismissals by that key.

- The release tarball is now byte-reproducible across operating systems. `scripts/build-release.js` left the gzip header's OS field as zlib stamped it (3 on Linux, 19 on macOS), so rebuilding a tagged tree on a different OS than the one CI cut it on produced a different sha256 — a verifier's only reading of that is tampering. The byte is now pinned to 255 ("unknown", per RFC 1952). Already-published artifacts keep their published checksums; this affects builds cut from here on.

- **The instructions Claude reads about the surface describe the surface it has.** Five claims in the rules file that `install` writes into your project — and in the descriptions Claude reads to pick a tool — had outlived the behaviour they described. It said every turn of Claude's commits a graph node (a turn that changes nothing on the surface commits nothing and folds onto the next node that does), told Claude to name a node by its stored id four lines after telling it the id is opaque and to use the label you can see (`n1.4`), banned `document.*` outright in a pane script when only the *queries* fail inside a shadow root (`document.createElement` is fine, and is the safe way to build a pane from data), described `list_components` as "components in this project" though it lists your user-level and builtin ones too and marks which carry a live `service.js`, and told Claude that a saved theme beats a builtin of the same name when `apply_theme` resolves the builtin first. **You may notice** Claude referring to nodes by the label on your screen, and reaching for a service-backed component more readily for live host state. `install`/`update` offer the corrected rules file the way they offer any managed file.
- **`claude-web-chat docs` prints fewer things that are no longer true.** The service-components reference placed the service trust store inside the project (consent moved to `~/.web-chat/services/trusted.json` precisely so a cloned repo cannot ship its own approval), omitted two of the supervisor's stop triggers, and showed a control-key startup snippet that would re-run a `save` clicked before the service existed; the driver reference sent authors to modules that no longer hold the lock TTL or the event ring; and platform-support still listed `install.sh` as something CI never runs and claimed `ls --reap` can never signal. A new `test/doc-truth.test.js` section holds each of these against the code, so the next consolidation that moves one of them fails the build instead of the docs.

### Internal

- **One CRC-32 and one ZIP writer.** The browser-extension download served a store-only ZIP encoder written inline in `lib/server/routes/extensions.js`, with its own bitwise CRC-32 next to it, while `extensions/make-icons.js` carried a second, table-driven CRC-32 for PNG chunks — a checksum Node has shipped natively since 22.2. Both now come from `lib/core/zip.js` (`writeZipStore` / `crc32`), which prefers `zlib.crc32` and keeps one fallback table for the point releases below it, guards the 32-bit header fields instead of silently writing a wrapped value, and walks the tree in sorted order so a directory packs to the same bytes every time. The encoder finally has a round-trip test — including a real `unzip -t` where the platform has one — and two ratchet rows keep either copy from growing back. The archive a user downloads is unchanged apart from entry order, and the checked-in icon PNGs are byte-identical.
- **The release history says what shipped when.** 0.5.0 had no section at all (its version bump carried the GitHub-Releases rewrite and touched no changelog, and the `[Unreleased]` block it shipped was relabelled `[0.6.0]` hours later), 0.3.0 claimed an install with "no npm registry" that in fact ran `npm i -g`, the 0.7.0 embed-check note described the `website` pane doing the opposite of what it does, and four changes released in 0.7.0 — `trust --all`, the drawer's copy button, the dropped MCP sidecar nudge, the daemon's no-capture-hub line — were recorded nowhere. All corrected in place, and `test/changelog-truth.test.js` now checks the claims that have a truth source in the tree.
- **The shell's stylesheet no longer describes chrome that does not exist.** Four families of class rules matched nothing in the product — `.qchip` and its `@keyframes qpulse` (the queue rail's collapsed chips, renamed `.rail-chip` long ago), `.rchip` (graph history row chips), `.pin-menu-text`, `.spacer` — alongside a `.update-banner.ok` success state and a `.ub-btn:disabled` for the one-click "Update & restart" flow that was removed, and six per-component `.hidden` rules shadowing a global `.hidden` that is already `!important`. Two comments described surfaces that had since shipped or been deleted. All gone, and `test/shell-chrome.test.js` now fails the build for any class `public/app.css` styles that nothing in `public/`, `templates/`, `lib/` or `extensions/` can set, with a named allowlist for the four class names `queue.js` composes at runtime.
- **One palette in `public/app.css`, ratcheted.** The 42 never-firing `var(--wc-x, #hex)` fallbacks are gone — the sheet is loaded by `public/index.html` alone, where `:root` defines every token asked for, so each fallback was a second (and in places a different) value for a colour that always had one. Three static tests in `test/shell-chrome.test.js` now hold the line: the Earthy Light block is the only rule that branches on mode, every `--wc-*` reference resolves to a token some palette block defines, and the literal colours outside those blocks are an allowlist of three (two mask alphas and one `#fff` lighten). No rendered pixel changes.
- **Tests consume the one truth source instead of restating it.** Five assertions hand-copied a fact the code already owns, and each copy could go stale while still passing: three `tools.length === 23` literals now compare against `mcpTools()` (and the tools/list test deep-equals the SDK-exposed *names* against `lib/mcp/tools/`), the `npm link` prohibition walks `docFiles()` rather than a two-element list — so it now covers CLAUDE.md, which carried the warning but was never checked — and the channel activation hint is asserted against `LAUNCH_COMMAND` in full, with a new pin that the constant ends in the channel name (the audited regression was a `--dangerously-load-development-channels` with nothing to load, which the old prefix match accepted). The deaf raw-socket WebSocket client that two shutdown suites had each copied is now `deafWs(t, port)` in `test-support/helpers.js`. `test/harness-conventions.test.js` gains two shrink-only rows — a hand-written `Sec-WebSocket-Key:` upgrade outside `test-support`, and a hardcoded MCP tool count anywhere — so the class cannot recur silently.

## [0.7.0] - 2026-08-28

### Upgrading from 0.6.0

No state migration runs — the on-disk schema is unchanged, so your graph, drafts, components, themes and packs are read as-is. What you have to do:

1. **Upgrade Node first — 22 is a hard floor.** A transitive dependency is ESM-only, so on Node 18–21 the daemon does not start at all.
2. **After `claude-web-chat update`, run `claude-web-chat install` once in each project.** This hop is performed by the 0.6.0 binary, which syncs managed files against *its own* templates — so the new `.claude/rules/web-chat.md`, the capture-profile skill and the `.gitignore`/`.mcp.json` reconcile arrive only on that next install. `status` says `N need refresh` until you do. (From 0.7.0 forward, `update` syncs with the new build's engine.)
3. **Re-trust the two builtin services.** Consent is keyed to the contents of `service.js` and both builtins changed: run `claude-web-chat trust git-dashboard` and `claude-web-chat trust file-editor` the first time such a pane comes up empty (bare `claude-web-chat trust` lists what is waiting).
4. **Finish a managed-file conflict by merging the `.new` sidecar and then deleting it.** Deleting it is the resolution; nothing deletes it for you, and `install`, `update`, `status` and `init` keep naming it until it is gone. Do not `git clean` an unmerged sidecar away — the offer is recorded as made, so you would silently keep the older text. `install --force` remains the alternative that adopts the shipped file and discards your edits.
5. **Reach the surface as `localhost` or `127.0.0.1`.** The daemon and the capture hub now check the `Host` header and answer `421 Misdirected Request` to anything else, so a forwarded or tunnelled port, a container hostname or a proxy that rewrites `Host` is refused — for the page as well as the API. Set `WEB_CHAT_HOST` to the address you bind (accepted alongside loopback), or to a wildcard such as `0.0.0.0`, which skips the check and leaves the bind address as your only access control.
6. **`claude-web-chat install` typed in a subdirectory now installs into the enclosing project root.** A deliberately nested second surface inside another installed project is no longer supported. `uninstall`, `on`, `off`, `status` and `doctor` resolve the same way.
7. **`init --json` renames `surfaces[].live` to `surfaces[].pid_alive`** (and adds `reachable`). Anything parsing that report needs updating.
8. **`file-editor` fences paths by realpath now**, so a symlink inside the project that resolves outside it — including one whose target does not exist yet — is refused where it used to be followed. Use `unfenced: true`, or point `root` at the tree you mean.

Three more repairs are conditional — they apply only if they describe you, and each is spelled out in *Fixed*: a committed `${CLAUDE_PLUGIN_ROOT}` stub in `.mcp.json` that the 0.6.0 code rewrites to an absolute path one last time (check `git diff .mcp.json`); an install made by an `install.sh` older than this one, whose `current` symlink may still point at the previous version (check `claude-web-chat version`); and a component ever saved over a builtin name, whose shadowing directory the daemon now names on stderr at boot for you to delete by hand.

### Security

- **Graph-node previews carry a Content-Security-Policy.** `/preview/node` is served from the daemon's own origin and the graph viewer instantiates one per node thumbnail plus the glance card, so pane scripts from nodes you are not on were re-executing unattended with `fetch` reach into `/api/*`. **You may notice:** inside a *preview*, a pane that pulls an image, font or iframe off the network renders empty; the live surface is unchanged.
- **`/api/embed-check` can no longer be used to probe your local network.** The route has the *daemon* fetch a caller-supplied URL and nothing restricted the target; loopback, private, CGNAT, link-local and reserved addresses — and any name that resolves to one — are refused at DNS time, every redirect hop is re-checked, and credentials are stripped. **You may notice:** nothing in the `website` pane. A `localhost` URL is framed without asking the daemon at all, and for every other target the daemon labels this one refusal (`code:"private-target"`), which the pane answers by framing the URL itself — so a dev server on `192.168.x`, `myapp.test`, `foo.local`, `host.docker.internal` or a Tailscale address still loads, because the browser is under no such restriction (see *Fixed*, below). What changed is that the daemon will not dial any of them on a caller's behalf.
- **`GET /api/export/:ref?format=file` refuses browser-originated requests.** The disk-writing half of the export route had no gate, and as a plain GET an `<img src>` on any page could write files under `.web-chat/exports/` and spam the event ring. The `export` tool, `claude-web-chat export` and the topbar **⬇** button are unaffected.
- **The daemon and the capture hub check the `Host` header.** A rebound DNS name reaches a loopback-bound daemon *same-origin*, so no `Origin` is sent, CORS reflected `*`, and the WebSocket gate was never consulted. The check is mounted first on both apps and folded into the WS upgrade; refusals are `421` naming the host dialled, and the hub's protocol version is bumped so the next instance boot bounces a pre-gate hub. See upgrade step 5.
- **A graph node's name can no longer run script in the chrome.** The ⌘K palette interpolated the node label into an `innerHTML` template while the bookmark route only trims it, so a bookmark named `<img src=x onerror=…>` executed in the surface's privileged origin.
- **`javascript:` hrefs no longer reach a capture pane or the reader sidecar.** The URL helper passed the scheme through, three bundled profiles carried ungated copies, and the one regex gate was bypassable with an embedded tab. `safeHref` now normalises through `new URL` and returns `''` for anything outside http/https/mailto/tel, keeping the link text.
- **Both builtin services are hardened.** `git-dashboard` passed store values into git's argv, where a leading `-` is an option and `git log --output=<file>` writes files — so anything on the surface could make the daemon overwrite a file you can write. `file-editor` joined a version id into a path unchecked, fenced lexically (a symlink out of the project was followed), and re-executed the persisted `editor_ctl` write on every respawn, silently rewriting a file from a stale buffer. Refs are now checked against what the service itself read and fenced behind `--end-of-options`, the fence is realpath-based, and the control cursor starts at the service's start time, so only a write stamped during this service's life executes and a respawn adopts view state (`open`/`browse`) only. **You may notice:** an `editor_ctl` write whose `seq` is not a wall-clock timestamp is ignored, and both services ask for trust again (upgrade steps 3 and 8).
- **A pack archive can no longer OOM the daemon by decompressing.** The pre-extraction gate gunzipped the whole archive into one Buffer with no ceiling, which the 64 MB download cap does not bound. Inflation, and so extraction, is capped at 256 MB.
- **A component name is validated before it becomes a path.** Express decodes `%2f` into a route parameter, so `..%2f..%2fx` reached the component read, seed and `use` routes unguarded — and `use` writes the name into the string the service supervisor forks. A name that fails the kebab grammar answers 404, and `pack remove` re-checks recorded unit names the same way.

### Added

- **A stated platform position — `docs/platform-support.md`.** macOS and Linux are supported (CI runs the full suite on both, Node 22 and 24); Windows means WSL2. It lists the known cross-platform defects rather than filing them away, with per-platform findings on the `platform/linux` and `platform/windows` branches.
- **A mount id may not name the shell's own chrome.** `main`, `topbar`, `status`, `dock`, `stage`, `overlay`, `drawer`, `minbar`, `queue-rail`, `cmd-palette` and the rest are refused on `render`, `use_component` and the capture path with `{ok:false, reserved:true, hint}` — a 200 with `ok:false`, because the tools and the drawer read `.ok`. The static half of the set is derived from `public/index.html` in a test, so it cannot fall behind the chrome.
- **A pack install is one transaction, and re-installing a pack is a real update.** An undo journal copies overwritten files aside and unwinds on any throw, so a failed install leaves the tree byte-identical and a failed update restores the previous version; the record is written first as a `pending` marker in its own file, so a half-install is never reported as installed (`pack list` shows it under **interrupted installs**, and re-running the install is the whole recovery). `pack install <same url>` now also diffs the previous record against the new plan. **You will notice:** an update can delete files, which it never did before — except ones you have edited, which are kept and released to you.
- **`claude-web-chat trust --all`** — one confirmation for everything waiting, instead of one command per service. A pack that ships three service-backed components used to mean three commands typed out of a notice on screen. There is deliberately no `--yes`: the whole point of the gate is that a human read what is about to run, so the flag collapses the typing, never the reading.
- **A copy button on the command a notice tells you to run.** The surface cannot grant a service approval — the component's own pane script runs in that page — so all it can do is name the command; getting it into a terminal is now one click rather than a careful re-type, with a select-it fallback where the clipboard is unavailable.

### Changed

- **Turns that changed nothing are hidden in the graph viewer.** Graphs written before fold-forward kept a run of byte-identical nodes, one per chat-only turn, which is what makes a long graph unnavigable. The payload now reports which nodes match their parent and which node absorbed each run. Nothing on disk changes, labels such as `n1.7` still name the same node, a filter chip shows them all again, and a node is never hidden if it is a root, fork, tip, active, bookmarked or named.
- **A capture pane is a pane like every other one.** It emits the ring `render` event (so it shows in `get_events` and the service supervisor sees it), carries a `gen`, is soft-rejected over a user-locked pane, and **carries the pane's `form_state`** — so a value you typed into a capture pane survives the next capture of that page. The extension still takes over its own pane on every capture; that one is deliberate.
- **`ls --reap` asks instead of signalling, and never signals a pid it cannot identify.** A row is stopped only when a daemon answers on its port and reports the pid the registry named, through the same acknowledged-shutdown engine `stop` uses — so a reaped surface's uncommitted work is saved to `draft.json`. **You will notice:** a wedged daemon (pid alive, port silent) is printed with its pid and a `kill` hint instead of being stopped, because from the outside it is indistinguishable from a stranger's process that inherited the pid.
- **`ls`, `init` and `init --json` tell the truth about a stale surface.** `surfaces[].live` becomes **`surfaces[].pid_alive`**, joined by `reachable`; the old field was permanently true, because the read pruned dead entries before anything looked at them.
- **One HTML escaper, and capture profiles get a helper kit instead of rolling their own.** `escapeHtml` lives in `lib/core/html.js` and escapes five characters (`& < > " '`) everywhere; extractors and panes receive `{ esc, collapse, safeHref, absolutize }` on their context, since a profile bundle lives outside the package and cannot `require` into it. **Byte-level consequence:** where a copy escaped only four characters, an apostrophe now serialises as `&#39;`. It renders identically, but the bytes change in the reader-lite pane, in the `<id>.simplified.html` sidecar, and in the HTML fields of the **wikipedia** and **reddit** distillates `get_captures` returns (`summaryHtml`, `valueHtml`, `bodyHtml`, `textHtml`). The `article` distillate was already on the five-character escaper and is unchanged; the youtube distillate carries no HTML fields.
- **An invalid `profile.json` is a logged skip rather than an inert profile.** A typo'd matcher `type`, an uncompilable regex or a malformed `pane` block used to load cleanly and simply never match; such a bundle now disappears from `list_profiles` and the extension's capture button, with the reason on the daemon log. In the other direction, a bundle with no `name` is accepted and takes its directory name.
- **Unresolvable relative hrefs and `data:` URLs disappear from distillates and reader panes.** `safeHref` returns `''` where the old resolver returned the raw value; the link text is kept. In practice: pages captured with no URL, and inline `data:` images in the reader view.
- **`article` and `simplify` resolve links against the page URL, not its origin.** `<a href="c.html">` on `https://x.com/a/b/page.html` used to resolve to `https://x.com/c.html` — broken images and dead links on any site using relative paths.
- **One wording for a managed-file conflict, and it terminates.** The reconcile recorded nothing when it offered a `<file>.new`, so a hand merge matched neither the baseline nor the shipped bytes and the same conflict re-fired on every install and update forever. The conflict branch now records the bytes it offered — `managed.json` means "the shipped bytes this file was last reconciled against, applied **or** offered" — so a merge settles as *kept (locally edited)* while a genuine template change still announces itself. The `.new` sidecar is the reminder and persists until you delete it; it used to be destroyed silently by the next reconcile, taking the merge material with it. No migration; how you finish one is upgrade step 4.
- **`claude-web-chat update` syncs the whole registration, and never writes Claude Code's own config.** The managed-file sync now runs the newly installed build's engine out of `versions/<target>` — it used to be bound at module load from the tree being replaced, so it compared your project against the *old* templates and reported everything up to date — and it also runs the registration engine's `apply()`, adding a missing `.web-chat/` line to `.gitignore` and reconciling the `.mcp.json` entry. What it will not do is `claude mcp add web-chat --scope local`, which writes Claude Code's config outside the project; `update` prints that command instead. **This fix does not apply to the 0.6.0 → 0.7.0 upgrade itself**, which the 0.6.0 binary performs with its own templates: see upgrade step 2.
- **Node 22 is now the floor** (`engines: >=22`, was `>=18`). `entities@5`, reached through `node-html-parser@8`, is ESM-only, and `require(esm)` landed in Node 22 — below that the daemon throws while `lib/server` is still being required. Node 18 and 20 are past end-of-life; CI covers 22 and 24.
- **Every URL the CLI prints honours `WEB_CHAT_REPO`.** The slug was hardcoded in four user-facing strings, so pointing web-chat at a fork moved the downloads while `update`, `version` and `init` still told you to `curl` the original repository's `install.sh`.
- **A `clear` naming an id that is not mounted no longer emits a clear frame.** The response is still `{ok:true}`; the wire now describes what the server actually did.

### Fixed

#### Daemon lifecycle

- **`stop` no longer reports a stopped server as running, or tells you to `kill -9` a pid that is gone.** A dead pid's leftover portfile and registry entry are reaped and the outcome reported as `{ok:true}`, so `restart` proceeds instead of aborting.
- **A daemon asked to stop always releases its records.** The SIGTERM `stop` fires at the end of its budget used to truncate a working shutdown instead of escalating a stuck one, leaving a stale portfile behind.
- **One unresponsive browser tab can no longer hold a shutdown open forever.** The connection drain gets a one-second grace and then hangs up, so a merely slow browser gets a hard hangup rather than a clean close code — and `stop`'s budget is now sized on a bounded worst case.
- **A departing daemon can no longer tear down the live one's records.** The `~/.web-chat` registry entry is now released under the portfile's ownership rule; an orphan's exit used to delete the live daemon's entry, taking `ls`, `doctor`'s registry check and the capture hub's routing with it.
- **`ensureHub` no longer stalls in silence when the hub belongs to another user.** An `EPERM` on the bounce ends the attempt immediately, naming `WEB_CHAT_HUB_PORT`, instead of costing two full waits and returning a `null` nobody logged.

#### Install & registration

- **`install` in a subdirectory installs into the project** instead of creating a nested surface Claude Code never loads. See upgrade step 6.
- **`uninstall` is reversible again.** It now also runs `claude mcp remove … --scope local` (printing the command when `claude` is not on PATH), so a "clean" removal is not undone by the first tool call re-creating `.web-chat/`.
- **`doctor` and `status` no longer pass a project that is missing half its hooks.** They report per event against the template; a project that had lost its `Stop` hook used to look healthy while no turn ever committed. The output shape changed with it: `status` now prints Hooks as `N/M registered` naming any missing event, and can report the MCP entry as `— NOT resolvable: <reason>` — worth knowing if you parse it.
- **`doctor`'s MCP repair points at `~/.web-chat/current/`,** not at a `versions/<v>/` path that pruning deletes three updates later — which silently stopped the MCP server from spawning, inside a local-scope registration that never self-heals.
- **`install` stops rewriting a committed `${CLAUDE_PLUGIN_ROOT}` stub to your machine's absolute path.** **On this upgrade only**, the 0.6.0 code performing it rewrites the placeholder one last time — check `git diff .mcp.json`, restore the stub, re-run `install`.
- **Re-running `install.sh` upgraded nothing.** The `current` symlink swap put the new link *inside* the old version directory, so every curl-one-liner upgrade after the first printed the new version and left all three commands on the old code (`claude-web-chat update` was never affected). **If you have upgraded that way, check `claude-web-chat version`** — re-running the new installer repairs the link.
- **`on` in a project that was never installed refuses and names `claude-web-chat init`,** instead of printing the reassuring "web-chat is not disabled for this project" and changing nothing.
- **An MCP tool call in an uninstalled project names a command that would help.** The disabled envelope carries `reason: 'not-installed' | 'marker'`, and the hint says `init` for the first.
- **`install` no longer kills `init` mid-sequence** by calling `process.exit(1)` from inside a library call on a malformed `.claude/settings.json` or `.mcp.json`.
- **`init` refuses Node 18–21** instead of passing them with a green tick and failing obscurely at `open` seconds later.
- **`claude-web-chat open` prints its manual-open fallback when there is no browser launcher,** rather than dying with a raw stack — a missing executable arrives as an async `'error'` event, so the `try`/`catch` around `spawn` was dead code.

#### Surface & graph

- **A pane could delete or hijack the surface's own chrome by naming it** — `render({id:'main'})` removed `<main>`, `id:'overlay'` the graph viewer, and the removal replayed on every reload, so the surface stayed dead until the mount was cleared from outside the browser. The client now only removes mount hosts and resolves targets against real slots. (The server-side refusal is in *Added*.)
- **The surface no longer comes up dead in a private window or with site data blocked.** `localStorage` *throws* under those conditions, and the unguarded read was the first statement the app ran, so the whole module graph went down with it.
- **One bad pane no longer reads as a dead surface.** Mounts from the `hello` frame are isolated, so one throw no longer takes the active pill, the queue rail and the version check with it.
- **Keyboard navigation, fork glyphs and the inspector breadcrumb follow the graph the viewer draws.** ArrowDown used to select a *hidden* node (no glyph, no camera move, a second press needed), a trunk node was labelled `⑃ FORK`, and the fork count read one high; `[`/`]` and the topbar's ↑/↓ now step where the arrow keys do.
- **Holding an arrow key can no longer leave the inspector describing one node while its buttons act on another.**
- **`Set active` from the graph overlay honours a queued re-aim.** The inspector button and the glance card's ◉ used to drop out of preview even when the server only *queued* the move, leaving an old node on screen and treated as live.
- **No native dialogs left in the chrome.** The three `Set active` failure paths used `alert()`, which wedges an automated driver.
- **The comment popover is dismissed by the same layer as every other panel,** so Escape reaches an open thread and opening another panel closes it.
- **`use_component` no longer clobbers a pane it does not own, and stops dropping the pane's theme.** It takes `render`'s mount-set path now and accepts `force`; the missing `gen` also let a queued Revert delete the fresh pane.
- **`use_component`'s schema gained `force` and `signals`, which its description already promised** — a top-level `signals` array used to be silently discarded, so the declared wake never registered.
- **A render that supplies a `theme` for an existing pane applies it,** rather than keeping whatever theme the pane was first created with.

#### State durability

- **A torn `graph/_meta.json` no longer boots you to a blank surface and then deletes your draft.** All three graph records are written atomically now, and an unreadable one recovers the active node from your latest commit instead of looking like a deliberate wipe.
- **A graph node file containing `null` or `{}` no longer wedges a project's daemon forever.** Both are valid JSON, so the old skip-on-error guard (which wrapped only the parse) let them through to throw later; the shape is checked inside the read now.
- **A draft the daemon cannot use is kept, not deleted** — renamed aside as `draft.json.corrupt-<ts>`, newest three kept. It is still not applied, but the bytes are recoverable.
- **An unreadable `_version.json` no longer skips every pending migration.** A missing file, a truncated one and an `EACCES` all returned `0`, which the runner reads as "fresh project — stamp and run nothing"; an unusable file now warns and is assumed to be v1.

#### Capture, packs & services

- **HTML entities are decoded once, everywhere.** Inline walkers read the raw source text, so `Tom &amp; Jerry&#8217;s&nbsp;show` reached the `article` distillate undecoded and the reader pane double-escaped it.
- **A nested list no longer emits its items twice** (`querySelectorAll('li')` descends into nested lists, so the inner item appeared merged into its parent and again on its own).
- **`inspect_capture { profile }` re-runs the profile with the capture's URL.** It had no `url` parameter, so the authoring dry-run its description advertises ran every extractor with an empty URL.
- **A `mount_suffix` collision now actually resolves** by walking to a free suffix, instead of falling back to the name that collided.
- **Re-using a service pane's id with different params restarts — and re-gates — the child.** Identity is now the (`service.js`, params) pair, matching the trust key; `file-editor`'s `unfenced:true` is exactly what params can change about what you approved.
- **A service that never finished shutting down could not be killed.** A second signal is decisive now — the child used to answer both the IPC `stop` and the follow-up `SIGTERM` with a handler that returned immediately, and there is no `SIGKILL` above it.
- **A restarted service pane could leave a second copy of the service running,** because a reconcile respawns in one pass and the old child's exit was read as the replacement crashing — dropping the live child from tracking so nothing ever stopped it.
- **A pack change reconciles the service supervisor,** so an update that removes a component's `service.js` stops the approved child with it.
- **A quarantined pack belongs to the project it was staged in.** Records keyed on the pack name alone let a second project orphan the first project's staged tree, read its files through `review`, and install and delete them through `approve`.
- **`pack remove` unlinked whatever the installed record named, with no containment check** — and `packs.json` is project-tier, so a cloned repo could ship a record whose unit name is `../../../..`. Records are validated at read time (kebab unit names, path refusals, realpath containment anchored on the project root); a failing unit is refused whole and kept so the evidence survives, and `--force` does not override it.
- **`planInstall` was documented as pure and created six directories** — including for the plan computed over a tree you have *not* approved.
- **`save_component` over a builtin name permanently broke that builtin,** writing a component with no `builtin` marker — the one thing `seedBuiltins` repairs on — so every later fix to `git-dashboard` or `file-editor` silently failed to land. **Two consequences:** the refusal is prospective, so a project where this already happened keeps the shadowed component and cannot overwrite it back; the daemon names the directory on stderr at every boot with the path to delete, and removes nothing itself, because your edits are in it. And a component directory whose name is not plain kebab-case stops resolving through the read routes rather than resolving by luck.
- **The `website` component reaches local dev servers again.** This release's SSRF fence on `/api/embed-check` made the pane skip its pre-check using a hand-copied, narrower private-address list, so a target that list missed — `myapp.test`, `foo.local`, `host.docker.internal`, a Tailscale `100.x` address, any name only your resolver can place — was pre-checked, refused by the daemon and painted "could not reach this URL" although the browser could frame it perfectly well. The daemon now labels that one refusal (`code:"private-target"`), the pane frames the URL itself when it sees it, and the private-address list exists in exactly one place. The daemon still never dials a private address on a pane's behalf.

### Internal

- **One mount-set engine — `lib/server/domain/mounts.js`.** Four routes hand-copied the reserved-id / lock / owner / `gen` / carry-rules / emit sequence and each dropped a different part of it.
- **One project-registration engine — `lib/setup/registration.js`,** consumed by `doctor`, `status`, `install`, `uninstall`, `on`, `off`, `update` and the MCP dispatcher — replacing five answers to "which root", two hook counts that counted different things, and two contradictory `${CLAUDE_PLUGIN_ROOT}` policies.
- **One durable-JSON-record engine — `lib/core/fsjson.js`:** an atomic write plus a four-state read (`ok`/`absent`/`corrupt`/`invalid`), replacing two spellings of the temp-file idiom and five private readers that each collapsed a different pair of states.
- **The capture route is thin.** `lib/capture/pane.js` owns pane rendering (so `profile dry-run` shows what the surface shows), and one bundle loader is shared by the daemon and `profile validate`.
- **Four generic helpers moved down into `lib/core`** with re-exports at their old homes: realpath containment (the pack pipeline's security walk was importing the *updater* for it), `escapeHtml`, the Node floor and the repo slug. `--wc-*` token sanitising also has one home now, replacing three different strip sets — a newline inside a token value becomes a space.
- **`topbar.leavePreview(opts)` and `graphIndex()` in the chrome.** The exit-preview transition had eight drifting copies of the flag that gates every write out of the page; the display-topology index was verbatim twice and decides both the fork glyphs and what the keyboard expands.
- **The test harness gained an engine, and `npm test` a timeout and a HOME sandbox.** Nine files carried a private deadline poll under four names with three incompatible contracts, and three opened SSE streams that could never reject. `--test-timeout=60000` turns an unsettled await into a named failing test (deliberately not `--test-force-exit`), and an `--import` sandbox points `HOME` at a throwaway dir before any `require`, so the suite no longer writes your real `~/.web-chat` or bounces your live capture hub.
- **Four ratchets, and coverage where there was none.** A dependency-direction test fails any relative `require()` edge the documented layering forbids; a doc-truth test checks every machine-checkable claim in the shipped docs (tools, routes, commands, the engines table, no hardcoded `localhost:5173`); `process.kill(` and browser storage joined the conventions tripwire. First tests arrived for `ls` and `--reap`, for keyboard navigation and the exit-preview divergences, and for the comment-pin composer.
- **The docs stopped claiming things the code stopped doing.** CLAUDE.md's route `ctx`, the `tab-stream` README's deleted `wait_for` and its 5 MB body limit (it is 200 MB), `embed-helper`'s hardcoded port, `docs/export-pages.md` (a pre-implementation plan linked as the user doc), and four sections of `docs/capture-profiles-and-panes.md` specifying an interaction slice that does not exist — now correct, or banner-marked `NOT BUILT — design`.
- **The MCP server stopped nudging about an unmerged `.new` sidecar.** Its once-per-session drift line says "run `claude-web-chat install`", and `install` cannot merge a conflict for you — the resolution is by hand — so a `pending` row would have repeated an unactionable reminder every session until the user got to it. `status`, `init`, `install` and `update`, which the user asks for, all still report it.
- **The daemon says so at boot when no capture hub could be brought up.** `ensureHub()`'s return value was discarded, so a hub that could not start (another user's, on the machine-wide hub port) was silent everywhere but `doctor` while captures from the browser extension had nowhere to land. It now writes one stderr line naming `claude-web-chat doctor`.

## [0.6.0] - 2026-08-24

### Security
- **`Authorization` is now dropped on a cross-host redirect.** A GitHub release asset URL redirects to object storage on a different host, and the redirect follower carried every header across that hop. Latent while nothing minted a token — but `GITHUB_TOKEN` has to be honoured (unauthenticated `api.github.com` is 60 requests/hour/IP, and a pack install makes several), which would have turned it into a live credential handed to whoever answered at the far end. A token is also only ever minted for a `github.com` host now, never for a URL the user pasted.
- **The daemon and the capture hub now bind loopback.** Both called `listen(port)` with no host, so everything web-chat serves — the graph, the shared store (which holds whatever a `file-editor` pane has open), arbitrary HTML/JS injection through `POST /api/render`, and `POST /api/update` — was reachable from the local network with no authentication. Set `WEB_CHAT_HOST` to opt into a different interface deliberately.
- **The WebSocket endpoint now checks `Origin`.** Browsers apply no same-origin policy to WebSocket connects and the `hello` frame is an unconditional full-state disclosure, so any page a user visited could open `ws://localhost:<port>/ws`, read the entire store and every pane's HTML, and write store keys back. Non-browser clients (local drivers, the CLI) send no `Origin` and are unaffected.
- **Service consent records moved to the user tier** (`~/.web-chat/services/trusted.json`). They used to live at `.web-chat/services/trusted.json` *inside the project*, so a repository could ship its own pre-approval: cloning a hostile repo and opening it ran its `service.js` with no prompt.
- **Service consent moved to the terminal — `claude-web-chat trust`.** It used to be a decision made on the surface, which cannot work: pane scripts are compiled with `new Function` and run in the page's own window realm with `document`, `fetch` and `WebSocket`, and no CSP is served, so a component's pane can synthesise a click on any button, open its own same-origin socket and read anything broadcast to the shell, and call any localhost endpoint. Nothing delivered to that page is a secret from the code the gate exists to gate. The surface now shows a notice naming the command; only a shell can grant. Consent is also keyed per **(project root, `service.js` hash, params shape)**, so the same component in another project, an edited service, or different params each ask again — which is what stops one `file-editor` approval covering `unfenced: true`, or a cloned repo inheriting a grant.
- **Capture reads are no longer world-readable.** The CORS layer reflected whatever `Origin` arrived, so any website the user visited could read every capture — distilled content and raw DOM — from the unauthenticated `GET /api/captures*` routes. Only extension and same-machine origins are reflected now.

### Fixed
- **The surface's first paint died on Node 18 and 20.** `public/app/mounts.js` read `navigator.platform` unguarded to pick `⌘` vs `Ctrl` for the zero-state's keyboard hints, and `globalThis.navigator` only exists from Node 21 — so on the versions `package.json` actually claims to support, the `ReferenceError` escaped the `hello` WebSocket handler and took the whole initial render with it. Found by CI's first-ever run: the suite had only ever run on a maintainer's Mac, on a newer Node than any supported floor.
- **The `＋` button never closed the drawer.** Every other chrome trigger declares `aria-controls`, which is what opts it into the dismiss layer's skip-the-panel-I-own rule; `＋` declared none, so `pointerdown` closed the drawer and the button's own click immediately reopened it. It also expressed openness with `.open` while every other panel uses `.hidden`, which is why the dismiss layer carried two special cases for it.
- **A component saved mid-session was invisible in the ⌘K palette until a reload.** The palette memoised its own component list and nothing ever invalidated it. There is now one cache, invalidated by a `components` frame the daemon emits wherever the component set can move — so a `save_component`, or a whole pack install, shows up everywhere at once.
- **A component whose `meta.json` name disagreed with its directory was listed but unspawnable.** The registry listed by `meta.json`'s `name` and resolved by directory, so such a component appeared in the drawer and the palette under a name `use_component` could not resolve. The directory name is the identity now; the disagreement is shown as a chip instead of silently preferred.
- **A soft rejection from `use_component` looked exactly like success.** The drawer discarded the response, so spawning into a locked or driver-owned pane simply appeared to do nothing.
- **Service-backed components could never be approved at all.** The trust prompt was emitted as a render targeting `overlay`, which the client resolves to the graph-viewer element — `display:none` until the user presses `G`. The prompt was filed inside a hidden panel, so both shipped builtins (`git-dashboard`, `file-editor`) and every user-authored service simply never started, with no prompt and no error. Approval is now a terminal command (see Security above), and the surface's notice is re-announced to every arriving viewer so a refresh mid-prompt no longer leaves a pane sitting there unexplained.
- **`claude-web-chat docs` crashed on every installed copy.** `docs/` was missing from the package `files` allowlist, so the three pointers the shipped rules file gives Claude all died with a raw `ENOENT` stack. The directory now ships, and a future packaging slip degrades to a message instead of a crash.
- **A single truncated node file could wedge a project's daemon permanently.** `graph.load()` parsed every node through a bare `JSON.parse`, so one partial write — a crash or a full disk — threw out of the unguarded `createServer` call path and the daemon could never boot again for that project. Unreadable nodes are now skipped with a warning.
- **Re-running `install` started a second daemon on the same project** and overwrote the portfile, orphaning the first — which kept running and kept writing the same graph directory, invisible to `stop`, `status` and `doctor`. It now probes for a live instance first, matching every other spawn site.
- **A Push could report "Delivered to Claude ✓" and be silently dropped.** Two causes, both fixed: `install` pinned `WEB_CHAT_CHANNEL=1` into `.mcp.json`, which made the MCP server start a channel bridge in *every* session including ones launched without the capability flag; and the bridge's ack confirmed only that bytes were written to stdout, not that anything received them. The env now comes solely from the launch line that also carries the flag, `install`/`update`/`doctor` clean a stale one, and an ack with no live consumer leaves the batch retained so the parked-delivery backstop still fires.
- **The launch command web-chat printed could not work.** `LAUNCH_COMMAND` omitted the `server:web-chat` argument the flag requires, so the incantation shown by `install`, the queue rail and `doctor` was inert.
- **`list_components` returned cross-tier duplicates.** The registry deduped on `get` but not on `list`, so a name present in both tiers appeared twice, identically, with no signal which one `use_component` would resolve to. Shadowed tiers are now reported on the surviving entry instead.
- **`get_graph` now reports `pending_bookmark` and `pending_reaim`** — the name of a graph the user just started (applied to the next commit) and a navigation queued during the current turn. Both were previously invisible, so Claude could be working inside a graph the user had named without any way to know it.
- Documentation no longer hardcodes `http://localhost:5173`. The port is per-project and walks upward, so that URL was wrong for every project after the first — and the rules file shipped into user projects was telling Claude to send people to another project's surface.

- **The port walk now probes before binding, and web-chat's own clients dial `127.0.0.1` rather than `localhost`.** Both fell out of the loopback bind above: a bind to `127.0.0.1:P` does not collide with a process holding the wildcard `*:P`, so the walk began handing out ports that already had a server on them — and because every internal client resolved the *name* `localhost`, which is both `::1` and `127.0.0.1` on a dual-stack machine, requests could land on whichever daemon that resolution happened to pick. Observed in practice while upgrading: a new loopback-bound daemon took a port a legacy wildcard-bound one still held, and another project's queue started arriving.

### Added
- **Component packs — `claude-web-chat pack`, and the `＋` drawer's Manage tab.** A pack is a git repository that installs as components **plus a Claude skill**, and the skill is the whole point: `list_components` is a *pull* (Claude only learns a component exists if it decides to call the tool) while a skill's frontmatter description sits in context from session start. The format was specified and had no code behind it; this is the pipeline.

  Fetching prefers a published release carrying `SHA256SUMS` (verified before anything is unpacked) and otherwise falls back to the repository tarball **pinned to a resolved commit sha** — an asset can be deleted and re-uploaded under the same tag, a commit sha cannot, so the weaker-looking option is the stronger pin. `pack get` downloads for review without installing: the verified tree is staged where nothing in web-chat reads it, inert *by location* rather than by a flag someone has to check, and `pack review` shows the manifest, the install plan, every file, and what `SKILL.md` actually tells Claude. `approve` re-hashes the staged tree against a record **this machine** wrote, so a repository cannot commit its own pre-approval. Removal is per **unit**: a component whose recorded files all still match is removed whole, and one you have edited is kept whole — never stripped down to the files you did not touch. Every install, quarantine and removal appends to `.web-chat/packs/audit.log` with its actor.

  A **built-in component name is refused outright**, in either tier, for either actor, with no override: `seedBuiltins` only repairs a directory whose `meta.json` says `builtin`, so a pack shadowing `git-dashboard` would have won permanently. Your own same-named component is never silently replaced (`--replace` is terminal-only), and a pack's `service.js` is unapproved by construction — consent is keyed to the file's hash, so a fresh one still waits for `claude-web-chat trust`. The honest limit is written down in `docs/component-packs.md` and at the head of `lib/server/routes/packs.js`: the install endpoint is reachable by any pane script and **cannot tell a pane's `fetch` from a user's click**.
- **`gh` is used to fetch a pack when it is on your PATH and logged in.** A component library can be private, and the plain HTTPS path cannot reach one: it authenticates only if `GITHUB_TOKEN` happens to be exported, and even then a bare token does not carry the SAML/SSO authorization an organization requires — which the credential `gh` already holds does. When `gh` is available it resolves the commit, reads the release, and streams the tarball; it also lifts the anonymous 60-requests/hour/IP API limit that a couple of installs can exhaust. Without `gh`, nothing changes — the HTTPS path is untouched and remains the fallback.

  Scoped the same way `Authorization` is: **your `gh` credential is only ever spent on github.com**, or on an enterprise host you configured yourself via `GH_HOST`. A pack URL is pasted by whoever asked for the install — and on the surface that can be a pane script — so an arbitrary host never gets it. `WEB_CHAT_NO_GH=1` forces the plain path. Which transport ran is recorded in the pack's provenance and shown in `pack list` and the drawer.
- **The `＋` drawer is now the components *and* packs manager**, with Library and Manage tabs — tabs rather than stacked sections, so an install form never pushes the hot path (spawn a pane) below the fold. Rows carry chips for `built-in`, tier, `service` (and *needs approval* when one is waiting), `seed`, `form` and shadowing; a row spawns into a **stable slot** so panes stop stacking forever, with `⧉` for a second copy. Install leads with *Download for review*; *Install now* is secondary and takes a second, deliberate click for a URL that was never reviewed.
- **The surface has a first-run state.** `#main` used to be literally empty on first open — every other panel in the app has a considered empty state, and the one thing every new user sees first had none. It now says what the surface is, offers a prompt to paste, and names the four keys that matter (palette, component library, graph, push).
- **`claude-web-chat ls`** — every surface running on this machine, which project each one is, and on what port. The daemon is one-per-project and its port walks upward from 5173, so this was previously unanswerable; the registry the capture hub keeps already had it. `--reap` stops the ones that aren't the current project and clears stale entries.
- **`npm test`, and CI.** The suite had never run anywhere but a maintainer's Mac and nothing had ever verified Linux. `npm test` is now the correct entry point (the obvious `node --test test/` misresolves), and GitHub Actions runs it on Ubuntu and macOS across Node 18/20/22.
- **The connected-browser count is exposed** on `/api/health`. It was already tracked for the service supervisor and never surfaced, so Claude could render into a surface nobody had open, say "take a look", and be told it worked.
- **`install` writes `.web-chat/` into `.gitignore`.** Three docs already stated it was gitignored and nothing ever wrote the line, so a project was one `git add -A` from committing its graph, portfile and drafts. Idempotent, and it respects a rule you already wrote.

### Changed
- **Installing a skill no longer claims to need a Claude Code restart.** `docs/component-packs.md` stated that components are picked up live and skills are not. Checked against Claude Code 2.1.243: a `SKILL.md` written into `.claude/skills/<name>/` mid-session becomes available on its own within a few seconds, with no `/exit` and reopen. (A `.mcp.json` change still does need one — that really is read only at session start.)
- **The `UserPromptSubmit` hook no longer claims the render tools will fail.** It said so whenever the daemon was down — but the MCP client auto-spawns and the call succeeds, so the hook was talking Claude out of using the surface on exactly the turns that needed it, on the strength of a false claim. It now reports the thing it never checked: whether a browser is actually watching.
- `install`'s next steps lead with the ordinary path (restart Claude Code, then `claude-web-chat open`) and present Channels as the optional research preview it is.
- `status` reports the real channel state — connected, or parked-until-your-next-message — instead of inferring it from project wiring.

## [0.5.0] - 2026-08-24

Written up after the fact. 0.5.0 was cut three hours before 0.6.0, its version bump carried the distribution rewrite and touched no changelog, and the `[Unreleased]` block it shipped was relabelled `[0.6.0]` that same evening — so everything else from 0.4.0 → 0.5.0 is recorded in the 0.6.0 section below, and what follows is what 0.5.0 added on top of it. Reconstructed from the commit that bumped the version and the tree it produced.

### Added

- **Distribution became GitHub Releases, and npm stopped being involved at any point.** `install.sh` is POSIX `sh` with no npm in it: resolve the latest release, download the tarball, **verify its SHA256 before unpacking anything**, stage it and move it into `~/.web-chat/versions/<version>/`, swap the `current` symlink atomically, link the three commands into `~/.local/bin`, prune to the three newest versions. No sudo, nothing outside your home, safe to re-run, and a download that dies midway leaves the previous `current` untouched. The motivating failure: a global npm install is a shared mutable directory, so an unrelated `npm i -g` silently replaced a maintainer's `npm link` with a copy of a 16-day-old build — on PATH, invisible, while every test in the checkout stayed green.
- **`claude-web-chat version`** — the version, and *where it came from*: the install kind (a managed release, a git checkout, or an unmanaged leftover), the tree actually running, what `~/.web-chat/current` points at, and a MISMATCH block when the `claude-web-chat` on PATH resolves somewhere else. That last signal is precisely what was missing while the stale binary above went unnoticed for two weeks.
- **`update --to <version>` rolls back from disk with no network**, `update --list` names the versions that are on disk, and **`update` refuses to run from a git checkout** — or any other copy it did not install — telling you to use git instead, because overwriting a checkout with a release tarball would throw the work away.
- **`claude-web-chat uninstall --self`** removes the program itself rather than only this project's wiring, and preserves every project's graph while doing it.
- **`scripts/build-release.js` and `.github/workflows/release.yml`.** The build produces a self-contained `claude-web-chat-<version>.tar.gz` — the `files` allowlist plus *production* `node_modules`, since there are four runtime dependencies and a source-only tarball dies on `Cannot find module 'express'` — alongside `SHA256SUMS`, with every varying field pinned (mtime, uid/gid, entry order, modes) so the checksum is reproducible. On a `v*` tag CI builds it, unpacks it into a scratch `HOME`, runs the CLI out of it, and only then attaches both files to the release.

### Changed

- **`stop` asks the daemon to shut down instead of signalling it and hoping.** `POST /api/shutdown` runs the same `gracefulShutdown` the idle timer uses — drain in-flight requests, wait out a live turn lock, stop services, snapshot uncommitted surface state to `draft.json` — and acknowledges *before* exiting, since responding after the drain deadlocks the shutdown on its own request. `stop` asks, waits up to 40 s and falls back to `SIGTERM` only if the request itself fails; escalating earlier would abort the snapshot it had just asked for. `restart` calls `stop` rather than carrying a second copy of kill-and-wait. The route is closed to browsers — it refuses anything carrying browser fetch metadata and requires a custom header — so no page script can stop your daemon.
- **`update` loads the restart it is about to perform out of `versions/<target>/` explicitly.** Reaching it through `~/.web-chat/current` hands back the *old* module (Node caches by realpath, and `current` was already resolved when the bin was invoked), so every update would otherwise have restarted the code it had just replaced.
- **Windows means WSL2, said plainly in the README** rather than half-supported.

## [0.4.0] - 2026-07-18

### Added
- **Service-backed components.** A saved component can carry a host-side `service.js` that the daemon supervises while its pane is on the active node and a browser is watching, so a pane can reflect live host state between Claude's turns with no turn of Claude's involved. Trust is confirm-on-first-use, keyed by the hash of `service.js` so an edit re-prompts. Full contract in `docs/service-components.md`.
- **`git-dashboard` and `file-editor` builtins.** A live git browser (branches, commit log, per-commit drill-in with file stats) and a lightweight file editor with version history and unified diffs — both service-backed, and both canonical examples to crib from.
- **Channels v2.** Activity routing is now opt-out: every user interaction in a pane coalesces into one rolling activity item per mount, so nothing the user does is lost even when a pane's script fails at mount. Typed form values persist per mount (`form_state`) across refresh, navigation, restarts and re-renders. Editing a form while previewing an older node auto-commits dirty live state and re-aims there (branch-on-edit), so the next commit branches instead of overwriting.
- **`claude-web-chat docs`** — prints the bundled contract docs from wherever the package landed on disk, so the rules file can point at them without knowing the install path.

### Changed
- A guidance audit pass over the agent-facing rules file and the MCP tool descriptions, which are load-bearing: Claude picks tools by reading them.

## [0.3.0] - 2026-07-12

### Added
- **Channels are the wake path, and they work everywhere.** Wake-worthy activity — page captures, declared pane signals, and shared comment pins — collects in the surface's queue rail; hitting **Push → Claude** hands over the whole batch. With the Claude Code Channels capability a Push wakes Claude live and no-prompt; without it the batch is *parked* and delivered as context with your next message. Either way there are no background listeners to arm, so the loop works on every Claude Code.
- **Bundled capture profiles.** The package now ships ready-to-use capture profiles — Gmail, Wikipedia, YouTube, Reddit, and a generic reader-lite article view — as a first-class package tier, so common sites distill cleanly the moment the browser extension is loaded, with no per-user setup. User-authored profiles still override the bundled ones.
- **Public-repo distribution.** MIT-licensed and installable in one line: `curl -fsSL …/install.sh | sh` puts the `claude-web-chat` command on your PATH straight from the public repository — no npm *registry* involved, though npm itself still was: the installer, and `update` with it, ran `npm i -g git+https://…` against the repo. (0.5.0 replaced that with a checksum-verified release tarball and dropped npm entirely.) `claude-web-chat update` (now reporting the version before and after) and the 24-hour update check target the repo too. The README leads with the one-liner and documents loading the browser extension from the installed package.

### Changed
- **Review hardening.** A pass over the queue / bridge / comment-policy substrate the wake path leans on: private comment pins no longer leak their text onto the wake bus, navigating the graph no longer strands queued items, and the surrounding fixes each landed with a test.

### Removed
- The legacy Claude-facing listener surface — the `wait_for` MCP tool and the `claude-web-chat watch` CLI — in favour of the queue / Push / parked-delivery path. (The `/api/wait` endpoint remains as a driver-only contract.)
