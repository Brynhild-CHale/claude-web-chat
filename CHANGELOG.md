# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security
- **The `git-dashboard` service no longer lets a pane turn a store value into a git option.** The pane picks what to show by writing `git_ctl { viewing, open }`, and the service passed both straight into git's argv. `execFile` keeps a shell out of it and the trailing `--` separates revs from paths, but git parses any earlier argv word beginning with `-` as an option — and `git log`/`git show` accept `--output=<file>`. The store is writable by every pane script in the page and by any local process, so once a user had run `claude-web-chat trust git-dashboard` (the builtin they are pointed at as the reference service), anything on the surface could make the daemon overwrite a file the user can write — a shell rc file, a `.git` hook — with git-log text. `viewing` is now accepted only when it matches a branch name the service itself just read, `open` only when it looks like an object name (`[0-9a-f]{7,40}`), and every ref is fenced behind `--end-of-options` on git 2.24+. A refused value falls back to the checked-out branch, which is what the pane already displays, so nothing about ordinary use changes.

  **After upgrading, service-backed components ask for trust once more.** Consent is keyed to the contents of `service.js`, so this fix invalidates the existing grant: run `claude-web-chat trust git-dashboard` (or bare `claude-web-chat trust` to see everything waiting) the first time a service pane comes up empty.
- **A pack archive can no longer OOM the daemon by decompressing.** `listTarGz` — the pre-extraction gate every pack install passes through — gunzipped the whole archive into one Buffer with no ceiling. The download cap (64 MB) bounds nothing on that side: deflate compresses a run of zeros at roughly 1000:1, so a 64 MB body inflates to tens of gigabytes, and `Buffer.MAX_LENGTH` is 2^53-1, so nothing refused the allocation — the daemon holding the live graph was OOM-killed rather than throwing anything catchable. The install endpoint is reachable by any pane's `fetch`, so a rendered script (or a pasted URL) could take the process down. The inflate is now capped at 256 MB and the overflow is reported as a refusal naming the archive. The same cap bounds extraction: the listing runs before the file is handed to `tar`, and the bytes it measures are the bytes `tar` would write.

### Added
- **A stated platform position — `docs/platform-support.md`.** macOS and Linux are supported (the full suite runs on both in CI on every push); Windows is WSL2 only. The page is deliberately honest about the difference between "supported" and "bug-free": it lists the cross-platform defects that a Windows and a Linux assessment both surfaced, rather than filing them away as somebody else's platform. Per-platform findings and test plans live on the `platform/windows` and `platform/linux` branches, written so someone with real hardware can confirm or overturn each hypothesis — every claim in them is marked observed or inferred.

### Changed
- **Node 22 is now the floor** (`engines: >=22`, was `>=18`). Not a preference — a dependency of `node-html-parser`, one of the four runtime deps, moved to ESM-only at `entities@5`, and `node-html-parser@8` requires `^8.0.0` of it. `require()` of an ESM module needs `require(esm)`, which landed in Node 22 (and was backported to 20.19). Below that, `entities/dist/index.js` throws `ERR_REQUIRE_ESM` while `lib/server` is still being required — so the daemon does not start and the CLI does not run at all. Pinning `entities` backwards would hand `node-html-parser` a package with a different API; Node 18 and 20 are both past end-of-life. CI now covers 22 and 24 (24 is what releases are built and run on, and it had never been tested).

### Security
- **A component name is validated before it becomes a path, at every entry.** `GET /api/components/:name`, `GET /api/components/:name/seed` and `POST /api/components/:name/use` had no name validation at all. Express decodes `%2f` into a route parameter, so `/api/components/..%2f..%2fx/seed` arrived as the name `../../x` and was joined and `existsSync`'d unguarded: `/seed` served any `<dir>/seed.js` on disk, `/:name` any `<dir>/component.html`, and `/use` both read that file and wrote the name into `mount.component` — the string the service supervisor turns into the `service.js` path it forks. The kebab grammar is the containment rule (a name that cannot carry a separator cannot leave the components directory), and a name that fails it now answers 404. `lib/packs`'s `verifyPack` re-checks a *recorded* unit name the same way before `removeUnits` unlinks inside the directory it names; a unit that fails is reported and skipped rather than removed, so `pack remove` over a damaged record degrades instead of deleting elsewhere.

### Fixed
- **Re-using a service pane's id with different params now restarts — and re-gates — the child.** The supervisor decided whether a running service was still the right one by its `service.js` hash alone, but params are the other half of what a service *does* and of what you approved: `file-editor`'s `unfenced:true` is exactly what lifts its writes out of the project root. Using a component again on an existing mount id replaces the mount in place, so the old child kept running with the old params — the pane's scope chip still reporting the old root, the requested change silently not applied — and the new shape was trust-checked only when something unrelated (a viewer leaving, a navigation) happened to restart it, at which point the pane went dark waiting for a `claude-web-chat trust` nobody had been asked for. Identity is now the pair, matching the trust key. Two bookkeeping leaks went with it: a pending trust request is retired when its pane is cleared (it was listed by `claude-web-chat trust` and re-announced to every arriving browser forever), and a crash block is dropped with its pane rather than keeping a reusable mount id blocked. Neither is retired merely because no browser is watching — a refresh must not swallow a request you are walking to the terminal to approve.
- **A service that never finished shutting down could not be killed.** The supervisor's documented fallback — IPC `stop`, then `SIGTERM` two seconds later — was answered in the child by a handler that returned immediately once a shutdown was already in flight. So a `stop()` that never resolves (an awaited stream close that never fires is the ordinary way to write one by accident) swallowed the IPC stop, ignored the SIGTERM, ignored the later disconnect, and lived on holding whatever timers, watchers or sockets it had failed to clear; there is no `SIGKILL` escalation above it. A second signal is decisive now: the child exits outright rather than waiting on the stop it is already stuck in. Cleanup that matters belongs inside the grace period — `docs/service-components.md` now says so rather than promising more than the fallback delivered.
- **A restarted service pane could leave a second copy of the service running.** The supervisor tracked each service child by mount id and bound its `exit` handler to that id alone — but a reconcile stops and respawns a mount in one synchronous pass, so the old child's exit arrived *after* its replacement was already registered under the same id. The exit was then read as the replacement crashing: the running child was dropped from tracking (and its version recorded as failed), which meant nothing ever stopped it — not clearing the pane, not the last viewer leaving, not navigating away, not daemon shutdown — and the next reconcile forked a third process writing the same store keys. The handler is bound to the child's own entry now and ignores an exit for a child that has already been superseded, the same identity check the `started` message has always made.
- **A pane could delete or hijack the surface's own chrome by naming it.** A mount id and a render target are both agent-supplied strings that nothing validated, and the client resolved them against the whole document: `render({ id: 'main' })` removed `<main>` and appended the pane to the detached element, `id: 'status'` deleted the connection pill, `id: 'overlay'` deleted the graph viewer, and `target: 'topbar'` filed a pane inside the header (the same class of mistake that shipped the 0.6.0 service-trust prompt inside the hidden graph viewer). Because the mount persists in `state.mounts` and in every committed node, the removal replayed on every reload and every later mount then threw on a null slot — the surface stayed dead until the mount was cleared from outside the browser. The client now only ever removes an element that is a mount host, and resolves a target against the list of real slots instead of by id. A pane host also no longer claims a DOM id that the chrome already owns — it carries the mount id in its dataset and mirrors it onto the element only when it is free — because the shell resolves its own chrome *live* (`document.getElementById` on every minbar reconcile, drawer open, queue-rail update): a pane named `minbar` or `drawer` used to win those lookups instead, and won them again after every reload. A comment pin resolves its anchor through that same mount-id lookup rather than by DOM id, so a pin placed on a chrome-named pane still draws instead of being silently dropped from the marker layer. Rejecting such an id outright is the server's job and comes with the mount-set engine; this is the client half, which is what stops a name bricking the surface.
- **One bad pane no longer reads as a dead surface.** The `hello` frame mounted its panes in a bare loop, so if any one of them threw, the whole handler unwound: the remaining panes never mounted and the rest of the frame — the topbar's active pill, the queue rail, the version check — never ran. Each mount is isolated now; a failure is logged and the frame carries on — and the failed mount is unwound rather than left half-built, so a later render of the same id replaces one pane instead of stacking a second beside an empty one.
- **Re-running `install.sh` upgraded nothing.** The `current` symlink was swapped with `mv -f current.incoming current`, and `mv` stat()s its destination: a `current` pointing at a version directory looks like a directory to it, so the new link was moved *inside* the old version (`versions/0.5.0/current.incoming`) instead of over it. A first install was fine; every upgrade through the curl one-liner after that unpacked the new release, printed `Installed claude-web-chat v<new>`, and left `current` — and all three commands in `~/.local/bin`, which resolve through it — running the old code. `claude-web-chat update` was never affected (its Node swap uses `rename(2)` correctly). The swap is now `ln -sfn`, and the installer is executed twice against a scratch HOME in the test suite, which is the case CI had never covered.
- **`save_component` over a builtin name permanently broke that builtin.** `POST /api/components` — what the `save_component` tool and any pane script's `fetch` hit — checked that a name was kebab-case and nothing else, and `componentsRegistry.write` then wrote a `meta.json` with no `builtin` marker. That marker is the only thing `seedBuiltins` repairs on, so a single `save_component({name: 'git-dashboard', …})` replaced the builtin with something that could never be refreshed: every later fix to `git-dashboard` or `file-editor` silently failed to land, and the pane was left pairing foreign HTML with the real `service.js`. The packs pipeline had always refused these names; the ordinary save path never did. The kebab grammar and the reserved list now live together in `lib/core/names.js` and are asserted at every writer — the save route (400 for a malformed name, 200 `{ok:false, reserved:true, hint}` for a reserved one, the shape the drawer and the tool already read), the registry write, `validateManifest` and `planInstall`. `save_component`'s description says so, so Claude does not try.

  Two consequences worth knowing about. The refusal is **prospective**: a project where this already happened keeps the shadowed component, and can no longer overwrite it back through the same route — `seedBuiltins` now names any such directory on stderr at boot, with the path to delete to get the builtin back, but it still will not touch it, because your edits are in there. And a component directory whose name is **not** plain kebab-case (hand-made, or created before the save route checked) stops resolving through the read routes rather than resolving by luck.
- **`claude-web-chat open` died with a raw stack when there was no browser launcher.** `launchBrowser` wrapped `spawn()` in a `try`/`catch`, but a missing executable is reported asynchronously as an `'error'` event, not a throw — so the catch was dead code and no listener was attached. On any Linux server, WSL, slim container or desktop without `xdg-utils`, `open` printed "server started at http://localhost:5173" and then took an unhandled error, exiting 1 with the URL scrolled off above the trace: the "open this URL manually" fallback it was carrying all along was unreachable, and the failure read as a broken install. `launch` awaits `open()`, so it went down too. The listener is attached before `unref()` now; the `try`/`catch` stays for the synchronous `EACCES` case.
- **A departing daemon could tear down the live one's portfile.** `deletePortfileFile` unlinked `.web-chat/server.json` unconditionally, with no check that the record it removed was the caller's. `server.json` is the only thing that maps a project to a running daemon — the CLI, the browser and the MCP tools all resolve through it — so if two daemons ever shared a root (the unguarded `install` spawn that 0.6.0 closed was one way in; a concurrent spawn slipping past `spawnDaemon`'s probe is another), whichever exited first deleted the survivor's record. The result is the worst kind of running server: `status` says "not running", `doctor` reports no problems, `stop` has nothing to stop, and the daemon keeps serving and keeps writing the graph. Deletes now carry the pid the caller believes owns the file — the daemon passes its own, `ls --reap` passes the pid it listed and signalled, `doctor` passes `null` for "reap only if the process it names is gone" — and a record held by a different, still-live process is left alone. Unowned or unparseable records are still removed.

- **Turns that changed nothing no longer clutter a graph written before they stopped committing.** Fold-forward stopped a no-change turn from committing a node, but it could only ever help going forward — every graph already in use kept its existing run of byte-identical nodes, one per chat-only turn, which is exactly what makes an old graph unnavigable. (One real project here: 744 nodes, 554 of them indistinguishable from their parent.) The graph payload now reports, at read time, which nodes are identical to their parent (`collapsed`), which surviving node stands for each run (`absorbed`/`absorbed_count`), and which edge to draw (`display_parent`); the viewer hides them, attributes their triggers to the node that absorbed them, and offers a chip to show them anyway. Nothing on disk is touched — node files stay append-only and `parent_id` stays the truth — so this is reversible by turning the chip on, and the same graph read by an older build is unchanged. A node is only ever hidden when hiding it costs nothing: never a root, a fork, a tip, the active node, or one that is bookmarked or named.


## [0.6.0] - 2026-08-24

### Security
- **`Authorization` is now dropped on a cross-host redirect.** A GitHub release asset URL redirects to object storage on a different host, and the redirect follower carried every header across that hop. Latent while nothing minted a token — but `GITHUB_TOKEN` has to be honoured (unauthenticated `api.github.com` is 60 requests/hour/IP, and a pack install makes several), which would have turned it into a live credential handed to whoever answered at the far end. A token is also only ever minted for a `github.com` host now, never for a URL the user pasted.
- **The daemon and the capture hub now bind loopback.** Both called `listen(port)` with no host, so everything web-chat serves — the graph, the shared store (which holds whatever a `file-editor` pane has open), arbitrary HTML/JS injection through `POST /api/render`, and `POST /api/update` — was reachable from the local network with no authentication. Set `WEB_CHAT_HOST` to opt into a different interface deliberately.
- **The WebSocket endpoint now checks `Origin`.** Browsers apply no same-origin policy to WebSocket connects and the `hello` frame is an unconditional full-state disclosure, so any page a user visited could open `ws://localhost:<port>/ws`, read the entire store and every pane's HTML, and write store keys back. Non-browser clients (local drivers, the CLI) send no `Origin` and are unaffected.
- **Service consent records moved to the user tier** (`~/.web-chat/services/trusted.json`). They used to live at `.web-chat/services/trusted.json` *inside the project*, so a repository could ship its own pre-approval: cloning a hostile repo and opening it ran its `service.js` with no prompt.
- **Service consent moved to the terminal — `claude-web-chat trust`.** It used to be a decision made on the surface, which cannot work: pane scripts are compiled with `new Function` and run in the page's own window realm with `document`, `fetch` and `WebSocket`, and no CSP is served, so a component's pane can synthesise a click on any button, open its own same-origin socket and read anything broadcast to the shell, and call any localhost endpoint. Nothing delivered to that page is a secret from the code the gate exists to gate. The surface now shows a notice naming the command; only a shell can grant. Consent is also keyed per **(project root, `service.js` hash, params shape)**, so the same component in another project, an edited service, or different params each ask again — which is what stops one `file-editor` approval covering `unfenced: true`, or a cloned repo inheriting a grant.
- **Capture reads are no longer world-readable.** The CORS layer reflected whatever `Origin` arrived, so any website the user visited could read every capture — distilled content and raw DOM — from the unauthenticated `GET /api/captures*` routes. Only extension and same-machine origins are reflected now.

### Fixed
- **The surface's first paint died on Node 18 and 20.** `public/app/mounts.js` read `navigator.platform` unguarded to pick `⌘` vs `Ctrl` for the zero-state's keyboard hints, and `globalThis.navigator` only exists from Node 21 — so on the versions `package.json` actually claims to support, the `ReferenceError` escaped the `hello` WebSocket handler and took the whole initial render with it. Found by CI's first-ever run: the suite had only ever run on a maintainer's Mac, on a newer Node than any supported floor.
- **The `＋` button never closed the drawer.** Every other chrome trigger declares `aria-controls`, which is what opts it into the dismiss layer's skip-the-panel-I-own rule; `＋` declared none, so `pointerdown` closed the drawer and the button's own click immediately reopened it. It also expressed openness with `.open` while every other panel uses `.hidden`, which is why the dismiss layer carried two special cases for it.
- **A component saved mid-session was invisible in the ⌘K palette until a reload.** The palette memoised its own component list and nothing ever invalidated it. There is now one cache, invalidated by a `components` frame the daemon emits wherever the component set can move — so a `save_component`, or a whole pack install, shows up everywhere at once.
- **A component whose `meta.json` name disagreed with its directory was listed but unspawnable.** The registry listed by `meta.json`'s `name` and resolved by directory, so such a component appeared in the drawer and the palette under a name `use_component` could not resolve. The directory name is the identity now; the disagreement is shown as a chip instead of silently preferred.
- **A soft rejection from `use_component` looked exactly like success.** The drawer discarded the response, so spawning into a locked or driver-owned pane simply appeared to do nothing.
- **Service-backed components could never be approved at all.** The trust prompt was emitted as a render targeting `overlay`, which the client resolves to the graph-viewer element — `display:none` until the user presses `G`. The prompt was filed inside a hidden panel, so both shipped builtins (`git-dashboard`, `file-editor`) and every user-authored service simply never started, with no prompt and no error. Approval is now a terminal command (see Security above), and the surface's notice is re-announced to every arriving viewer so a refresh mid-prompt no longer leaves a pane sitting there unexplained.
- **`claude-web-chat docs` crashed on every installed copy.** `docs/` was missing from the package `files` allowlist, so the three pointers the shipped rules file gives Claude all died with a raw `ENOENT` stack. The directory now ships, and a future packaging slip degrades to a message instead of a crash.
- **A single truncated node file could wedge a project's daemon permanently.** `graph.load()` parsed every node through a bare `JSON.parse`, so one partial write — a crash or a full disk — threw out of the unguarded `createServer` call path and the daemon could never boot again for that project. Unreadable nodes are now skipped with a warning.
- **Re-running `install` started a second daemon on the same project** and overwrote the portfile, orphaning the first — which kept running and kept writing the same graph directory, invisible to `stop`, `status` and `doctor`. It now probes for a live instance first, matching every other spawn site.
- **A Push could report "Delivered to Claude ✓" and be silently dropped.** Two causes, both fixed: `install` pinned `WEB_CHAT_CHANNEL=1` into `.mcp.json`, which made the MCP server start a channel bridge in *every* session including ones launched without the capability flag; and the bridge's ack confirmed only that bytes were written to stdout, not that anything received them. The env now comes solely from the launch line that also carries the flag, `install`/`update`/`doctor` clean a stale one, and an ack with no live consumer leaves the batch retained so the parked-delivery backstop still fires.
- **The launch command web-chat printed could not work.** `LAUNCH_COMMAND` omitted the `server:web-chat` argument the flag requires, so the incantation shown by `install`, the queue rail and `doctor` was inert.
- **`list_components` returned cross-tier duplicates.** The registry deduped on `get` but not on `list`, so a name present in both tiers appeared twice, identically, with no signal which one `use_component` would resolve to. Shadowed tiers are now reported on the surviving entry instead.
- **`get_graph` now reports `pending_bookmark` and `pending_reaim`** — the name of a graph the user just started (applied to the next commit) and a navigation queued during the current turn. Both were previously invisible, so Claude could be working inside a graph the user had named without any way to know it.
- Documentation no longer hardcodes `http://localhost:5173`. The port is per-project and walks upward, so that URL was wrong for every project after the first — and the rules file shipped into user projects was telling Claude to send people to another project's surface.

- **The port walk now probes before binding, and web-chat's own clients dial `127.0.0.1` rather than `localhost`.** Both fell out of the loopback bind above: a bind to `127.0.0.1:P` does not collide with a process holding the wildcard `*:P`, so the walk began handing out ports that already had a server on them — and because every internal client resolved the *name* `localhost`, which is both `::1` and `127.0.0.1` on a dual-stack machine, requests could land on whichever daemon that resolution happened to pick. Observed in practice while upgrading: a new loopback-bound daemon took a port a legacy wildcard-bound one still held, and another project's queue started arriving.

### Added
- **Component packs — `claude-web-chat pack`, and the `＋` drawer's Manage tab.** A pack is a git repository that installs as components **plus a Claude skill**, and the skill is the whole point: `list_components` is a *pull* (Claude only learns a component exists if it decides to call the tool) while a skill's frontmatter description sits in context from session start. The format was specified and had no code behind it; this is the pipeline.

  Fetching prefers a published release carrying `SHA256SUMS` (verified before anything is unpacked) and otherwise falls back to the repository tarball **pinned to a resolved commit sha** — an asset can be deleted and re-uploaded under the same tag, a commit sha cannot, so the weaker-looking option is the stronger pin. `pack get` downloads for review without installing: the verified tree is staged where nothing in web-chat reads it, inert *by location* rather than by a flag someone has to check, and `pack review` shows the manifest, the install plan, every file, and what `SKILL.md` actually tells Claude. `approve` re-hashes the staged tree against a record **this machine** wrote, so a repository cannot commit its own pre-approval. Removal is per **unit**: a component whose recorded files all still match is removed whole, and one you have edited is kept whole — never stripped down to the files you did not touch. Every install, quarantine and removal appends to `.web-chat/packs/audit.log` with its actor.

  A **built-in component name is refused outright**, in either tier, for either actor, with no override: `seedBuiltins` only repairs a directory whose `meta.json` says `builtin`, so a pack shadowing `git-dashboard` would have won permanently. Your own same-named component is never silently replaced (`--replace` is terminal-only), and a pack's `service.js` is unapproved by construction — consent is keyed to the file's hash, so a fresh one still waits for `claude-web-chat trust`. The honest limit is written down in `docs/component-packs.md` and at the head of `lib/server/routes/packs.js`: the install endpoint is reachable by any pane script and **cannot tell a pane's `fetch` from a user's click**.
- **`gh` is used to fetch a pack when it is on your PATH and logged in.** A component library can be private, and the plain HTTPS path cannot reach one: it authenticates only if `GITHUB_TOKEN` happens to be exported, and even then a bare token does not carry the SAML/SSO authorization an organization requires — which the credential `gh` already holds does. When `gh` is available it resolves the commit, reads the release, and streams the tarball; it also lifts the anonymous 60-requests/hour/IP API limit that a couple of installs can exhaust. Without `gh`, nothing changes — the HTTPS path is untouched and remains the fallback.

  Scoped the same way `Authorization` is: **your `gh` credential is only ever spent on github.com**, or on an enterprise host you configured yourself via `GH_HOST`. A pack URL is pasted by whoever asked for the install — and on the surface that can be a pane script — so an arbitrary host never gets it. `WEB_CHAT_NO_GH=1` forces the plain path. Which transport ran is recorded in the pack's provenance and shown in `pack list` and the drawer.
- **The `＋` drawer is now the components *and* packs manager**, with Library and Manage tabs — tabs rather than stacked sections, so an install form never pushes the hot path (spawn a pane) below the fold. Rows carry chips for `built-in`, tier, `service` (and *needs approval* when one is waiting), `seed`, `form` and shadowing; a row spawns into a **stable slot** so panes stop stacking forever, with `⧉` for a second copy. Install leads with *Download for review*; *Install now* is secondary and takes a second, deliberate click for a URL that was never reviewed.
- **The surface has a first-run state.** `#main` used to be literally empty on first open — every other panel in the app has a considered empty state, and the one thing every new user sees first had none. It now says what the surface is, offers a prompt to paste, and names the four keys that matter (palette, component library, graph, push).
- **`claude-web-chat ls`** — every surface running on this machine, which project each one is, and on what port. The daemon is one-per-project and its port walks upward from 5173, so this was previously unanswerable; the registry the capture hub keeps already had it. `--reap` stops the ones that aren't the current project and clears stale entries.
- **`npm test`, and CI.** The suite had never run anywhere but a maintainer's Mac and nothing had ever verified Linux. `npm test` is now the correct entry point (the obvious `node --test test/` misresolves), and GitHub Actions runs it on Ubuntu and macOS across Node 18/20/22.
- **The connected-browser count is exposed** on `/api/health`. It was already tracked for the service supervisor and never surfaced, so Claude could render into a surface nobody had open, say "take a look", and be told it worked.
- **`install` writes `.web-chat/` into `.gitignore`.** Three docs already stated it was gitignored and nothing ever wrote the line, so a project was one `git add -A` from committing its graph, portfile and drafts. Idempotent, and it respects a rule you already wrote.

### Changed
- **Installing a skill no longer claims to need a Claude Code restart.** `docs/component-packs.md` stated that components are picked up live and skills are not. Checked against Claude Code 2.1.243: a `SKILL.md` written into `.claude/skills/<name>/` mid-session becomes available on its own within a few seconds, with no `/exit` and reopen. (A `.mcp.json` change still does need one — that really is read only at session start.)
- **The `UserPromptSubmit` hook no longer claims the render tools will fail.** It said so whenever the daemon was down — but the MCP client auto-spawns and the call succeeds, so the hook was talking Claude out of using the surface on exactly the turns that needed it, on the strength of a false claim. It now reports the thing it never checked: whether a browser is actually watching.
- `install`'s next steps lead with the ordinary path (restart Claude Code, then `claude-web-chat open`) and present Channels as the optional research preview it is.
- `status` reports the real channel state — connected, or parked-until-your-next-message — instead of inferring it from project wiring.
- Server tests sandbox `HOME`, so the suite no longer writes the developer's real `~/.web-chat`.

## [0.4.0] - 2026-07-18

### Added
- **Service-backed components.** A saved component can carry a host-side `service.js` that the daemon supervises while its pane is on the active node and a browser is watching, so a pane can reflect live host state between Claude's turns with no turn of Claude's involved. Trust is confirm-on-first-use, keyed by the hash of `service.js` so an edit re-prompts. Full contract in `docs/service-components.md`.
- **`git-dashboard` and `file-editor` builtins.** A live git browser (branches, commit log, per-commit drill-in with file stats) and a lightweight file editor with version history and unified diffs — both service-backed, and both canonical examples to crib from.
- **Channels v2.** Activity routing is now opt-out: every user interaction in a pane coalesces into one rolling activity item per mount, so nothing the user does is lost even when a pane's script fails at mount. Typed form values persist per mount (`form_state`) across refresh, navigation, restarts and re-renders. Editing a form while previewing an older node auto-commits dirty live state and re-aims there (branch-on-edit), so the next commit branches instead of overwriting.
- **`claude-web-chat docs`** — prints the bundled contract docs from wherever the package landed on disk, so the rules file can point at them without knowing the install path.

### Changed
- A guidance audit pass over the agent-facing rules file and the MCP tool descriptions, which are load-bearing: Claude picks tools by reading them.

## [0.3.0] - 2026-07-12

### Added
- **Channels are the wake path, and they work everywhere.** Wake-worthy activity — page captures, declared pane signals, and shared comment pins — collects in the surface's queue rail; hitting **Push → Claude** hands over the whole batch. With the Claude Code Channels capability a Push wakes Claude live and no-prompt; without it the batch is *parked* and delivered as context with your next message. Either way there are no background listeners to arm, so the loop works on every Claude Code.
- **Bundled capture profiles.** The package now ships ready-to-use capture profiles — Gmail, Wikipedia, YouTube, Reddit, and a generic reader-lite article view — as a first-class package tier, so common sites distill cleanly the moment the browser extension is loaded, with no per-user setup. User-authored profiles still override the bundled ones.
- **Public-repo distribution.** MIT-licensed and installable in one line: `curl -fsSL …/install.sh | sh` puts the `claude-web-chat` command on your PATH straight from the public repository — no npm registry. `claude-web-chat update` (now reporting the version before and after) and the 24-hour update check target the repo too. The README leads with the one-liner and documents loading the browser extension from the installed package.

### Changed
- **Review hardening.** A pass over the queue / bridge / comment-policy substrate the wake path leans on: private comment pins no longer leak their text onto the wake bus, navigating the graph no longer strands queued items, and the surrounding fixes each landed with a test.

### Removed
- The legacy Claude-facing listener surface — the `wait_for` MCP tool and the `claude-web-chat watch` CLI — in favour of the queue / Push / parked-delivery path. (The `/api/wait` endpoint remains as a driver-only contract.)

## [0.2.0] - 2026-06-19

### Added
- **Page export.** Export any graph node to a self-contained, interactive `.html` (every pane's HTML/JS + store snapshot + resolved theme inlined; opens with no server or network). Three surfaces over one server-side assembler (`lib/server/export.js`): the topbar **⬇** Download button (exports the node currently viewed, as rendered), the `export` MCP tool, and `claude-web-chat export [node]`. Files land in `.web-chat/exports/`. Refs accept a label (`n1.7`), a stored id, `active` (default), or `live`.
- **Managed-file propagation.** `update`/`install` now reconcile the per-project managed templates (`.claude/rules/web-chat.md`, `.claude/commands/web-chat.md`) with an edit-preserving 3-way merge instead of skip-if-exists: safe template updates auto-apply, local edits are kept, conflicts surface as `<file>.new` sidecars. Baselines tracked in `.web-chat/managed.json`; drift surfaced in `status` and a once-per-session MCP-startup nudge.
