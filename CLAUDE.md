# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`claude-web-chat` is the **package that implements** the web-chat surface — not a project that uses it. It gives Claude Code a live browser canvas (a per-project port, walking upward from 5173) plus a turn-by-turn graph: Claude renders interactive HTML/JS into shadow-rooted mounts, reads/writes a shared key/value store the page is bound to, and every Claude turn becomes a navigable graph node the user can branch or revisit.

Note: `.claude/rules/web-chat.md` in this repo is the **end-user-facing rules file** (this dogfooding install of the product), describing the 24 MCP tools and how to use the surface. It is product behavior, not guidance for developing the package. When working on the package source, the architecture below is what matters.

## Commands

```sh
npm install               # dev setup; run the CLI in place: node bin/claude-web-chat.js <cmd>
npm test                  # run the full test suite (Node built-in runner, test/*.test.js)
node --test --test-timeout=60000 test/root.test.js   # run a single test file
WEB_CHAT_E2E_CHROME=1 WEB_CHAT_E2E_FFMPEG=1 npm test   # also run the real-Chrome/ffmpeg e2e tests (opt-in; skipped otherwise, CI never sets them)
node scripts/build-release.js   # build the release tarball + SHA256SUMS into dist/
```

> ⚠️ Do **not** `npm link` this package. npm's global prefix is shared mutable
> state — an unrelated `npm i -g` silently replaced that link with a 16-day-old
> copied build once already. See `docs/extending.md` for how to put a checkout on
> PATH deliberately; `claude-web-chat version` always reports which tree is running.

There is no build step (plain CommonJS) and no lint config. `npm start` / `node bin/claude-web-chat.js start` runs the server in the foreground; `claude-web-chat` is the user-facing CLI (`open`, `stop`, `restart`, `unlock`, `install`, `on`/`off`, `status`, `update`, `tunnel`).

> ⚠️ Run tests with `npm test` — `node --test --test-timeout=60000 --import ./test-support/sandbox.js` (auto-discovers
> `test/`). `node --test test/` mis-resolves and reports a spurious single failure. The
> timeout is load-bearing: without it one leaked handle or never-settling await hangs the
> whole run indefinitely. Do **not** add `--test-force-exit` — it turns a hang into a
> silent pass. `npm test` also passes `--import ./test-support/sandbox.js`, which points
> HOME at a throwaway dir before any require, so a test that spawns a subprocess (which
> inherits `process.env`) cannot reach the developer's real `~/.web-chat`.

## Architecture

**Three entry points, one server.** The three bin shims each load a different `lib/` subsystem:

- `bin/claude-web-chat.js` → `lib/cli` — the user-facing CLI.
- `bin/claude-web-chat-mcp.js` → `lib/mcp` — the stdio MCP server Claude Code spawns (registered with Claude Code at local scope by `install`, `init` and `doctor`; `.mcp.json` only when `claude` cannot be found).
- `bin/claude-web-chat-hook.js` → `lib/hooks` — the Claude Code hook dispatcher: `turn-begin` / `turn-end` (the turn lifecycle), `mirror` (the chat mirror's events) and `ask` (permission prompts); the `halt` handlers are a POSIX `sh` script beside it, never Node.

**`lib/server/` is the single source of truth.** It's an Express + `ws` HTTP/WebSocket server (`createServer({root, port})` in `index.js`). All live state lives here: `state.js` holds mounts/store/events; `graph.js` loads/saves/restores the turn graph; routes under `routes/` expose one HTTP endpoint group per concern — one file each, and the `mountXRoutes(app, ctx)` calls in `index.js` are the authoritative list of them. Each route file exports `mountX(app, ctx)` where `ctx = { state, bus, graph, paths, root, broadcastReset, retain, release, sseClients, services, getViewers, getMcpSeen, triggerShutdown, hooks, redactor, audience, mirror, turnGuard }`; a route announces a change through `ctx.bus.emit` (never a hand-paired broadcast + event push), and `broadcastReset` is the one full-state WS snapshot that stays outside the ring.

**MCP tools and hooks are thin HTTP clients to that server.** `lib/mcp/tools/<name>.js` (24 of them, listed in `lib/mcp/index.js`) go through `lib/mcp/client.js`, which discovers the running daemon's port from the `.web-chat/server.json` portfile (or `WEB_CHAT_PORT`) and auto-spawns the daemon if it isn't running. The turn hooks use that client too, but pass `noSpawn` and their own root, and the `mirror` and `ask` hooks post through `lib/client` with `noSpawn`, so no hook ever starts a daemon. So the MCP layer holds no state — it translates tool calls into HTTP requests. Each tool module exports `{ name, description, inputSchema, async handler(args) }`; tool descriptions are load-bearing (Claude reads them to choose tools).

**Turn lifecycle / the lock.** A user prompt fires the `UserPromptSubmit` hook (`turn-begin`), which acquires a graph lock pinning the commit point; a channel wake acquires one too (`turn-begin-on-push`: `emitWake` → `acquireWakeLock`, author `'wake'`, short TTL — a typed prompt mid-wake-turn upgrades it in place). Claude's `render`/`set_store`/`clear`/`use_component` calls mutate live server state during the turn. The `Stop` hook (`turn-end`, which `StopFailure` also runs when a turn ends on an API error) releases the lock and commits all of it as one new graph node — but only if the surface actually changed: a turn that leaves the surface byte-identical to the active node commits nothing, accumulates its trigger on `graph.pendingFolded`, and rides forward as `folded[]`/`folded_count` on the next node that does commit (`skipTurn`/`applyFolded` in `lib/server/domain/turns.js`; `/api/graph` reports the waiting total as `pending_folded`). A user re-aim during a locked turn is never 409'd — it queues as `graph.pendingReaim` (last wins) and applies after the turn-end commit or on unlock. Claude never commits nodes or moves `active` — the harness and the user do. A previewed older node is **read-only** in the chrome (edits are refused with a hint); the user moves `active` on the graph screen (`POST /api/graph/active` — Set active / ⑃ Branch), which first auto-commits any dirty live state as a `user`-authored preserve node, so the move never discards work and the next commit branches from the new active (`liveIsDirty` in `lib/server/domain/turns.js`). The lock records the Claude Code session holding it (`session_id`, `claude_pid`, `prompt_id`): a second prompt from the same session (equal session id, or equal pid across a `/clear`) JOINS the held turn — a message absorbed mid-turn — unless the turn guard has evidence the held turn ended, in which case turn-begin ends it as `interrupted` first; a background task's completion is its own turn (author `task`, a 3-minute TTL) and joins a held one; another session's prompt is still 409'd, and another session's Stop folds onto the next commit instead of committing the held turn. The turn guard (`lib/server/turn-guard`, `ctx.turnGuard`) ends a turn Claude Code never Stops — the mirror's `turn-closed {by:'status'}` (an Esc) with no Stop within 5 s, SessionEnd or a dead process, an unanswered wake — through the graph routes' own `endTurn`, and the Stop that arrives late for a turn it ended is reconciled onto that node, not committed. Node triggers carry `ended` (`stop`/`failed`/`interrupted`/`session-ended`), `ended_by` (`terminal`/`web`/`hook`) and `error`; every text the graph keeps (the lock's message, a trigger's message/summary/reply/error, folded entries) passes `graph.redactText` (the redactor). A stale/orphaned lock is cleared with `claude-web-chat unlock`. On graceful shutdown the server snapshots uncommitted live state to `draft.json` and restores it on next boot.

**Hooks — twelve events, one template.** `templates/settings.hooks.json` lists every web-chat hook handler, by Claude Code event. `lib/update/managed-files` `hookTemplate()` is the one reader of the file (`mergeHooks` merges from it), and `lib/setup/registration` names its events, handlers and roles from that reader (`hookEvents()`, `hookHandlers()`, and `HOOK_ROLES` for what each handler is for). `turn-begin` (UserPromptSubmit) and `turn-end` (Stop, StopFailure) run the lifecycle above, and the turn routes also put those three events on the hook tap. `mirror` (SessionStart, SessionEnd, PreToolUse, PostToolUse, PostToolUseFailure, SubagentStop, PreCompact; async except SessionEnd) builds envelope v1 (`lib/hooks/envelope.js`, bounded in the hook) and posts it to the host-only intake `POST /api/hooks/event`, which publishes it on the hook tap (`ctx.hooks`) the chat mirror reads. `ask` (PermissionRequest) only reports there for now; the prompt is still answered in the terminal. The three `halt` handlers (PreToolUse, PostToolUse, PostToolBatch) run `lib/hooks/claude-web-chat-hook-halt.sh`, which prints nothing unless a "stop after this step" flag (`~/.web-chat/halt/<session id>`) is set — and nothing writes one yet, so they are inert. Every hook exits 0 whatever happens, and arrival order is not event order (async hooks race), so nothing downstream may depend on it. `install`, `update` and `doctor` repair a handler that is missing, bare or stale (`applyHooks`).

**Toggle policy — three scopes, most-restrictive-wins** (`lib/toggle/`): user (`~/.web-chat/disabled`), project (`${cwd}/.web-chat/`), session. The MCP server enforces only user+project because Claude Code doesn't pass `session_id` to MCP subprocesses; session scope only affects hooks. When disabled, hooks no-op and MCP tools return `{ disabled, scope, reason, hint }` — `reason` is `'not-installed'` or `'marker'`, because the project scope conflates "no `.web-chat/`" with "disabled" (right for the hooks, wrong as an instruction: the hint names `init` for the first and `on` for the second).

**State migrations** (`lib/update/migrations/`) run on every server boot for any project below `SCHEMA_VERSION`. They edit files in `.web-chat/` and must be idempotent and append-only — never rewrite graph history.

**Per-project runtime state** lives in `${cwd}/.web-chat/` (graph nodes, saved components, `_version.json`, portfile, draft) — gitignored. Per-user state in `~/.web-chat/` (disable markers, update-check throttle).

**Use the engines — don't bolt on.** Each concept is consolidated behind one module; extend it, never hand-roll a second copy (a second copy is a review-blocking defect, and `test/conventions.test.js` fails the build for the most-copied constructs — the tripwire table in `docs/extending.md` lists every one and its allowed home). Full guide + rationale: `docs/extending.md`.

| wait on a condition in a test | `test-support/helpers` (`waitUntil`) | a private `waitFor`/`until` loop |
| open an SSE stream in a test | `test-support/helpers` (`openSSE`) | `subscribeSSE` with only `onOpen` — it can never reject |
| pin a socket open with a deaf WS client in a test | `test-support/helpers` (`deafWs`) | a hand-written `Sec-WebSocket-Key:` upgrade over `net.connect` |
| boot the real chrome (public/index.html + main.js) in jsdom in a test | `test-support/chrome-shell` (`bootShell({routes, onSocket, init})`, once per file, in a before() hook) | a hand-rolled JSDOM of index.html (the harness ratchet keeps that list shrinking) |
| give a test a fake Claude Code tier (transcripts, sessions files, MCP presence rows) | `test-support/claude-home` (`claudeHome(t, {root, isolate})`) | a fixture copied from a real `~/.claude` (it holds real prompts and secrets) |
| build a synthetic transcript (or a rewind in one) in a test | `test-support/claude-records` (`createRecords`) · `test-support/rewind-fixtures` (`branch`/`reset`/…, each with its hooks and expected verdict) | a record shape written by hand, or one copied from a real transcript |
| assert what the code contains (tool set, doc set, routes, CLI commands) in a test | `test-support/doc-truth` (`mcpTools`/`docFiles`/`routePaths`/`cliCommands`) | a literal count, or a hand-written list of docs to check |

Dependency direction is one-way: `core` ← `client` ← everything else, `core` imports nothing else from `lib/`, and entry points never reach into each other's internals — **`test/dependency-direction.test.js` enforces all three**, with a named baseline for the edges that legitimately remain — it grows only by a reviewed, reasoned entry, a vanished edge fails as stale, and a target reached across entry points is pinned to what it may itself require (the portal picker → `lib/server/theme.js` edge: `fs`, `lib/core/*`, `./theme-packs` only). Every concept is consolidated behind one engine (paths, portfiles, durable JSON records, the daemon HTTP client, the change bus — whose second and third instances are the hook tap and the mirror bus — the mount runtime, the tiered resource registry, the turn lock, the service supervisor, the file watch, the redactor, the audience gate) — extend the engine, never add a parallel mechanism. Full concept→engine map: `docs/extending.md`.

- **New MCP tool**: add `lib/mcp/tools/<name>.js`, append to the `tools` array in `lib/mcp/index.js`, add any backing route under `lib/server/routes/`, then `/exit` and reopen Claude Code (the MCP subprocess loads code at session start).
- **New CLI subcommand**: add `lib/cli/commands/<name>.js`, register in the `commands` map in `lib/cli/index.js`, update `showHelp()`.
- **New HTTP route**: add `lib/server/routes/<concern>.js` exporting `mountX(app, ctx)`, mount it from `lib/server/index.js`.
- **New migration**: add `lib/update/migrations/v<N>-to-v<N+1>.js`, register in the `migrations` map, bump `SCHEMA_VERSION`.
- **Component packs** (`lib/packs/`): a pack is a repo that installs as components **plus a `.claude/skills/<pack>/SKILL.md`** — the skill is the point (`list_components` is a pull; a skill's description is in context from session start). The pipeline is one direction: `source` (parse a URL, pin a commit) → `fetch` (download, verify, stage — refusing hostile archive members on our terms, not `tar`'s) → `manifest` (validate, read the skill frontmatter) → `plan` (PURE — no writes) → `tree` (copy / remove per unit, under ONE undo journal — `beginJournal`) → `install` (orchestrate + record + audit). **An install is one transaction**: `beginJournal` records every creation, copies every file it is about to overwrite into `projectPaths().packsBackup`, and remembers every directory the apply created — any throw unwinds in reverse and rethrows, so nothing lands. The provenance record is written as a `pending` marker (its own `.web-chat/packs/pending.json`, never `packs.json`, so `ownerOf`/`verifyPack`/`pack list` never see a half-install as installed) BEFORE the bytes and finalised after; a same-pack re-install diffs the previous record against the plan (`droppedUnits`, pure) and prunes the difference through `removeUnits` AFTER a successful apply. `lib/packs/install.js` and `lib/packs/plan.js` are held at zero `copyFileSync`/`unlinkSync`/`rmSync` by the conventions ratchet. `lib/server/routes/packs.js` and `lib/cli/commands/pack.js` are both thin over `lib/packs/install`. **Read the risk paragraph at the head of `routes/packs.js` before touching any of it**: the install endpoint is reachable by any pane and cannot distinguish a pane's `fetch` from a user's click. A builtin component name is a hard refusal with no override, in either tier, for either actor — `seedBuiltins` only repairs directories marked `builtin`, so a shadowing pack would win permanently.
- **New service-backed component**: ship `templates/components/<name>/` with `component.html` + `meta.json` + `service.js` (+ optional `seed.js`), add the name to `BUILTINS` in `lib/server/builtins.js`. The daemon runs `service.js` (via the supervisor, `lib/server/services.js`) while the pane is active. Full contract: `docs/service-components.md`.

**What restarts after which edit:** `public/*` → refresh browser (served from disk, no cache). `lib/server/*` and `lib/capture/*` → `claude-web-chat restart` (saved capture profiles also hot-reload live via `claude-web-chat profile reload`, no restart). `lib/hub/*` → restart the hub — but an instance restart self-heals it: the hub reports a `HUB_PROTOCOL_VERSION` in `/api/health`, and `ensureHub` (called on every instance boot) bounces a hub older than the current build, so bumping that version when hub routes change is enough. `lib/mcp/*` → `/exit` + reopen Claude Code. `lib/hooks/*` → nothing (fresh process per fire; the halt script too). `templates/settings.hooks.json` → reaches a project only when `claude-web-chat install`, `update` or `doctor` runs there (every other project keeps the hooks it has until then), and a Claude Code session already running may also need a restart: whether one picks up a hook `install` just registered is untested until validation gate V24 (c) passes, which is why every hook-upgrade line ends with `HOOK_RESTART_NOTE`. `lib/core/markdown.js` is also served to the browser from a per-process memo (`browserSrc`, read through `browserModuleSource()`), so an edit to it needs `claude-web-chat restart` AND a browser refresh. `lib/cli/*` → next invocation. `lib/portal/*` and `lib/tunnel/*` → `claude-web-chat tunnel down` then `tunnel up`; after a `PORTAL_PROTOCOL_VERSION` bump, `tunnel up` alone does both, because it restarts a portal from an older build.

## Conventions

- CommonJS (`require`/`module.exports`), Node 22.12+, no transpile. The floor is 22.12 because `node-html-parser` pulls in an ESM-only `entities`, and `require(esm)` is unflagged from 22.12 (22.0–22.11 have it only behind a flag) — below it the daemon does not start at all. `NODE_FLOOR` in `lib/core/versions` is that major.minor, and package.json `engines` and install.sh carry the same number. Developing needs 22.13+ (jsdom, the test devDependency) — see `docs/extending.md`.
- **One engine per concept, enforced.** `test/conventions.test.js` is a ratchet — it fails on a new *or newly-removed* occurrence of any banned construct (dynamic eval in both its spellings, `http.request(`, `os.homedir()`, the readline require, both hand-rolled HTML escapers, the design-token and component-name regexes, a raw `fs.watch(`, the redaction mask and the PEM marker, the bidi-override range, a sorted-keys serializer) outside its single allowed home (a baseline count grows only by a reviewed, reasoned entry, and a drop must be lowered in the same change); `docs/extending.md`'s tripwire table names each one and its home. Run the suite with `npm test`. See `docs/extending.md`.
- Forward-compat stubs exist for Claude Code plugin packaging: `.claude-plugin/plugin.json` and `.mcp.json` use `${CLAUDE_PLUGIN_ROOT}` to resolve bin paths. A project's own MCP registration is not in `.mcp.json` any more: `install`/`doctor` register it at Claude Code's local scope, and in this repo an entry pointing at the checkout's `bin/claude-web-chat-mcp.js` is accepted as it is (see `docs/extending.md`, dogfooding).
- **Distribution is GitHub Releases — npm is not involved at any point.** `scripts/build-release.js` builds a self-contained `claude-web-chat-<version>.tar.gz` whose tar is byte-reproducible — same tree → same tar bytes on any OS and Node (entry mtimes fixed, entries sorted, uid/gid 0) — with a pinned gzip header (MTIME 0, OS byte 255); the `.tar.gz` digest still matches only between builds linked against the same zlib — official nodejs.org binaries (what CI's setup-node installs) agree across 22.x and 24.x, Homebrew and distro Node do not — so the build summary prints `process.versions.zlib` and the uncompressed tar's sha256 to make a mismatch explainable. The tarball carries the `files` allowlist plus production `node_modules` (the four runtime deps mean a source tarball cannot run), and the build writes `SHA256SUMS` beside it; `.github/workflows/release.yml` attaches both to the release on a `v*` tag. `install.sh` and `claude-web-chat update` download it, verify the checksum, unpack into `~/.web-chat/versions/<v>/`, swap the `~/.web-chat/current` symlink and link three bins into `~/.local/bin` — no sudo, and `update --to <v>` rolls back to a version still on disk. `update` refuses to run from a git checkout or any other unmanaged copy (`lib/update/install-layout.js`). **macOS and Linux are supported; Windows means WSL2** — the policy, what CI does and does not prove, and the known cross-platform bugs are in `docs/platform-support.md`, with per-platform findings on the `platform/linux` and `platform/windows` branches. `package.json` keeps `"private": true` as an anti-publish guard — it makes an accidental `npm publish` fail fast.
